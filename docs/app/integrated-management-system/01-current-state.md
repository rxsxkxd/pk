# 現状の構成と課題

## 構成

```
                 統合管理システム（Rails 5）
                 ├─ テナント指定の検索
                 ├─ テナント横断の検索
                 └─ 検索結果に対するバッチ
                        │
        ┌───────────────┼──────────────────────┐
        ▼               ▼                      ▼
  tenant_001 DB   tenant_002 DB   …   tenant_200 DB      license DB
  （行動履歴）     （行動履歴）          （行動履歴）       （ライセンス管理）
```

検索もバッチも、**行動履歴 DB とライセンス DB の JOIN** を前提にしている。

## 課題

### 1. DB をまたぐ JOIN が成立する条件が限られる

| テナント DB の配置（Q1） | ライセンス DB との JOIN |
|---|---|
| ライセンス DB と**同じインスタンス上の別スキーマ** | SQL で書ける（`tenant_001.user_actions JOIN license_db.licenses`） |
| **別インスタンス** | SQL では書けない。RDS for MySQL は FEDERATED エンジンを使えないため、アプリ側で結合するしかない |

インスタンスの配置を変えると（負荷分散でテナントを別インスタンスへ移すなど）、同じインスタンスであることを前提にした SQL は動かなくなる。**配置の変更とアプリのコードが結びついている**ことが根本の問題である。

### 2. テナント横断の処理が「全 DB を順に回る」形になる

- 100〜200 回の接続と問い合わせが必要で、遅い。
- 途中で失敗したときに、どこまで処理したかが分からない。
- 横断の集計（並べ替え・ページングを含む）をアプリのメモリ上で行うことになる。

### 3. Rails 5 での接続の切り替え

Rails 5 には複数 DB を扱う標準機能がないため、`establish_connection` で接続先を切り替えていると考えられる（要確認）。この方式には次の問題がある。

- **接続プールが膨らむ**。DB ごとにプールができるため、最大で「DB 数 × プロセス数 × プールサイズ」の接続になりうる。RDS の `max_connections` に当たりやすい。
- **`establish_connection` は重い**。リクエストごとに呼ぶと、プールの作り直しが起きる。
- **スレッドセーフでない**。Puma や Sidekiq のスレッド間で接続先が混ざる事故が起きうる。
- 切り替えのコードが各所に散らばりやすく、「今どの DB に繋がっているか」をコードから追えない。

### 4. 関心事が 1 か所に混在している

次の 4 つが、1 つのアプリの中で「接続の切り替え＋JOIN」として絡み合っている。

1. テナント単位の参照（OLTP 的）
2. テナント横断の検索（分析的）
3. ライセンスという別の業務領域との結合
4. バッチ処理

それぞれ求められる性能特性（応答速度、鮮度、スループット）が違うのに、同じ仕組みで処理している。

### 5. DB を変えにくい

テナント DB とライセンス DB は、テナント向けシステムとライセンス管理システムも参照しており、それらは変更できない。**統合管理システムの都合で既存 DB のスキーマを変えたり、データを書き込んだりすることはできない**。整理は統合管理システム側で行う必要がある（[08](08-data-sync-options.md)）。

### 6. Rails 5 のサポートが終了している

Rails 5 と、それが動く Ruby（2.x 系）はすでにセキュリティ修正の提供が終わっている。構成の問題とは別に、**バージョンを据え置くこと自体がリスク**である（[06-platform-options.md](06-platform-options.md)）。
