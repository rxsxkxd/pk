# 整理の基本方針

## 結論

1. **3 つの関心事に分ける**: テナント DB（OLTP）、ライセンス DB（参照データ）、横断検索・分析の場。
2. **実行時に DB をまたいで JOIN しない**。用途に応じて A・B・C の 3 パターンのどれかに置き換える。
3. **接続の切り替えは 1 か所にまとめる**。どの DB に問い合わせるかを、呼び出し側のコードから隠す。

## 1. 3 つの関心事に分ける

```
① テナント DB（行動履歴）  … 書き込みと、テナント単位の参照だけ
② ライセンス DB            … マスタ／参照データ。小さく、更新頻度も低い（はず）
③ 横断検索・分析の場       … ①と②を集めた読み取り専用のストア
        ↑
   バッチは「テナント単位の処理」と「横断の集計（③を使う）」に分ける
```

| 関心事 | 求められる特性 | 置き場所 |
|---|---|---|
| テナント単位の参照・更新 | 応答速度、整合性 | ① テナント DB |
| ライセンス情報 | 正確さ、単一の正 | ② ライセンス DB |
| テナント横断の検索・集計 | 一括処理の速さ。鮮度は多少遅れてよい（Q2） | ③ 横断ストア（[03](03-cross-tenant-store.md)） |
| バッチ | スループット、再実行しやすさ | ①へのテナント単位ジョブ＋③（[04](04-batch-design.md)） |

## 2. DB をまたぐ JOIN を置き換える 3 パターン

現在の JOIN を 1 つずつ洗い出し、次のどれで置き換えるかを分類する。

### A. アプリ側で JOIN する

- 先にライセンス DB から対象（ライセンス・ユーザー ID など）を取得し、テナント DB を `WHERE user_id IN (...)` で引いてアプリ側で結合する。
- **向いている用途**: テナント指定の検索。
- **長所**: 今の Rails 5 のままでできる。インスタンスの配置に依存しない。Rails 7.0 以降なら `disable_joins: true` で関連として書ける（[05](05-rails-horizontal-sharding.md)）。
- **短所**: `IN` の要素が多いと遅い（数千件を超えるなら分割する）。ライセンス側の条件で並べ替えやページングをする検索には向かない。

### B. 参照データを複製する

> **制約により、既存のテナント DB への複製はできない**（[README](README.md) の制約）。複製するなら、統合管理システム側に新しく作る DB へ、テナントのデータとライセンスのデータの両方を集める形になる。これは [08](08-data-sync-options.md) の S2（集約レプリカ）・S3（CDC → クローン）にあたる。以下は制約が分かる前の一般論として残す。

- ライセンス情報のうち必要な列だけを、各テナント DB に同期する。テナント内の JOIN で済むようになる。
- **向いている用途**: テナント内の検索で、ライセンス情報による絞り込みや並べ替えが頻繁に必要な場合。
- **長所**: クエリが単純で速い。
- **短所**: 200 か所への同期を運用する必要がある（同期の遅れ、失敗時の再同期、スキーマ変更の追従）。**複製はあくまで読み取り用**で、更新はライセンス DB だけで行う。

### C. 横断用のストアに集約する

- 全テナントの行動履歴に `tenant_id` を付けて 1 か所に集め、ライセンスデータもそこに置く。
- **向いている用途**: テナント横断の検索・集計、横断のバッチの入力。
- **長所**: 横断検索が 1 本の SQL で済む。テナント DB に負荷をかけない。
- **短所**: 鮮度が遅れる。基盤を 1 つ増やすことになる。詳細は [03-cross-tenant-store.md](03-cross-tenant-store.md)。

### 選び方

```
その JOIN は…
├─ テナント横断？ ───────────────────────── Yes → C
└─ テナント指定
     ├─ ライセンス側の列で並べ替え・ページング？ ─ Yes → 統合管理システム側への集約（08 の S2／S3）または C
     └─ No → A
```

## 3. アプリ内の構造

| 部品 | 役割 |
|---|---|
| `TenantContext` | 「今どのテナントを処理しているか」を保持する。リクエストやジョブの入口で設定し、出口で必ず戻す |
| 接続の切り替え層 | `TenantContext` に応じて接続先を決める。**`establish_connection` を呼ぶのはここだけ**にする |
| Query Object／Repository | 検索ごとに、①②③のどこに問い合わせるかを内部に閉じ込める。呼び出し側は問い合わせ先を知らない |
| ライセンスのモジュール | ライセンスは別の境界づけられたコンテキストとして扱い、参照はモジュール（将来は API）経由にする。テナント DB 側の SQL から直接 JOIN させない |

### Rails 5 のままでの実装の選択肢（Q1 による）

| テナント DB の配置 | 切り替えの方法 |
|---|---|
| 同じインスタンス上の別スキーマ | インスタンスごとに 1 本の接続を張り、テーブル名をスキーマ付きで指定する（`self.table_name` を動的に切り替える、または `USE` 文）。接続数が増えない |
| 別インスタンス | インスタンス（またはテナント）ごとの抽象クラスを起動時に作って `establish_connection` しておき、実行時はクラスを選ぶだけにする。**実行時に `establish_connection` しない** |

Rails 6.1 以降に上げれば、この層の大部分は水平シャーディングの機能に置き換えられる（[05](05-rails-horizontal-sharding.md)）。
