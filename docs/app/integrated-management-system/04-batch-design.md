# バッチの設計

## 結論

- **1 ジョブ＝1 テナント**に分けて、キューから並列に処理する（fan-out）。
- **RDS インスタンスごとに同時実行数の上限**を設ける。
- ジョブは**冪等**にし、失敗したテナントだけを再実行できるようにする。
- テナント横断の集計は横断ストア（[03](03-cross-tenant-store.md)）で行い、テナント単位のジョブとは分ける。

## 処理の形

```
[起点]（スケジューラ／運用者の操作）
   │
   ├─ 対象テナントの決定
   │    ・テナント指定 → そのテナントだけ
   │    ・横断       → 横断ストアの検索結果から対象テナントと対象レコードを決める
   │
   ├─ テナントごとにジョブをキューへ積む（fan-out）
   │     job(tenant_id, 実行 ID, パラメータ)
   │
   ├─ ワーカーがテナント DB に対して処理する
   │     ・ライセンス情報が必要なら、ジョブの開始時にまとめて取得する（パターン A）
   │
   └─ 全テナント分の完了を集約する（fan-in）
         ・成功／失敗の一覧、再実行の対象
```

## 設計のポイント

### 同時実行数の制御

- 並列数を上げすぎると、同じ RDS インスタンス上のテナントにジョブが集中し、本番の応答が遅くなる。
- **インスタンス単位**で同時実行数の上限を設ける（テナント単位ではなく）。
- 接続数の見積もり: `ワーカー数 × スレッド数 × 1 ジョブあたりの接続数` が、各インスタンスの `max_connections` から本番の利用分を引いた残りに収まるようにする。足りなければ RDS Proxy を検討する。

### 冪等性と再実行

- ジョブの実行状態を `(実行 ID, tenant_id)` 単位で記録する（未実行／実行中／成功／失敗）。
- 書き戻しがある場合（Q3）は、「すでに処理済みか」を判定できる印（処理済みフラグ、処理した実行 ID、更新日時の比較など）を持たせ、2 回実行しても結果が変わらないようにする。
- 大量の行を更新するときは、小さい単位でコミットし、途中から再開できるようにする。

### 横断ストアとの関係

- 横断ストアのデータは遅れがありうる。**対象の抽出**には横断ストアを使ってよいが、**書き戻しの直前にはテナント DB の最新の状態で再確認**する。
- 集計だけで完結する処理（レポートの作成など）は、テナント DB に触れず横断ストアだけで行う。

### 失敗時の扱い

- 1 テナントの失敗で全体を止めない。失敗したテナントを一覧にして、あとから再実行できるようにする。
- テナント DB に接続できない（メンテナンス中など）場合は、自動で再試行し、上限回数を超えたら失敗として記録する。

## 実行基盤の選択肢

> AWS の定番構成（EventBridge Scheduler → Step Functions → ECS on Fargate）と、現状のバッチの調査の観点は [09-batch-on-ecs.md](09-batch-on-ecs.md) にまとめた。

| 選択肢 | 長所 | 短所 |
|---|---|---|
| **Sidekiq（既存の Rails の中）** | 既存のモデルとコードを流用できる | Rails 5 のスレッドと接続切り替えの問題を引き継ぐ。インスタンス単位の同時実行数の制御は追加の仕組みが要る |
| **SQS ＋ ECS のワーカー** | 規模に応じて増減できる。言語を選べる | キューとワーカーの基盤を用意する必要がある |
| **Step Functions（Map ステート）＋ ECS／Lambda** | fan-out・fan-in、再試行、並列数の上限（`MaxConcurrency`）を宣言的に書ける。実行履歴が残る | AWS への依存が増える。インスタンス単位の制御は、インスタンスごとに Map を分けるなどの工夫が要る |

- まずは**既存の Rails の中で、テナント単位のジョブ化と冪等化**を行う。基盤の移行はそのあとでもよい。
- バッチだけを別の言語・別のサービスに切り出す選択肢は [06-platform-options.md](06-platform-options.md) を参照。
