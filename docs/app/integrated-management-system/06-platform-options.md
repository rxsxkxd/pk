# Rails のバージョンアップと言語の置き換え

## 結論

- **Rails 7.x 系（できれば最新の安定版）へのバージョンアップを推奨**する。構成の整理の効果と、セキュリティの両方の理由から。
- **言語の置き換えだけでは、この問題は解決しない**。問題の原因はデータの配置とアクセスパターンであり、言語ではない。別システムへの置き換え（d）を選ぶ場合も、効果の中心はデータ連携層の設計にある（[10](10-replacement-architecture.md)）。
- 置き換えるとしても、**バッチや横断集計だけを別サービスに切り出す**部分的なもので十分なことが多い。
- DB 構成を変えられない制約のもとでは、**新しく作る部品（取り込みワーカー、テナント単位のバッチ）から Go／Python を採用する**のが現実的である（下記「一部を Go／Python に置き換える場合」）。

## 選択肢の比較

| 選択肢 | 構成の整理への効果 | 工数・リスク | 備考 |
|---|---|---|---|
| **a. Rails 5 のまま** | 小。接続の切り替え層は自前で作る（[02](02-architecture-direction.md)） | 小 | セキュリティ修正が出ないリスクが残り続ける |
| **b. Rails 7.x へバージョンアップ** | 大。水平シャーディング、`disable_joins`、`ShardSelector` が使える（[05](05-rails-horizontal-sharding.md)） | 中。5.2 → 6.0 → 6.1 → 7.0 → 7.1 … と段階的に上げる。Ruby のバージョンアップと gem の更新を伴う | 推奨 |
| **c. バッチ・横断集計だけ別サービス化** | 中〜大。バッチの基盤を自由に選べる | 中。2 つのコードベースで同じ業務ルールを持たないよう注意が要る | b と組み合わせられる |
| **d. 別システムへ置き換える** | 大。データ連携層から設計し直せる。言語を変えること自体の効果は小さく、効果はデータの持ち方を変えることから来る | 大。ただし既存 DB を変えないため、新旧を並行稼働して段階的に移せる | 構成案は [10](10-replacement-architecture.md) |

## a. Rails 5 のままの場合にやること

- 接続の切り替えを 1 か所に集約し、実行時の `establish_connection` をなくす（[02](02-architecture-direction.md)）。
- テナント単位のジョブ化と冪等化（[04](04-batch-design.md)）。
- 横断ストアの構築（[03](03-cross-tenant-store.md)）。Rails のバージョンに関係なく進められる。

いずれもバージョンアップ後に無駄にならない作業である。

## b. バージョンアップの進め方

1. テストの整備（特に DB の接続先が関わる処理）。
2. Rails 5.x の最新パッチ → 5.2 → 6.0 → 6.1 → 7.0 → 7.1 以降と、**1 段ずつ**上げる。各段で非推奨の警告をなくしてから次へ進む。
3. Ruby も Rails の各段に合わせて上げる。
4. 6.1 以降に上がった時点で、自前の接続の切り替え層を水平シャーディングに置き換える。

## c. 別サービスに切り出す場合

| 対象 | 候補 | 理由 |
|---|---|---|
| 横断の集計・レポート | SQL（Redshift／Athena）中心。必要なら Python | 処理の大半を横断ストアの SQL に寄せられる |
| テナント単位のバッチ | 既存の Rails のジョブ、または Go／Python の ECS タスク | 業務ルールを既存のモデルに持っているなら Rails のまま。ルールが単純なら単体のバイナリで配りやすい Go も候補 |
| 取り込み（ETL） | マネージドサービス（zero-ETL、DMS、Glue） | 自前のコードを持たない |

## 一部を Go／Python に置き換える場合

DB 構成をそのままにする前提では、置き換えの対象は**統合管理システムの中で、画面から切り離せる部分**になる。

### 置き換えの候補

| 対象 | 置き換える価値 | 推奨 |
|---|---|---|
| CDC イベントの取り込みワーカー（[08](08-data-sync-options.md) の S3） | 新しく作る部品なので、既存コードとの兼ね合いがない。常駐して大量のイベントを捌く | **Go**（並行処理が書きやすく、メモリが少なく、単一のバイナリで小さいイメージにできる） |
| テナント単位のバッチ（200 DB への fan-out） | Rails 5 の接続切り替えの問題から解放される。DB ごとの接続を明示的に扱える | **Go**。ただし業務ルールを Rails のモデルに多く持っている場合は Rails のまま ECS に載せる（[09](09-batch-on-ecs.md)） |
| 横断の集計・レポート、データの加工 | SQL で書ききれない集計や、CSV・Excel の出力 | **Python**（データ処理のライブラリが充実。AWS Glue や Athena との相性も良い） |
| 画面（管理画面の検索など） | 置き換えの効果が小さく、工数が大きい | **置き換えない**。Rails のバージョンアップで対応する |

### Go と Python の使い分け

| 観点 | Go | Python |
|---|---|---|
| 向いている処理 | 常駐ワーカー、並列の DB アクセス、決まった処理を速く安定して動かす | データの加工・集計、試行錯誤しながら作る処理 |
| 配布と実行 | 単一の静的バイナリ。コンテナイメージが小さい | ランタイムと依存ライブラリが要る |
| 型と保守 | 静的型。リファクタリングしやすい | 動的型（型ヒントで補う） |
| チームの習熟 | 要確認 | 要確認 |

**言語の数はなるべく増やさない**。Rails に加えて 1 言語（例えば新しい部品はすべて Go）に絞ると、運用と採用の負担が小さい。

### 切り出しの進め方

1. 新しく作る部品（取り込みワーカーなど）から新しい言語で作る。既存のコードには手を入れない。
2. 既存のバッチは、まず Rails のまま ECS に載せ（[09](09-batch-on-ecs.md)）、テナント単位のジョブ化を済ませる。
3. そのうえで、問題（性能、接続、テストのしにくさ）が大きいバッチから順に置き換える。**一律に置き換えることは目的にしない**。

注意点:

- **業務ルール（ライセンスの判定など）を 2 つのコードベースに重複させない**。重複しそうなら、ルールを持つ側に API を用意するか、ルールを SQL（横断ストアのビュー）に寄せる。
- テナントの一覧（接続先）は 1 か所で管理し、Rails 側と切り出したサービス側の両方がそれを読む。
