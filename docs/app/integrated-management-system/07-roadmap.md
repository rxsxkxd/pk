# 段階的な進め方

## 方針

- テナント DB・ライセンス DB とそれを使う他システムは変更しない（[README](README.md) の制約）。整理は統合管理システム側で行う。
- **改修で進める（トラック A）か、別システムへ置き換える（トラック B）かに関係なく、共通の土台（ステップ 0〜3）から始める**。どちらに進んでも無駄にならない。
- 改修か置き換えかは、ステップ 1 の棚卸しの結果を見て決める。

## 共通のステップ

| # | ステップ | 内容 | 成果物 | 関連 |
|---|---|---|---|---|
| 0 | 前提の確認 | Q1〜Q6 の回答を集める。特に Q5（既存 DB の RDS 設定に触れられるか）は DB の所有者との合意が要るため早めに着手する | README の確認事項の更新 | [README](README.md) |
| 1 | 棚卸し | 統合管理システムの機能（画面・検索・バッチ）、DB をまたぐ JOIN、テナント横断の処理、現状のバッチの仕組みを一覧にする | 機能一覧、JOIN・横断処理の一覧、バッチの一覧 | [02](02-architecture-direction.md), [09](09-batch-on-ecs.md) |
| 2 | データ連携層 | 08 の選択肢から方式を決めて構築する（第一候補は S2 集約レプリカ。成立しなければ S3 CDC → クローン） | 集約レプリカ or クローン DB、テナント台帳 | [08](08-data-sync-options.md) |
| 3 | バッチ基盤 | EventBridge Scheduler → Step Functions → ECS on Fargate を用意する。既存のバッチを（まずは今のコードのまま）コンテナで動かせるようにする | バッチ基盤、コンテナイメージ | [04](04-batch-design.md), [09](09-batch-on-ecs.md) |

ステップ 2 と 3 は並行して進められる。

## 判断ポイント：改修か、置き換えか

ステップ 1 の棚卸しの結果で決める。

| 置き換え（トラック B）に傾く条件 | 改修（トラック A）に傾く条件 |
|---|---|
| 使われていない機能が多く、作り直すほうが小さく済む | 機能が多く、どれも使われている |
| Rails 5 からのバージョンアップの工数が大きい（gem の更新が難しい、テストがない） | テストがあり、段階的なバージョンアップが現実的 |
| 用途が検索・集計・レポート中心で、データ基盤＋BI（10 の R3）で多くを賄える | 画面からの更新操作や細かい業務ルールが多い |
| チームが新しい技術（Go など）で長期的に保守したい | チームが Ruby 中心で、今のコードの知識を活かしたい |

## トラック A：改修で進める

| # | ステップ | 内容 | 関連 |
|---|---|---|---|
| A1 | 接続の切り替え層 | `TenantContext` と接続管理を 1 か所にまとめ、実行時の `establish_connection` をなくす。参照先をステップ 2 のデータ連携層に切り替える | [02](02-architecture-direction.md) |
| A2 | バッチの fan-out | テナント単位のジョブ化、同時実行数の制御、冪等化。ステップ 3 の基盤に載せる | [04](04-batch-design.md) |
| A3 | Rails のバージョンアップ | 6.1 を経由して 7.x 以降へ。A1 の層を水平シャーディングに置き換える（データ連携層に S2 を選んだ場合は不要なこともある） | [05](05-rails-horizontal-sharding.md), [06](06-platform-options.md) |
| A4 | 部分的な言語の置き換え | 必要に応じて、取り込みワーカーや一部のバッチを Go／Python で作る | [06](06-platform-options.md) |

## トラック B：別システムへ置き換える

| # | ステップ | 内容 | 関連 |
|---|---|---|---|
| B1 | 構成案の決定 | R1（Rails で作り直す）／R2（Go API＋SPA）／R3（データ基盤＋BI）から選ぶ。組み合わせも可 | [10](10-replacement-architecture.md) |
| B2 | バッチから移す | 新旧を同じ入力で動かして結果を比べ、一致を確かめてから旧バッチを止める | [10](10-replacement-architecture.md) |
| B3 | 画面・検索を移す | 読み取りだけの画面から順に移す | [10](10-replacement-architecture.md) |
| B4 | 旧システムの停止 | 旧システムの DB 接続ユーザーを無効にして停止する | — |

旧システムは B4 まで動き続けるため、トラック B の期間中も旧システムのセキュリティリスク（Rails 5）は残る。期間が長くなるなら、旧システムの最低限の対策（公開範囲の制限など）も合わせて検討する。

## 先に決めておきたいこと

- Q5（既存 DB の RDS 設定に触れられるか）。ステップ 2 の方式が決まる。
- Q2（横断検索の鮮度）と Q3（書き戻しの有無）。データ連携層とバッチの設計が決まる。
- 改修か置き換えかを判断する時期（ステップ 1 の完了時点を想定）。
