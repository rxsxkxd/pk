# DB 構成を変えずにデータを統合管理システム側へ持ってくる選択肢

> 位置づけ: **検討中のメモ**である。[README](README.md) の制約（テナント DB・ライセンス DB とそれを使うシステムは変更できない）を前提に、選択肢を並べる。

## 前提と制約

- テナント DB とライセンス DB は、**テナント向けシステム**と**ライセンス管理システム**も参照している。これらのシステムは変更できない。
- そのため、次のことはできない（またはしない）。
  - テナント DB・ライセンス DB のスキーマの変更（列やテーブルの追加、トリガーの追加を含む）
  - テナント向けシステム・ライセンス管理システムのコードの変更（例: 登録時に SQS へイベントを発行する処理の追加）
  - 統合管理システムからテナント DB・ライセンス DB へ、統合管理システム都合のデータを書き込むこと
- 一方で、次のことは**統合管理システム側の判断でできる**と想定する。
  - 統合管理システム専用の DB・ストア・キュー・ワーカーを新しく作ること
  - 既存 DB の**読み取り**（現状も行っている）
- 次のことは **DB の所有者との合意が必要**（Q5）。スキーマやアプリは変えないが、RDS の設定に触れる。
  - リードレプリカの作成
  - バイナリログの設定（`binlog_format=ROW`、保持期間の延長）
  - レプリケーション・CDC 用の DB ユーザーの作成

## 選択肢の一覧

| # | 選択肢 | 既存 DB への影響 | 鮮度 | 統合管理システムの SQL の変更 | 運用負荷 |
|---|---|---|---|---|---|
| S0 | 直接参照を続け、アプリ側を整理する | なし（現状どおり） | リアルタイム | 中（JOIN をアプリ側結合へ） | 小 |
| S1 | リードレプリカを参照する | 小（レプリカ作成） | 数秒 | S0 と同じ | 小 |
| **S2** | **集約レプリカ（マルチソースレプリケーション）** | 小（バイナリログ設定、レプリケーション用ユーザー） | 数秒 | **小（今の SQL がほぼそのまま動く）** | 中 |
| **S3** | **CDC → イベント → 統合管理システム側のクローン** | 小（バイナリログ設定、CDC 用ユーザー） | 数秒〜数分 | 中（クローンの設計次第） | 中〜大 |
| S4 | 定期的な差分抽出（ポーリング） | 読み取り負荷のみ | 数分〜日次 | 中 | 中 |
| S5 | 分析基盤への複製（zero-ETL／スナップショットのエクスポート） | 小〜なし | 数秒〜日次 | 大（Redshift／Athena 向けに書き直し） | 小〜中 |

## S0. 直接参照を続け、アプリ側を整理する

- DB には何もしない。統合管理システム側で、接続の切り替え層と、アプリ側での JOIN（パターン A）に整理する（[02](02-architecture-direction.md)）。
- テナント横断の処理は全 DB を順に回る形のまま残るため、**テナント指定の検索が中心で、横断処理が少ない場合**に向く。
- 本番 DB に統合管理システムの負荷がそのままかかる点は変わらない。

## S1. リードレプリカを参照する

- テナント DB（のインスタンス）とライセンス DB にリードレプリカを作り、統合管理システムはレプリカだけを読む。
- 本番（テナント向けシステム・ライセンス管理システム）への負荷を切り離せる。
- DB をまたぐ JOIN の問題は解決しないため、**S0 と組み合わせる**前提。
- テナント DB がインスタンスごとに分かれている場合（Q1）、レプリカの数も増える（費用に注意）。

## S2. 集約レプリカ（マルチソースレプリケーション）

```
tenant インスタンス群 ─┐ binlog
                       ├──────────▶ 集約レプリカ（RDS for MySQL、統合管理システム専用）
license インスタンス ──┘             ├─ tenant_001 スキーマ
                                     ├─ tenant_002 スキーマ …
                                     └─ license_db スキーマ
```

- 統合管理システム専用の RDS for MySQL を 1 台用意し、各テナント DB とライセンス DB から**レプリケーションで集める**。RDS for MySQL はマルチソースレプリケーションに対応している（対応バージョンは要確認）。
- すべてのスキーマが 1 台に揃うため、**スキーマをまたぐ JOIN（`tenant_001.x JOIN license_db.y`）が今の SQL のまま動く**。統合管理システムの変更が最も少ない。
- ソースへの影響はバイナリログの送出だけで、スキーマもアプリも変わらない。
- 集約レプリカは**読み取り専用**として扱う。統合管理システム自身のデータは別の DB に置く。

要確認:

- 1 台に集約できるソースの数の上限（MySQL のレプリケーションチャネルの上限と、RDS 側の制約）。テナント DB が少数のインスタンスに載っていれば（Q1）、チャネル数はインスタンスの数で済む。
- **スキーマ名の衝突**。テナント DB がインスタンスごとに同じスキーマ名（例: すべて `app`）の場合、そのままでは 1 台に集約できない。スキーマ名を書き換えるレプリケーションフィルタが RDS で使えるかを確認する。
- 集約レプリカのサイズ（全テナント分のデータが載る）と、レプリケーション遅延。
- テナントの追加時に、チャネル（またはフィルタ）を追加する手順。

横断の集計が重い場合は、集約レプリカに MySQL のまま集計させるのではなく、S5 と組み合わせる。

## S3. CDC → イベント → 統合管理システム側のクローン

例として挙げた「テナント DB の一部データを、登録イベントの発行時に SQS で統合管理システム側のクローンにも登録する」は、**テナント向けシステムを変更できないため、アプリからイベントを発行する形では実現できない**。代わりに、**DB のバイナリログから変更を拾って（CDC）イベントにする**。

```
tenant DB / license DB
   │ binlog（変更を読むだけ）
   ▼
CDC（DMS または Debezium）
   │
   ▼
Kinesis Data Streams / MSK（Kafka）
   │                    （必要なら EventBridge Pipes などで SQS へ流す）
   ▼
取り込みワーカー（ECS のサービス。Go／Python／Rails のどれでも）
   │ 必要な列だけ、tenant_id を付けて書き込む
   ▼
統合管理システム側のクローン DB（統合管理システムの専用 DB）
```

| CDC の手段 | 特徴 |
|---|---|
| **AWS DMS** | マネージド。出力先に Kinesis Data Streams・Kafka・S3・MySQL などを選べる（SQS は直接の出力先ではない）。テナント数が多いと、タスクとレプリケーションインスタンスの設計が要る |
| **Debezium（MSK Connect など）** | OSS の CDC。イベントの形式が詳しく、行単位の変更イベントとして扱いやすい。Kafka（MSK）の運用が増える |

- **長所**: クローンのスキーマを統合管理システムの都合で設計できる（`tenant_id` 付きの 1 テーブル、ライセンスとの結合済みのテーブルなど）。必要なテーブル・列だけを持てる。イベントを契機に別の処理（通知、バッチの起動）も行える。
- **短所**: 取り込みワーカーの開発と運用が要る（順序、重複、再送、初期データの投入、スキーマ変更への追従）。最も作り込みが多い。

設計の注意:

- **初期データの投入（フルロード）と、その後の変更の追従**の切り替え手順を決めておく。DMS は「フルロード＋CDC」を 1 つのタスクで扱える。
- 同じ行の変更が順序どおりに届くよう、ストリームの分割キーを `tenant_id + 主キー` にする。
- 取り込みは **upsert で冪等**にする（同じイベントが 2 回届いても結果が同じ）。
- 削除の扱い（物理削除するか、削除フラグにするか）を決める。

## S4. 定期的な差分抽出（ポーリング）

- 一定間隔で各テナント DB を読み、前回以降に変わった行をクローンに取り込む。
- バイナリログの設定が不要で、**既存 DB の設定を一切変えずにできる**。
- 差分の判定には、既存のテーブルに `updated_at` や単調増加の ID が必要（スキーマを追加できないため、**既存の列で判定できるテーブルに限られる**）。
- **削除を検出できない**。削除の反映が必要なら、定期的な全件の突き合わせが要る。
- 読み取りの負荷は S1 のリードレプリカに向けると本番への影響を避けられる。

## S5. 分析基盤への複製

- RDS for MySQL → Redshift の zero-ETL 統合、または DMS や RDS スナップショットのエクスポートで S3 に置き、Athena で検索する。詳細は [03-cross-tenant-store.md](03-cross-tenant-store.md)。
- 横断の集計・レポートに強いが、統合管理システムの SQL は Redshift／Athena 向けに書き直しになる。
- S2・S3 と排他ではなく、**画面の検索は S2／S3、重い集計は S5** のように分担できる。

## 選び方

```
既存 DB の RDS 設定（binlog・レプリカ）に触れられる？（Q5）
├─ No  → S0（＋読み取り負荷が問題なら S4 を検討）
└─ Yes
     ├─ 統合管理システムの SQL をなるべく変えたくない → S2（集約レプリカ）
     ├─ 統合管理システム用にデータの形を変えたい
     │   ／変更を契機に処理を動かしたい               → S3（CDC → クローン）
     └─ 横断の集計・レポートが中心                    → S5（S2・S3 と併用も可）
```

最初の一手としては、**S2（集約レプリカ）を検証してみる**のが、変更の少なさと効果のバランスが良い。スキーマ名の衝突やチャネル数の上限で S2 が成立しない場合に、S3 へ進む。
