# 統合管理システムを別システムへ置き換える場合の構成案

> 位置づけ: **検討中のメモ**である。統合管理システムを改修するのではなく、**新しいシステムに置き換える**場合の構成案を並べる。テナント DB・ライセンス DB とそれを使う他システムは変更しない（[README](README.md) の制約）。

## 前提

- 置き換えるのは**統合管理システムだけ**。テナント DB・ライセンス DB はそのまま残り、新システムは**読み取り**でデータを得る。
- 新システムは、自分専用の DB・ストア・キュー・ワーカーを持ってよい。
- 新旧のシステムは、同じ既存 DB を読むだけなので**並行稼働できる**。機能単位で少しずつ移せる。

## どの案にも共通する土台

置き換えの方式に関係なく、次の 3 つは必要になる。アプリより先に作れる。

```
            既存（変更しない）                          新システム
 ┌──────────────────────────────┐        ┌─────────────────────────────────────────┐
 │ tenant DB × 100〜200         │ binlog │ ① データ連携層                           │
 │ license DB                   │──────▶│   集約レプリカ（08 の S2）              │
 │ （テナント向けシステム、       │        │   または CDC → クローン DB（08 の S3）  │
 │   ライセンス管理システムが利用）│        │                                         │
 └──────────────────────────────┘        │ ② 新システム自身の DB                    │
                                         │   テナント台帳、バッチの実行状態、        │
                                         │   新システムが持つ業務データ              │
                                         │                                         │
                                         │ ③ バッチ基盤                             │
                                         │   EventBridge Scheduler → Step Functions │
                                         │   → ECS on Fargate（09）                │
                                         └─────────────────────────────────────────┘
```

| 土台 | 内容 | 詳細 |
|---|---|---|
| ① データ連携層 | 既存 DB のデータを、新システムが扱いやすい形で手元に置く | [08](08-data-sync-options.md) |
| ② 新システムの DB | **テナント台帳**（tenant_id、接続先、状態）を新システムの正とする。バッチの実行状態や、新システム固有のデータもここに置く | — |
| ③ バッチ基盤 | テナント単位の fan-out、再実行、通知 | [04](04-batch-design.md), [09](09-batch-on-ecs.md) |

**既存 DB への書き戻し**（バッチの結果をテナント DB に反映するなど。Q3）がある場合は、①を経由せず、③のバッチから既存 DB へ直接書く。書き込み先のテーブルと列は、今の統合管理システムが書いているものに限る（他システムとの取り決めを変えないため）。

## 構成案

### 案 R1. 最新の Rails で作り直す（モジュラーモノリス）

```
CloudFront ─▶ ALB ─▶ ECS on Fargate（Rails 8：画面＋API）
                          │
                          ├─▶ ① 集約レプリカ（読み取り。今の SQL をほぼ流用）
                          └─▶ ② 新システムの DB（Aurora MySQL など）
バッチ: EventBridge Scheduler → Step Functions → ECS（同じ Rails イメージ）
```

- 今の統合管理システムの SQL や業務ルールを**読み替えて流用しやすい**。チームの習熟もそのまま活かせる。
- ①に集約レプリカ（S2）を使えば、スキーマをまたぐ JOIN が今のまま動くため、移行の工数が最も小さい。
- 1 つのアプリの中を「テナント検索」「ライセンス」「バッチ」などのモジュールに分け、モジュール間は決めたインターフェースだけで呼び合う。
- **向いている場合**: 画面が多い、業務ルールが Rails のコードに多く埋まっている、チームが Ruby 中心。

### 案 R2. API（Go）＋ SPA に分ける

```
CloudFront ─┬─▶ S3（SPA：React など）
            └─▶ ALB ─▶ ECS on Fargate（Go の API）
                              │
                              ├─▶ ① CDC → クローン DB（新システム向けに設計したスキーマ）
                              └─▶ ② 新システムの DB
CDC の取り込みワーカー: ECS サービス（Go）
バッチ: EventBridge Scheduler → Step Functions → ECS（Go）
```

- ①に CDC → クローン（S3）を使い、**新システムの都合でスキーマを設計し直す**（`tenant_id` 付きの 1 テーブル、ライセンスと結合済みのテーブルなど）。DB をまたぐ JOIN の問題が根本から消える。
- API・取り込みワーカー・バッチをすべて Go に揃えると、言語は Go と画面用の TypeScript の 2 つで済む。
- **向いている場合**: 画面とバッチを長く保守していく前提で、作り込みの時間がとれる。チームに Go の経験がある。
- **注意**: 作るものが最も多い（CDC の運用、クローンのスキーマ設計、画面の作り直し）。

### 案 R3. データ基盤＋BI を中心にする

```
① zero-ETL → Redshift（または DMS／エクスポート → S3 → Athena）
      │
      ├─▶ 検索・集計・レポート: QuickSight などの BI（画面を作らない）
      └─▶ バッチ: Step Functions → ECS（Python／Go）、または Redshift／Athena の SQL
小さな管理画面だけを別に用意する（必要なら）
```

- 統合管理システムの用途が**主に検索・集計・レポートとバッチ**で、画面からの更新操作が少ないなら、画面の大半を BI に置き換えられる。
- 作るものが最も少ない。横断の集計に強い。
- **向いている場合**: 利用者が社内の運用者で、定型の検索やレポートが中心。
- **注意**: 細かい画面操作や、権限の作り込み（テナントごとに見せる範囲を変えるなど）は BI では難しいことがある。

## 比較

| 観点 | R1 Rails で作り直す | R2 Go API＋SPA | R3 データ基盤＋BI |
|---|---|---|---|
| データ連携層（08） | S2 集約レプリカ（S3 も可） | S3 CDC → クローン | S5 分析基盤 |
| 今の SQL・ロジックの流用 | ◎ | △（設計し直し） | ○（SQL は方言の書き換え） |
| 作る量 | 中 | 大 | 小 |
| テナント横断の検索・集計 | ○（重い集計は S5 を併用） | ○ | ◎ |
| 細かい画面操作 | ◎ | ◎ | △ |
| 長期の保守のしやすさ | ○ | ◎ | ○ |
| 必要なスキル | Ruby | Go、TypeScript、CDC の運用 | SQL、BI、Python |

R1 と R3 は組み合わせられる（画面は R1、重い集計とレポートは R3）。

## 移行の進め方（ストラングラー方式）

新旧を並行稼働させ、機能ごとに新システムへ移す。既存 DB を変えないため、切り戻しも容易である。

1. **土台を作る**: ①データ連携層、②新システムの DB とテナント台帳、③バッチ基盤。この段階では旧システムに影響しない。
2. **機能の棚卸し**: 今の統合管理システムの画面・検索・バッチを一覧にし、利用頻度と重要度で移行の順番を決める。使われていない機能は移さない。
3. **バッチから移す**: 画面より切り離しやすく、Step Functions の実行履歴で新旧の結果を比べやすい。新旧を同じ入力で動かし、結果が一致することを確かめてから旧バッチを止める。
4. **画面・検索を移す**: 読み取りだけの画面から先に移す。
5. **旧システムを止める**: 全機能を移したら、旧システムの接続ユーザーを無効にして停止する。

## 決めるために必要な情報

- 今の統合管理システムの**機能の一覧**（画面、検索、バッチ）と、それぞれの利用者・利用頻度
- 画面からの**更新操作**の有無と量（R3 が成り立つか）
- 既存 DB への**書き戻し**の有無（Q3）
- 既存 DB の RDS 設定に触れられるか（Q5。①の方式が決まる）
- チームの言語の経験（Ruby／Go／Python／TypeScript）と、置き換えにかけられる期間
