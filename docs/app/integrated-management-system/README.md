# 統合管理システムの整理と置き換え

> 位置づけ: **検討中のメモ**である。方針は未決定で、[前提として確認が必要なこと](#前提として確認が必要なこと) の回答によって結論が変わる。

## 対象システム

- テナントごとに**ユーザー行動履歴 DB** がある（100〜200 テナント）。
- テナントとは別に、**ライセンス管理情報の DB** が 1 つある。
- **統合管理システム**（Rails 5、複数 DB 機能なし）から、次のことをしている。
  - テナントを指定して、またはテナントを横断して、行動履歴 DB とライセンス DB を JOIN して検索する。
  - 検索結果に対してバッチ処理を行う。
- DB はすべて RDS for MySQL。
- Rails のバージョンは据え置きの方向だが、バージョンアップや言語の置き換え、**別システムへの置き換え**も選択肢に含めてよい。
- 現状のバッチがどの仕組みで動いているかは未調査。

## 制約

- **テナント DB とライセンス DB は、別のシステム（テナント向けシステム、ライセンス管理システム）も参照しており、それらは変更できない。**
- そのため、テナント DB・ライセンス DB の構成（スキーマ）はなるべくそのままにし、整理は統合管理システム側で行う。既存 DB の RDS 設定（リードレプリカ、バイナリログ）に触れるかは DB の所有者との合意次第（Q5）。
- 統合管理システム専用の DB・ストア・キュー・ワーカーは新しく作ってよい前提とする。

## 前提として確認が必要なこと

どの手が使えるかは次の点で決まる。未回答のものは各ドキュメントで「要確認」としている。

| # | 確認点 | 影響するドキュメント |
|---|---|---|
| Q1 | テナント DB は**同じ RDS インスタンス上の別スキーマ**か、**インスタンスごとに別**か（混在か） | 01, 02, 05 |
| Q2 | テナント横断検索に求める**鮮度**（リアルタイム／数分遅れ／日次で可） | 03 |
| Q3 | バッチは**読むだけ**か、**テナント DB へ書き戻す**か | 04 |
| Q4 | 行動履歴の**データ量**（テナントあたり・全体の行数と増加ペース） | 03, 04 |
| Q5 | 既存 DB の **RDS 設定に触れられるか**（リードレプリカの作成、バイナリログの `binlog_format=ROW` と保持期間、レプリケーション・CDC 用ユーザーの作成） | 08 |
| Q6 | 現状のバッチが**どの仕組みで動いているか**（cron、Sidekiq、ECS など） | 04, 09 |

追加で分かると判断しやすくなること。

- ライセンス DB のサイズと更新頻度
- テナントの追加・削除の頻度（月に何件か）
- 統合管理システムの利用者（社内運用者だけか、顧客も使うか）
- 現在の接続切り替えの実装（`establish_connection` の呼び方、gem の利用有無）
