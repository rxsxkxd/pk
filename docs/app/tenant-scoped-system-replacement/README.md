# テナントを指定して使うシステムの置き換え

> 位置づけ: **検討中のメモ**である。統合管理システム（[../integrated-management-system/](../integrated-management-system/README.md)）とは別のシステムを対象にする。テナント台帳・認証・実行基盤などの共通の土台は、統合管理システムの置き換えと共有する前提で書いている。

## 対象システム

- マルチテナントのシステムで、**テナントを 1 つ指定し、そのテナントの DB を参照する**。
- テナント向けシステムとも、統合管理システムとも別のシステムである。
- テナントごとに、**メイン DB** とは別に**追加の DB** がある。追加の DB は、テナントごとの RDS インスタンス（メイン DB と同じインスタンス）上にある（解釈が正しいか要確認: T1）。
- メイン DB と追加の DB の間で、**スキーマをまたぐ JOIN** をしている。

```
テナント A の RDS インスタンス            テナント B の RDS インスタンス
├─ main_db（テナント向けシステムも利用）    ├─ main_db
└─ extra_db（追加の DB）                   └─ extra_db
     ↑ main_db.x JOIN extra_db.y               ↑ 同上
```

## 統合管理システムとの違い

| 観点 | 統合管理システム | このシステム |
|---|---|---|
| 1 回の処理で触るテナント | 複数（横断）あり | **常に 1 つ** |
| DB をまたぐ JOIN | テナント DB ⇔ ライセンス DB（**別インスタンス**になりうる） | メイン DB ⇔ 追加の DB（**同じインスタンス**） |
| JOIN の成立 | インスタンスの配置次第で成立しない | 同じインスタンスなので SQL で成立する |

このシステムの JOIN は**テナントの中で閉じている**ため、統合管理システムほど構造上の問題は大きくない。置き換えでは、**このデータの配置（テナントのインスタンスにメイン DB と追加の DB が同居する形）を活かし、アプリ側の作りを整える**のが基本方針になる。

## 結論

1. **データの配置は変えない**。追加の DB はメイン DB と同じインスタンスに置いたままにし、JOIN はそのインスタンスの中で SQL で行う。
2. 新システムは「**リクエストごとにテナントを 1 つに決め、そのテナントのインスタンスにだけ接続する**」ステートレスなアプリとして作る。
3. 接続はテナント（インスタンス）単位で 1 つのプールを持ち、**メイン DB と追加の DB を同じ接続でスキーマ名付きで参照する**。
4. テナント台帳（接続先）、認証、実行基盤は、統合管理システムの置き換え（[10](../integrated-management-system/10-replacement-architecture.md)）と**共通の土台**にする。

## 構成

```
利用者 ─▶ CloudFront ─▶ ALB ─▶ ECS on Fargate（新システム：ステートレス）
                                  │
                                  │ ① リクエストからテナントを決める
                                  │   （URL・サブドメイン・ログインユーザーの所属）
                                  │ ② テナント台帳で接続先を引く
                                  │ ③ そのテナントのインスタンスへの接続プールを使う
                                  ▼
                       テナント X の RDS インスタンス
                       ├─ main_db   （読み取り。書き込みは今の範囲に限る）
                       └─ extra_db  （このシステムのデータ）

共通の土台（10 と共有）
├─ テナント台帳（tenant_id → ホスト、スキーマ名、認証情報の参照先、状態）
├─ Secrets Manager（テナントごとの DB 認証情報）
├─ 認証（SSO／Cognito など。ユーザーとテナントの対応を持つ）
└─ バッチ基盤（EventBridge Scheduler → Step Functions → ECS。09）
```

### アプリの要点

| 項目 | 内容 |
|---|---|
| テナントの決定 | リクエストの入口で 1 回だけ決め、処理中は変えない（Rails 7.1 以降なら `ShardSelector` の `lock: true`、Go ならリクエストのコンテキストに入れる） |
| 接続 | テナントのインスタンスごとに 1 つの接続プール。使われたときに作り、一定時間使われなければ閉じる。100〜200 インスタンス × アプリのタスク数で接続数を見積もる |
| SQL | `main_db.users JOIN extra_db.user_settings` のようにスキーマ名付きで書く。スキーマ名はテナント台帳から引き、SQL に直書きしない（テナントによって名前が違う場合に備える） |
| 権限の分離 | テナントごとに DB ユーザーを分け、そのテナントのスキーマにだけ権限を与える。アプリのバグで別テナントのデータを読む事故を DB 側でも防ぐ |
| 書き込み | メイン DB への書き込みがある場合（T2）は、今のシステムが書いているテーブル・列に限る。テナント向けシステムとの取り決めを変えないため |

### 実装の選択肢

| 選択肢 | テナントの切り替え | 向いている場合 |
|---|---|---|
| Rails 7.1 以降（8 系） | 水平シャーディングでインスタンスを 1 シャードとし、`ShardSelector` でリクエストから選ぶ。JOIN は同じ接続の中なのでそのまま書ける（[05](../integrated-management-system/05-rails-horizontal-sharding.md)） | 今のシステムが Rails で、ロジックを流用したい |
| Go | テナント ID → `*sql.DB`（接続プール）の対応表を持ち、初回アクセスで作る。リクエストのコンテキストでテナントを渡す | 統合管理システムの置き換えを Go（10 の R2）で行う場合に揃える |

どちらでも成り立つ。**統合管理システムの置き換えと同じ言語・同じ土台に揃える**ことを優先する。

## 追加の DB の扱い（所有者による）

追加の DB を**このシステムだけが使っている**なら（T3）、置き換えの中でスキーマを変えてよい。選択肢は次のとおり。

| 案 | 内容 | JOIN | 評価 |
|---|---|---|---|
| **X1. 今の配置のまま（推奨）** | テナントのインスタンスに同居させたまま、必要ならスキーマを整理する | SQL で成立 | テナントごとの分離が保たれ、データが近い。変更が最も少ない |
| X2. 追加の DB を 1 つに集約 | 全テナント分の追加データを、新システム専用の DB に `tenant_id` 付きで集める | **成立しない**（別インスタンス）。アプリ側で結合するか、メイン DB の複製（08 の S2／S3）が要る | 追加データのテナント横断の集計はしやすくなるが、JOIN の問題を新たに作る。**横断の要件が強い場合に限る** |
| X3. 追加の DB をメイン DB に統合 | 追加のテーブルをメイン DB に移す | 同じスキーマの中で成立 | メイン DB はテナント向けシステムと共有で変更できないため、**採れない** |

X1 を選んだうえで、追加データをテナント横断で集計したい要件があれば、統合管理システム向けのデータ連携層（[08 データ連携の選択肢](../integrated-management-system/08-data-sync-options.md)）に追加の DB も含めて取り込めばよい。

### 追加の DB のスキーマ変更

X1 でスキーマを変える場合、マイグレーションを 100〜200 インスタンスに適用する必要がある。

- マイグレーションはテナント単位のジョブにして、バッチ基盤（Step Functions の Map → ECS）で並列に流す（[09](../integrated-management-system/09-batch-on-ecs.md)）。
- テナントごとの適用状況（どのバージョンまで適用済みか）を記録し、失敗したテナントだけを再実行できるようにする。
- 新旧のアプリが並行稼働する期間があるため、**後方互換のある変更**（列の追加 → アプリの切り替え → 古い列の削除）に分ける。

## 移行の進め方

既存の DB を使い続けるため、新旧を並行稼働させて切り替えられる。

1. **共通の土台**を用意する（テナント台帳、認証、ECS、Secrets Manager）。統合管理システムの置き換えと同時に進める。
2. **画面・機能の棚卸し**をして、移行の順番を決める。
3. **テナント単位で切り替える**。テナント台帳に「新／旧どちらのシステムを使うか」を持たせ、一部のテナント（社内の検証用テナントなど）から新システムへ移す。問題があればそのテナントだけ旧システムへ戻せる。
4. 全テナントを移したら旧システムを止める。

テナント単位で切り替えられるのは、このシステムが**1 回の処理で 1 テナントにしか触らない**からである。統合管理システム（機能単位で切り替える）との違いとして押さえておく。

## 統合管理システムとまとめるか

両方を置き換えるなら、**1 つの新システムの中の 2 つのモジュール**にする選択肢もある。

| 案 | 内容 | 向いている場合 |
|---|---|---|
| 別々のシステム（土台だけ共有） | テナント台帳・認証・実行基盤を共有し、アプリは分ける | 利用者や権限が違う（例: このシステムはテナントの担当者、統合管理システムは社内の運用者） |
| 1 つのシステムの 2 モジュール | テナントを指定する画面（テナントのインスタンスへ直接）と、横断の画面（データ連携層へ）を 1 つのアプリに収める | 利用者が同じで、画面を行き来する |

どちらにしても、データへのアクセスは次の 2 種類に整理される。**システムの境界より、このアクセスの種類で設計を分ける**ことが重要である。

| アクセスの種類 | 接続先 | 鮮度 | 書き込み |
|---|---|---|---|
| テナントを指定したアクセス | テナントのインスタンス（メイン DB＋追加の DB） | リアルタイム | 可（決められた範囲） |
| テナント横断のアクセス | データ連携層（08） | 数秒〜日次 | 不可（書き戻しはバッチ経由） |

## 確認が必要なこと

| # | 確認点 | 影響 |
|---|---|---|
| T1 | 追加の DB は、メイン DB と**同じ RDS インスタンス**にあるか（テナント 1 つにインスタンス 1 台か、複数テナントで 1 台か） | 接続の単位と接続数の見積もり |
| T2 | このシステムは**メイン DB に書き込む**か | 書き込みの範囲と、テナント向けシステムとの取り決め |
| T3 | 追加の DB を使っているのは**このシステムだけ**か | 追加の DB のスキーマを変えられるか |
| T4 | 利用者は誰か（テナントの担当者／社内の運用者）、認証はどうしているか | 統合管理システムとまとめるか、認証の設計 |
| T5 | テナントによってスキーマ名やテーブル構成に違いがあるか | スキーマ名をテナント台帳で持つ必要があるか |
