# ECS Service Connect / VPC Lattice / RDS Proxy の使い所

2026-10-23 時点のまとめ。料金や新しい機能の対応状況は記憶に基づく部分があるので、採用前に AWS の公式ドキュメントで確認すること。

## 0. 先に結論

3 つは競合する製品ではない。**つなぐ対象と範囲**が違う。

| サービス | つなぐもの | 範囲 | ひとことで |
|---|---|---|---|
| ECS Service Connect | ECS サービス → ECS サービス | 同じ Cloud Map 名前空間の中 | ECS の中だけで閉じたサービスメッシュ |
| VPC Lattice | どの基盤のクライアント → どの基盤のサービス | VPC・アカウントをまたぐ | VPC やアカウントをまたいでサービスを公開する仕組み |
| RDS Proxy | アプリ → RDS / Aurora | 同じ VPC（DB の手前） | DB 接続のプール |

- サービス間の通信が ECS の中で閉じている → **Service Connect**
- VPC やアカウントをまたぐ。または Lambda・EC2・EKS が混在する → **VPC Lattice**
- DB への接続数や接続の張り直しが問題になっている → **RDS Proxy**

## 1. Amazon ECS Service Connect

### 何をするものか

ECS が管理する Envoy プロキシを、各タスクにサイドカーとして自動で入れる。同じ Cloud Map 名前空間にあるサービス同士が、`http://orders:8080` のような短い名前で通信できるようになる。

- クライアント側でロードバランスする。内部 ALB は不要
- リトライ、タイムアウト、外れ値の検出（異常なタスクを外す）をアプリの変更なしで使える
- サービスごとのリクエスト数、レイテンシ、5xx 件数が CloudWatch のメトリクスとして出る
- AWS Private CA を使えば、サービス間の通信を TLS にできる
- 追加料金はない。かかるのは Envoy サイドカーが使う CPU とメモリの分だけ

### 向いているケース

- ECS 上のマイクロサービス同士の内部通信
- サービスごとに内部 ALB を置いていて、そのコストや管理を減らしたい
- App Mesh からの移行先。App Mesh のサポートは 2026-09-30 で終了している
- アプリに手を入れずに、サービス間のメトリクスとリトライがほしい

### 向いていないケース・注意点

- **クライアントも ECS で、Service Connect を有効にしたタスクである必要がある。** Lambda、EC2、オンプレミスからは短い名前で呼べない。
- エンドポイントの一覧は、タスクの起動時にサイドカーへ配られる。Service Connect の設定を変えたら、クライアント側のサービスも再デプロイが要る。
- サイドカーのぶん、タスクの CPU とメモリを少し多めに見積もる。
- 細かい認可（どのサービスがどのサービスを呼んでよいか）の仕組みはない。それが必要なら、セキュリティグループで分けるか VPC Lattice を使う。
- アカウントをまたぐ構成は、名前空間の共有（AWS RAM）で対応されてきているが、制約は公式ドキュメントで確認すること。またぎが前提なら VPC Lattice のほうが素直。

## 2. Amazon VPC Lattice

### 何をするものか

アプリケーション層のネットワークを管理するサービス。「サービス」を「サービスネットワーク」に登録し、そのサービスネットワークを VPC に関連付ける。関連付けた VPC の中のクライアントは、ピアリングや Transit Gateway なしで、そのサービスを呼べる。

- ターゲットには EC2、IP、Lambda、ALB、ECS（ECS サービスとの統合）、EKS（Gateway API Controller 経由）を使える
- VPC の CIDR が重なっていても通信できる
- IAM の認可ポリシー（auth policy）で、呼び出し元のロールごとに許可・拒否を決められる。リクエストには SigV4 署名を付ける
- HTTP、HTTPS、gRPC のルーティング（パス、ヘッダー、重み付け）ができる
- TCP のリソース（RDS など）も、resource configuration と resource gateway で公開できる
- 料金は次の 3 つの合計になる
  - サービスごとの時間課金
  - 処理したデータ量
  - リクエスト数

### 向いているケース

- **マルチアカウントのマイクロサービス**。プラットフォームチームが、各チームのサービスを横断で公開・管理する場合
- ECS、Lambda、EKS、EC2 が混在していて、基盤に関係なく同じ方法で呼びたい
- VPC ピアリング、Transit Gateway、PrivateLink（NLB + エンドポイントサービス）の組み合わせが複雑になってきた
- サービス間をゼロトラストにしたい。ネットワークの到達性ではなく、IAM の ID で認可したい
- CIDR が重なっている VPC 同士をつなぎたい

### 向いていないケース・注意点

- **リクエストが多いサービスでは、リクエスト課金とデータ課金が効いてくる。** 同じ VPC の中で閉じた大量の通信なら、Service Connect や内部 ALB のほうが安いことが多い。
- 経由するホップが 1 つ増えるので、レイテンシが少し増える。
- IAM 認可を使う場合、クライアントは SigV4 で署名する必要がある。AWS SDK を使うか、署名を付ける仕組みを入れる。
- クライアントの VPC は、サービスネットワークに関連付けるか、サービスネットワークのエンドポイントを置く必要がある。
- サービスやターゲットグループの数にはクォータがある。大規模に使うなら事前に確認する。

## 3. Amazon RDS Proxy

### 何をするものか

RDS / Aurora の手前に置く、マネージドの接続プール。MySQL、PostgreSQL、MariaDB、SQL Server に対応している。

- 多数のクライアント接続を、少数の DB 接続にまとめる（多重化）
- フェイルオーバー時、DB のエンドポイントが切り替わっても、クライアント側の接続を保ったまま待つ。そのぶん切り替わりが速く見える
- 認証情報を Secrets Manager で管理できる。クライアントは IAM 認証で接続できる
- Aurora では、読み取り専用のエンドポイントを作れる
- 料金は、DB インスタンスの vCPU 数（Aurora Serverless では ACU）に応じた時間課金

### 向いているケース

- **Lambda から RDS につなぐ**。同時実行が増えると接続数が `max_connections` を超えたり、接続を張る負荷が大きくなったりするので、その対策になる
- 接続を頻繁に開いて閉じるアプリ。PHP や短命なワーカーなど
- フェイルオーバーやメンテナンス時の切断時間を短くしたい
- DB のパスワードをアプリに持たせたくない（IAM 認証と Secrets Manager を使う）

### 向いていないケース・注意点

- **ECS や EC2 で常駐するアプリには不要なことが多い。** アプリ側の接続プール（HikariCP、Go の `database/sql` など）の上限を、タスク数 × 1 タスクあたりの接続数で設計すれば足りる。
- **ピン留め（pinning）**: セッションの状態に依存する操作があると、その接続はクライアント専用になり、多重化が効かなくなる。セッション変数の `SET`、一時テーブル、MySQL のプリペアドステートメントなどが該当する。CloudWatch のピン留めのメトリクスを確認する。
- 1 ホップ増えるぶん、クエリのレイテンシが数 ms 増えることがある。
- 長いトランザクションが多いと、多重化の効果は小さい。
- Proxy は DB と同じ VPC に置く。別の VPC から使う場合は、Proxy のエンドポイントを追加するか、VPC Lattice の TCP リソースとして公開する。
- Blue/Green デプロイ（`rds_mysql_upgrade` でやっているもの）と組み合わせる場合は、切り替え時の Proxy の扱いを公式ドキュメントで確認すること。

## 4. 組み合わせの例

```
[アカウント A: ECS]
  frontend ──Service Connect──> orders ──Service Connect──> inventory
                                  │
                                  │ VPC Lattice（IAM 認可）
                                  ▼
[アカウント B: 決済チーム]  payments（ECS / Lambda どちらでも）

[アカウント A: Lambda]  batch-jobs ──RDS Proxy──> Aurora MySQL
[アカウント A: ECS]     orders ─────アプリ側の接続プール────> Aurora MySQL
```

- アカウントの中の ECS 同士は Service Connect で安く、細かく制御する。
- アカウントやチームの境界をまたぐ呼び出しは VPC Lattice にして、IAM で認可する。
- DB へは、Lambda からは RDS Proxy を通す。常駐する ECS からは、アプリ側の接続プールで直接つなぐ。

## 5. 選び方

| 状況 | 選ぶもの |
|---|---|
| ECS の中だけで、サービス間の名前解決・LB・メトリクスがほしい | ECS Service Connect |
| App Mesh を使っていた | ECS Service Connect（ECS の場合） |
| アカウントや VPC をまたいでサービスを公開したい | VPC Lattice |
| Lambda・EC2・EKS・ECS が混在している | VPC Lattice |
| サービス間の認可を IAM でやりたい | VPC Lattice |
| 同じ VPC の中で、リクエストが非常に多い | Service Connect または内部 ALB（Lattice はコストを試算してから） |
| Lambda から RDS / Aurora につなぐ | RDS Proxy |
| フェイルオーバー時間を短くしたい / DB の認証情報をアプリに持たせたくない | RDS Proxy |
| 常駐するアプリから DB につなぐ | まずアプリ側の接続プール。足りなければ RDS Proxy |

## 6. 採用前に確認すること

- VPC Lattice の料金（時間・データ量・リクエスト）を、想定するトラフィックで試算する
- Service Connect のアカウントをまたぐ構成のサポート範囲
- RDS Proxy が、使う DB エンジンとバージョンに対応しているか。Blue/Green デプロイとの相性
- 各サービスのクォータ
