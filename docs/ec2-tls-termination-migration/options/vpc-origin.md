# VPC オリジン（オプション）

> 位置付け: **オプション**（今はとらない）。採用した B. CloudFront → EC2 は、CloudFront から稼働サーバーへ公開のオリジン（インターネット経由の HTTPS）で接続する（[README の T14](../README.md#決めたこと)）。ここには、インターネットを通さずに接続する VPC オリジンに移すときの条件と、することを書き出す。手順の全体は [README](../README.md#ステップの流れ)。
>
> 確かめた範囲: VPC オリジンの仕様は AWS のドキュメントと照らし合わせた（2026-11-17）。**定義は書いておらず、AWS でも試していない**。料金は確かめていない。
>
> 作成日: 2026-11-17

## 用語

[README の用語](../README.md#用語)に加えて、次の語を使う。

| 用語 | 指すもの |
|---|---|
| 公開のオリジン | 今の方式。CloudFront が、公開の DNS の名前（EC2 のパブリック DNS 名）で稼働サーバーへインターネット経由で接続する |
| VPC オリジン | CloudFront が、VPC の中に作るネットワークインターフェースを通って、プライベートサブネットの稼働サーバーへ接続する方式 |
| プライベートサブネット | ルートテーブルにインターネットゲートウェイへの経路がないサブネット。そこに置いたインスタンスは、インターネットから直接は届かない |

## 公開のオリジンとの違い

| | 公開のオリジン（採用） | VPC オリジン |
|---|---|---|
| 稼働サーバーの置き場所 | 今のパブリックサブネットのまま（Elastic IP あり） | **プライベートサブネット** |
| CloudFront から稼働サーバーへの経路 | インターネット | VPC の中（CloudFront が作るネットワークインターフェース） |
| オリジンの名前 | EC2 のパブリック DNS 名 | インスタンスのプライベート IP の DNS 名 |
| 稼働サーバーへの直接の接続を止める方法 | セキュリティグループ（CloudFront のプレフィックスリスト）と秘密のヘッダー（[ステップ 4](../step4-origin-restriction.md)） | サブネットがプライベートなので、インターネットから届かない。セキュリティグループで CloudFront のプレフィックスリストか、CloudFront が作るセキュリティグループを許可する |
| Elastic IP を指定している相手 | 届く（ステップ 4 で止まる） | **届かない** |
| 稼働サーバーから外への通信（yum、certbot の申請など） | インターネットゲートウェイで出る | **NAT ゲートウェイなどが要る** |
| 定義 | ある（`step2-cloudfront.yml`、`<prefix>-step2-cloudfront`） | ない（`AWS::CloudFront::VpcOrigin` を足す必要がある） |

## 条件（AWS のドキュメントの記述）

- 使えるのは、プライベートサブネットにある ALB、NLB、EC2 のインスタンス
- VPC にインターネットゲートウェイが要る（インターネットから受けられる VPC であることを示すため。経路には使わない）
- プライベートサブネットに、空きの IPv4 アドレスが 1 つ以上要る（CloudFront がネットワークインターフェースを作る）
- オリジンのリソースにはセキュリティグループを付け、次のどちらかを許可する
  - CloudFront のプレフィックスリスト `com.amazonaws.global.cloudfront.origin-facing`（VPC オリジンを作る前でもよい）
  - VPC オリジンを作ると AWS が作るセキュリティグループ `CloudFront-VPCOrigins-Service-SG`（作った後。自分のディストリビューションだけに絞れる）
- 使えないもの: gRPC、Lambda@Edge のオリジン側のトリガー。ネットワーク ACL の受信の規則は評価されないが、戻りの送信の規則は評価される
- 東京リージョン（`ap-northeast-1`）は対象。ただし AZ `apne1-az3` は除く
- オリジンが EC2 のインスタンスなら、オリジンのドメインにはインスタンスのプライベート IP の DNS 名を入れる
- 既存のディストリビューションに足すときの AWS の手順は、VPC オリジンを作る → ステージングのディストリビューションで試す → 本番の設定に反映する → **最後にサブネットをプライベートにする**（ルートテーブルの関連付けを変える）

## 移すときにすること（下書き）

1. 稼働サーバーの AZ が `apne1-az3` でないことを確かめる
2. Elastic IP を指定している相手を、名前での接続に移してもらう（[README の共通の確認](../README.md#どの手順でも共通して確かめること)）
3. 稼働サーバーから外への通信の経路を用意する（NAT ゲートウェイ、または必要な宛先だけの VPC エンドポイント）。certbot の申請、OS の更新、アプリが呼ぶ外部の API を洗い出す
4. 踏み台サーバーからの運用の経路（SSH・SSM）が、プライベートサブネットでも通ることを確かめる
5. VPC オリジン（`AWS::CloudFront::VpcOrigin`）を定義に足し、CloudFront のオリジンをそれに替える。オリジンのドメインはインスタンスのプライベート IP の DNS 名
6. CloudFront から稼働サーバーへの通信を HTTPS のままにするか、HTTP にするかを決める（HTTP にすると、オリジンの証明書と HTTP-01 の更新をやめられる見込み。確かめていない）
7. 確かめてから、稼働サーバーのサブネットをプライベートにする（同じサブネットのほかのリソースにも効く）

## 今とらない理由

- サブネットをプライベートにすると、Elastic IP を指定している相手がすぐに止まる
- 外への通信に NAT ゲートウェイなどが要り、構成と料金が増える
- まずルーティングを作ることを優先し、直接の接続はステップ 4 のセキュリティグループと秘密のヘッダーで止められる
