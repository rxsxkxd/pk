
AMIの実態   実態: 「ストレージ（EBS）のスナップショット」＋「起動設定のメタデータ」のセット

「AMIの実態は『EBS（ストレージ）のスナップショット』＋『起動設定のメタデータ』である」という前提を踏まえると、**AWS EC2 Image Builder** が裏側でやっていることの仕組みがとてもクリアに理解できます。

EC2 Image Builderが「AMIというスナップショット（型）」を作るまでの流れを、この前提に沿ってわかりやすく分解して説明します。

---

### 🛠️ EC2 Image Builder の裏側の挙動（4ステップ）

Image Builderで設定した「レシピ（こういうアプリを入れてね）」に従って新しいAMIができるまでの実態は、AWSのインフラ上で以下のような「組み立て作業」が行われています。

#### ステップ1：まっさらな「親のスナップショット」からEC2を起動する

* あなたがレシピで指定したベースイメージ（例：Amazon Linux 2023の公式AMI）を選びます。
* そのAMIの実体である「親のEBSスナップショット」から、新しいハードディスク（EBS）を1つ切り出し、それを一時的なビルド用EC2インスタンスに「Cドライブ（ルートボリューム）」としてドッキングして起動します。

#### ステップ2：インスタンスの中で「調理（セットアップ）」をする

* 起動した一時的なEC2に対して、AWS Systems Manager (SSM) 経由でコマンドが流し込まれます。
* レシピ（コンポーネント）に書かれていた「PHPをインストールする」「特定のミドルウェアやセキュリティ設定を追加する」といった作業が、**この一時的なサーバーのハードディスク上で実際に行われます。**

#### ステップ3：【重要】完成したハードディスクを「パシャリ」とスナップショットに撮る

* セットアップが完了したら、一時的なEC2を停止します。
* そのうえで、**アプリや設定が追加されて「熟成された状態」になったハードディスク（EBS）を、そのまま「スナップショット」として保存**します。
* これが、新しく生まれたAMIの「ストレージ（EBS）のスナップショット」部分になります。

#### ステップ4：メタデータを添えて「AMI」として登録する

* ステップ3で撮ったスナップショットに対し、「このイメージはどのCPUアーキテクチャ（x86なのかARMなのか）で動くか」「起動時のデバイス設定はどうするか」といった「起動設定のメタデータ（説明書のようなもの）」をセットします。
* これで、誰でもいつでも同じ環境を復元できる「カスタムAMI」の完成です。最後に、ビルドに使った一時的なEC2や古いディスクは自動で片付け（削除）されます。

---

### 💡 まとめると

EC2 Image Builderの本質は、「一時的にEC2を立ち上げて、ディスク（EBS）をいじり倒して、それをスナップショットとして切り出してAMIというパッケージにする一連の手順を、全部全自動でやってくれるロボット」と言えます。

この「スナップショットの作成とパッケージング」という実態が分かっていると、もしビルドが失敗したときも「あ、一時的なEC2のディスク書き込みでエラーが出たんだな」などとトラブルシューティングがしやすくなります。
