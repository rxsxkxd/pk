# メモ: AMI 作成に EC2 Image Builder を使う案（未採用）

> 位置付け: 選択肢を忘れないための備忘メモ。**現時点では採用しない。** 採用中の方式は [Rails アプリのリリース検証・AMI 化・起動テンプレート更新の自動化](../../ami-build-pipeline.md)（常時起動のリリース用インスタンスで検証し、`ec2 create-image` で AMI を作る方式）。

## 前提

EC2 Image Builder は、**稼働中の既存インスタンスから AMI を作ることはできない**。親イメージ（AMI）から毎回自分でビルド用インスタンスを起動し、コンポーネントを実行して AMI を作る。そのため、現行フローの AMI 作成部分をそのまま Image Builder に置き換えることはできず、組み込むなら次のいずれかになる。

## 案 2: 2 段構成（中間 AMI + Image Builder）

- **流れ**: リリース用インスタンス → `create-image` で中間 AMI → 中間 AMI を親イメージとして Image Builder を実行 → test フェーズ → 配布設定で起動テンプレート更新
- **得られるもの**: 新 AMI から起動したインスタンスでのテスト、Image Builder の後片付け、配布設定による起動テンプレート更新、ライフサイクルポリシーによる古い AMI の整理
- **代償・課題**:
  - AMI を 2 回作るため、時間とスナップショット費用が増える。中間 AMI の削除が必要
  - レシピは不変で親イメージも固定されるため、リリースごとに新しいレシピバージョンを API で作るか、親イメージを SSM パラメータで参照する必要がある（後者は対応状況を要確認）
  - test フェーズのインスタンスには UserData が渡らないため、本番設定なしでアプリが起動しない可能性がある。テスト内容を絞るか、test フェーズ内で検証用設定を取得する
  - リリース用インスタンスで `create-image` する点は変わらず、再起動は発生する
  - インスタンスの使い回しによる状態の蓄積という根本の問題は残る

## 案 3: 処理を Image Builder に全面移行

- **流れ**: チェックアウト・`bundle install`・RSpec・起動確認を Image Builder のコンポーネント（build / validate / test フェーズ）で行い、AMI 作成・テスト・起動テンプレート更新まで Image Builder で完結させる
- **得られるもの**: Image Builder の利点すべて、AMI の再現性（毎回まっさらなインスタンスから作る）
- **代償・課題**:
  - **常時起動のリリース用インスタンスを使い回す前提を捨てる**ことになる
  - 毎回 `bundle install` から行うため遅い
  - Image Builder 固有の概念（コンポーネント定義、レシピの不変性、パラメータを渡せないパイプライン実行など）の学習が必要

## 再検討のきっかけ

- 使い回しによる状態の蓄積で、AMI の再現性が問題になってきた → 案 3
- 「AMI から起動して動くか」の検証や古い AMI の整理を自作で賄いきれなくなった → 案 3（案 2 は案 1 と案 3 のどちらよりも複雑になるため優先度は低い）
