# 設計: 国内だけに絞る設定（iptables ＋ ipset）を複数台に入れるスクリプト

> 位置付け: [作業計画: OS（iptables ＋ ipset）で特定のポートを国内だけに絞る](./access-restriction-os-firewall-work-plan.md) を、台数が多いため手作業ではなくスクリプトで行うための**設計**。実装はまだしていない。サーバーに入れる設定・スクリプト・ユニットの中身は [暫定対応: OS（iptables ＋ ipset、または firewalld）](./access-restriction-os-firewall.md) のものを使う。
>
> 作成日: 2026-10-28

## 結論

| # | 結論 |
|---|---|
| 1 | **できる**。作業者の PC で動く 1 つの道具（以下「展開の道具」）が、AWS の API（EC2・IAM・SSM）と **SSM の Run Command** で各インスタンスを操作する。SSH を使うのは、SSM Agent を確かめて入れる「SSM の準備」の段階だけ |
| 2 | 作業を **3 つのチェックポイント**で区切る。各チェックポイントの終わりで止まり、全台の結果の報告を出す。作業者が報告を見てから、次のチェックポイントを実行する |
| 3 | 進み具合は**インスタンスごとの状態のファイル**に残す。途中で失敗しても、同じコマンドをもう一度実行すれば、済んだところを飛ばして続きから進む |
| 4 | 遮断を効かせる最後のチェックポイントでは、**「10 分後に自動で元に戻る」予約を入れてから有効にし、確認に合格したインスタンスだけ予約を取り消して確定する**。不合格や応答なしのインスタンスは、自動で元に戻る |
| 5 | チェックポイント 2 以降は SSM の Run Command で操作する。その前に **「SSM の準備」の段階**で、全台の SSM Agent を確かめ、入っていない・止まっているインスタンスには、作業者の確認を得てから SSH でインストールと有効化を行う（決めること C2） |

## 全体の構成

```
作業者の PC
  └ 展開の道具
       ├ EC2 の API … インスタンスの情報の記録、AMI の作成
       ├ IAM の API … Session Manager（SSM）の権限の用意
       ├ SSM の API … Run Command で各インスタンスにシェルの処理を送る、登録の状態を見る
       │     ├ 対象のインスタンス（AL2）… 確認、パッケージの導入、ファイルの配置、有効化
       │     └ 海外の確認の拠点（別のリージョンの EC2）… 海外からつながらないことの確認
       ├ SSH … 「SSM の準備」の段階だけ。SSM Agent の確認とインストール・有効化
       └ 作業者の PC から直接 … 日本の回線から対象のポートにつながることの確認
```

| 要素 | 内容 |
|---|---|
| 展開の道具 | 作業者の PC で動く。対象の一覧と共通の設定を読み、チェックポイントごとに全台を処理する |
| 遠隔の実行 | SSM の Run Command（`AWS-RunShellScript`）。インスタンスに置くファイル（設定、スクリプト、ユニット）の中身は、送るシェルの処理の中に埋め込む。SSM がまだ使えない「SSM の準備」の段階だけは SSH |
| 海外の確認の拠点 | 海外のリージョンに置いた小さな EC2。SSM で操作できるようにしておき、展開の道具が Run Command で `nc` を実行させて、対象のポートにつながらないことを確かめる |
| 状態のファイル | 実行ごとのフォルダに、インスタンスごとの進み具合と結果（AMI の ID、確認の結果、集合の件数など）を残す |

## チェックポイント

### チェックポイント 1: バックアップまで

インスタンスのディスクには何も変更を加えない。

| # | 処理 | 内容 | 失敗したとき |
|---|---|---|---|
| 1-1 | 対象の確認 | 一覧のインスタンスが存在し、動いていることを確かめる | そのインスタンスを「失敗」にして進めない |
| 1-2 | インスタンスの外の設定の記録 | セキュリティグループ、インスタンスプロファイル、パブリック IP、タグを状態のファイルに残す | 同上 |
| 1-3 | SSM の登録の確認（読み取り） | `describe-instance-information` で登録されているか（`Online` か）を記録する。まだ何も変えない（詳しい確認と直す作業は、次の「SSM の準備」で行う） | 記録だけ |
| 1-4 | 書き込みの反映 | **1-3 で `Online` のときだけ**、Run Command で `sync` を実行する。登録されていなければ省く（AMI は電源を急に切ったときと同じ状態になるが、設定ファイルを残す用途なら足りる） | 記録だけ（AMI は作る） |
| 1-5 | AMI | `create-image --no-reboot`。名前とタグに、実行の ID とインスタンスの名前を入れる。**完了は待たない**（取り始めた時点の中身が残る） | そのインスタンスを「失敗」 |

**報告**: インスタンスごとに、AMI の ID、SSM の登録の状態、記録した設定。

### SSM の準備（チェックポイント 1 と 2 の間）

チェックポイント 2 以降は Run Command で操作するので、その前に**全台で SSM を使える状態にそろえる**。SSM Agent が動いていないインスタンスには Run Command が使えないため、この段階だけは**今の入り方（SSH）**でインスタンスに入る。SSM Agent のインストールはディスクへの変更なので、チェックポイント 1（バックアップ）の後に行う。

流れ:

1. **全台の確認**（変更なし）
2. **一覧の表示と、インストールの可否の確認**（チェックポイント。作業者が「進める」と答えたときだけ次へ）
3. **インストールと有効化**（対象のインスタンスだけ）
4. **動作の確認**

#### 1. 全台の確認

AWS の API と SSH の両方で見て、インスタンスごとに状態を分ける。

| 見るもの | 手段 | 内容 |
|---|---|---|
| 登録の状態 | AWS の API（`describe-instance-information`） | `Online` / `ConnectionLost` / 一覧にない |
| 権限 | AWS の API（インスタンスプロファイルの関連付け、ロールに付いているポリシー） | インスタンスプロファイルがあるか、ロールに `AmazonSSMManagedInstanceCore` があるか |
| SSM Agent | SSH（`rpm -q amazon-ssm-agent`、`systemctl is-enabled` / `is-active amazon-ssm-agent`） | 入っているか、起動時に有効か、今動いているか |
| AWS の窓口への接続 | SSH（`ssm-cli get-diagnostics` があれば。なければエージェントのログの誤り） | 送信の 443 番、DNS、インスタンスのメタデータに届くか |

| 分類 | 状態 | この段階での扱い |
|---|---|---|
| A. 使える | `Online` | 何もしない |
| B. 入っていない | SSM Agent のパッケージがない | **インストールの対象** |
| C. 止まっている | 入っているが、動いていない・起動時に有効でない | **有効化の対象**（`systemctl enable --now`） |
| D. 権限がない | 動いているが、インスタンスプロファイルがない・ロールに権限がない | **権限の付与の対象**（決めること C3）。インスタンスプロファイルがなければ道具が付け、付いているロールに権限が足りなければ道具がロールに足す |
| E. 届かない | 動いていて権限もあるが、AWS の窓口に届かない | 「手作業が要る」（ネットワークの見直し） |
| F. SSH で入れない | SSH の接続に失敗する | 「手作業が要る」 |

#### 2. 一覧の表示と、インストールの可否の確認（チェックポイント）

分類ごとの台数と、B・C・D のインスタンスの一覧（名前、インスタンスの ID、行う処理）を表示し、作業者の確認を求める。D のうちロールに権限を足すものは、**そのロールを使っているほかのインスタンス（対象の一覧にないものを含む）も一緒に表示する**（ロールは共有されていることがあり、足した権限はそれらにも及ぶため）。作業者が「進める」と答えたときだけ、3 に進む。答えなければ、確認の結果を状態のファイルに残して終わる（後で同じ確認からやり直せる）。

#### 3. インストールと有効化

| 分類 | 処理（SSH で実行） |
|---|---|
| B | `sudo yum install -y amazon-ssm-agent` → `sudo systemctl enable --now amazon-ssm-agent` |
| C | `sudo systemctl enable --now amazon-ssm-agent` |
| D（インスタンスプロファイルがないもの） | AWS の API で、用意したインスタンスプロファイルを付ける（再起動は不要）。付けた後に `sudo systemctl restart amazon-ssm-agent` で登録を早める |
| D（付いているロールに権限が足りないもの） | AWS の API で、そのロールに `AmazonSSMManagedInstanceCore` を足す（`iam:AttachRolePolicy`）。足したこと（ロールの名前）を状態のファイルに残し、元に戻すときに外せるようにする。足した後に `sudo systemctl restart amazon-ssm-agent` |

複数台を並べて処理するが、同時に処理する台数には上限を設ける。

#### 4. 動作の確認

| 確認 | 手段 | 合格の条件 |
|---|---|---|
| エージェントの状態 | SSH（`systemctl is-enabled` / `is-active`） | 起動時に有効で、今動いている |
| 登録 | AWS の API（`describe-instance-information`） | 上限の時間内に `Online` になる |
| Run Command | AWS の API（`echo ok` を送る） | 成功する |
| Session Manager の経路 | SSH（`ssm-cli get-diagnostics` があれば） | `ssmmessages` の窓口に届く（Run Command と Session Manager は使う窓口が一部違うため。シェルで入れることは、少なくとも 1 台で `aws ssm start-session` を手で試す） |

合格したインスタンスは分類 A になり、チェックポイント 2 に進める。不合格のインスタンスは「手作業が要る」として報告する。

#### SSH での接続

| 項目 | 内容 |
|---|---|
| 接続のしかた | 道具は作業者の PC の `ssh` のコマンドを呼ぶ。作業者の SSH の設定（鍵、踏み台、ユーザー名）をそのまま使える |
| 入力 | インスタンスごとの接続先（ホスト名か IP）とユーザー名（例: `centos`）。共通の値と、インスタンスごとの上書き |
| 実行のしかた | 確認の処理を送って、結果を決まった形（キーと値）で受け取る。`BatchMode=yes` で、パスワードの入力待ちなどで止まらないようにする |
| 権限 | インストールと有効化に `sudo` が要る（パスワードなしで使えること） |

### チェックポイント 2: 制限の設定の前まで

遮断はまだ効かせない。チェックポイント 2 の終わりの状態は、「集合はできているが、どのルールからも参照されていない」。

| # | 処理 | 内容 | 失敗したとき |
|---|---|---|---|
| 2-1 | 前の段階の確認 | チェックポイント 1 が成功していること。**AMI が `available` になっていること**（なっていなければ待つか、そのインスタンスは後回し） | 後回し |
| 2-2 | SSM の確認 | 「SSM の準備」で分類 A（使える）になっていること。念のため `Online` であることをもう一度見る | 「手作業が要る」 |
| 2-4 | 今の状態の確認 | Run Command で「事前の確認」のスクリプトを実行し、結果を残す。**firewalld が動いている・iptables にルールがある・ipset の集合がある・起動時に有効なものがある、のどれかなら止める**（そのインスタンスは「要確認」） | 「要確認」 |
| 2-5 | パッケージ | `yum install -y ipset python3`。入れた直後に `systemctl is-enabled` で、起動時に有効になったものがないかを見る | 「失敗」 |
| 2-6 | ファイルの配置 | 設定（ポート）、許可する IP（共通の一覧＋インスタンスごとの追加）、2 つのスクリプト、systemd のユニット（`daemon-reload` まで。enable しない） | 「失敗」 |
| 2-7 | 日本の IP の範囲 | 更新のスクリプトを 1 回実行する（集合も作られる） | 「失敗」 |
| 2-8 | 中身の確認 | 集合の件数、確認用の IP（日本の回線の IP、許可する相手の IP）が集合に入っていること、**海外の確認の拠点の IP が入っていないこと**（拠点があれば）、`PORT_GUARD` のルールがまだないこと | 「失敗」 |

**報告**: インスタンスごとに、確認の結果（既存のファイアウォールの有無）、集合の件数、2-8 の判定。

### チェックポイント 3: 制限の有効化と確認

一度に全台を有効にせず、**最初は 1 台（カナリア）、その後は決めた台数ずつ**進める。決めた数を超えて失敗したら、残りは進めずに止まる。

| # | 処理 | 内容 |
|---|---|---|
| 3-1 | 前の段階の確認 | チェックポイント 2 が成功していること |
| 3-2 | 控え | `iptables-save` の結果をインスタンスの中に保存する |
| 3-3 | 自動で元に戻る予約 | `systemd-run --unit port-guard-auto-revert --on-active=10min` で、10 分後に遮断のルールを消す予約を入れる |
| 3-4 | 有効化 | `systemctl enable --now port-guard` |
| 3-5 | 確認 | 下の表の確認をすべて行う |
| 3-6 | 確定 | **すべて合格したときだけ**、予約を取り消し（`systemctl stop port-guard-auto-revert.timer`）、cron を置く |
| 3-7 | 不合格のとき | すぐにルールを消して元に戻す（予約の時間を待たない）。そのインスタンスは「失敗」 |
| 3-8 | 応答がないとき | 何もしない。10 分後に予約が動いて元に戻る。戻った後に SSM で入れるかを確かめ、報告に出す |

3-5 の確認:

| 確認 | どこから | 合格の条件 |
|---|---|---|
| SSM で操作できる | 展開の道具（Run Command） | コマンドが成功する（遮断で SSM まで止まっていない） |
| 日本からつながる | 作業者の PC（日本の回線） | 対象のポートに接続できる |
| 海外からつながらない | 海外の確認の拠点（Run Command で `nc`）。**拠点がない場合は、この確認を飛ばし、報告に「手作業で確認」と出す**（C4） | 対象のポートに接続できない（タイムアウト） |
| 対象外のポート | 作業者の PC | 決めたポート（例: 443 のウェブ）に今までどおりつながる |
| ルールが入っている | 展開の道具（Run Command） | `PORT_GUARD` のルールと、INPUT からの参照がある |

**報告**: インスタンスごとに、確定・自動で戻った・失敗、と各確認の結果。

### （任意）チェックポイント 4: 再起動しても戻るか

保守の時間帯に、決めたインスタンスだけを対象にする。再起動して `Online` に戻るのを待ち、ルール・集合・`port-guard` と SSM Agent の状態を見て、3-5 の確認をもう一度行う。再起動を伴うので、ほかのチェックポイントとは別のコマンドにして、明示したときだけ動かす。

## 状態の管理

| 項目 | 内容 |
|---|---|
| 実行の単位 | 実行ごとに ID を決め、フォルダ（例: `runs/<実行の ID>/`）を作る。対象の一覧と設定の写しもそこに残す |
| インスタンスごとの状態 | チェックポイントと処理ごとの結果（未着手・成功・失敗・手作業が要る・要確認）、記録した値（AMI の ID、元のインスタンスプロファイル、集合の件数など）、Run Command のコマンドの ID |
| 再実行 | 同じチェックポイントをもう一度実行すると、成功したインスタンスと処理は飛ばし、それ以外だけをやり直す。各処理は、何度実行しても同じ結果になるように作る（サーバーに入れるスクリプトは、すでにそうなっている） |
| 個別の指定 | 特定のインスタンスだけを対象にする指定（例: 「要確認」を手で直した後に、そのインスタンスだけ進める） |
| インスタンスのタグ（任意） | 進み具合をインスタンスのタグ（例: `PortGuardStage=checkpoint-2`）にも書けば、コンソールから全体を見渡せる |
| ログ | 処理ごとの標準出力と標準エラー。Run Command の出力は、長いと途中で切られるので、必要なら S3 のバケットに出力させる |

## 入力

| 入力 | 内容 |
|---|---|
| 対象の一覧 | インスタンスの ID、名前、リージョン、SSH の接続先とユーザー名（共通の値と違う場合）、絞るポート（既定と違う場合）、そのインスタンスだけの許可する IP |
| 共通の設定 | 絞るポートの既定、共通の許可する IP、日本の IP の範囲の最低件数、海外の確認の拠点（インスタンスの ID とリージョン）、日本の回線の IP（作業者の PC の IP）、対象外の確認に使うポート、カナリアの台数・1 回の台数・止める失敗の数、自動で戻るまでの時間 |
| サーバーに入れる中身 | 設定・2 つのスクリプト・ユニット・cron の雛形（[暫定対応のドキュメント](./access-restriction-os-firewall.md) と同じもの）。道具に埋め込む |

## 道具の使い方（案）

```bash
port-guard-rollout plan        --run <実行の ID> --targets targets.yml --config config.yml   # 何をするかを表示するだけ
port-guard-rollout checkpoint1 --run <実行の ID>      # バックアップまで
port-guard-rollout ssm-prepare --run <実行の ID>      # SSM の準備（全台の確認 → 一覧の表示と確認 → インストールと有効化 → 動作の確認）
port-guard-rollout checkpoint2 --run <実行の ID>      # 制限の設定の前まで
port-guard-rollout checkpoint3 --run <実行の ID>      # 制限の有効化と確認（カナリア → 決めた台数ずつ）
port-guard-rollout checkpoint4 --run <実行の ID> --instances i-aaa,i-bbb   # 再起動の確認（任意）
port-guard-rollout status      --run <実行の ID>      # 全台の進み具合
port-guard-rollout revert      --run <実行の ID> --instances i-aaa         # ルールを外す（仕組みは残す）
```

各チェックポイントは、実行の前に対象と処理の一覧を表示し、作業者の確認を求める。

## 権限

作業者の IAM に要るもの:

| 対象 | 操作 |
|---|---|
| EC2 | インスタンスの情報（`ec2:DescribeInstances` など）、AMI の作成と情報（`ec2:CreateImage`、`ec2:DescribeImages`、`ec2:CreateTags`）、インスタンスプロファイルの関連付け（`ec2:AssociateIamInstanceProfile`、`ec2:DescribeIamInstanceProfileAssociations`） |
| IAM | インスタンスプロファイルとロールの情報、関連付けのための `iam:PassRole`（用意したロールだけ）、ロールへの権限の追加（`iam:AttachRolePolicy`。条件で `AmazonSSMManagedInstanceCore` だけに絞る） |
| SSM | `ssm:DescribeInstanceInformation`、`ssm:SendCommand`（`AWS-RunShellScript` を、対象のインスタンスと確認の拠点だけに）、`ssm:GetCommandInvocation`、`ssm:ListCommandInvocations` |

`AWS-RunShellScript` はインスタンスの上で root として何でも実行できる強い権限なので、対象を絞り、作業の期間だけ与える。

## 安全のための作り

| 作り | 内容 |
|---|---|
| チェックポイントで止まる | 1 回の実行で、次のチェックポイントまで勝手に進まない。「SSM の準備」も、インストールの前に一覧を表示して確認を求める |
| 表示だけの実行 | `plan` で、何をするかを変更なしで確かめられる |
| 段階的な有効化 | カナリア → 決めた台数ずつ。失敗が決めた数を超えたら止まる |
| 自動で元に戻る | 有効化の前に予約を入れ、確認に合格したときだけ取り消す。道具が途中で止まっても、予約が元に戻す |
| 一覧にないものに触らない | 対象の一覧にあるインスタンスだけを操作する。セキュリティグループは変えない |
| ロールへの追加は見せてから | すでに付いているロールに権限を足すときは、「SSM の準備」の確認の画面で、そのロールを使うほかのインスタンスも表示してから行う。足すのは `AmazonSSMManagedInstanceCore` だけで、ほかの権限には触らない。足したロールは記録し、元に戻せるようにする |
| 既存のファイアウォールを壊さない | 2-4 で既存の仕組みが見つかったインスタンスは止める |

## 実装の言語（決定: Go）

| 案 | 利点 | 欠点 |
|---|---|---|
| **Go**（AWS SDK for Go） | このリポジトリの方針（作業者の PC で動く道具は Go。決定事項 D10）に合う。状態の管理、並列の処理、待ち合わせ、表の報告を書きやすい。サーバーに入れる中身を `go:embed` で埋め込める | 書く量が多い |
| Bash（AWS CLI と jq） | 早く書ける | 状態の管理、並列、失敗の扱いが複雑になり、台数が増えると保守しにくい |

**勧め: Go**。サーバーの上で動く部分（設定・スクリプト・ユニット）は、もともとシェルなので、そのまま埋め込む。

## 決めること

| # | 論点 | 選択肢・勧め |
|---|---|---|
| C1 | 遠隔の実行の手段 | **決定**: 「SSM の準備」の段階だけ SSH、チェックポイント 2 以降は SSM の Run Command |
| C2 | SSM Agent が動いていないインスタンス | **決定**: 「SSM の準備」の段階で全台を確かめ、入っていない・止まっているインスタンスの一覧を表示して作業者の確認を得てから、SSH でインストールと有効化を行い、動作を確かめる |
| C3 | インスタンスプロファイル | **方針を決定**: なければ用意したものを付け、付いているロールに権限が足りなければ**道具が足す**。実環境でないと試せないので、試すのは保留 |
| C4 | 海外の確認の拠点 | **保留**（用意できるかは相手の環境しだい）。案は、海外のリージョンに小さな EC2 を 1 台（SSM で操作できるようにする）。用意できない場合は、チェックポイント 3 の「海外からつながらない」の確認を手作業にする（チェックポイント 3 の確認の表） |
| C5 | 段階の大きさ | カナリアの台数、1 回の台数、止める失敗の数 |
| C6 | 自動で元に戻るまでの時間 | 10 分（確認にかかる時間を見て決める） |
| C7 | 絞るポートと許可する IP | 共通の値と、インスタンスごとの追加 |
| C8 | 実装の言語と置き場所 | **決定**: Go。置き場所は新しいフォルダ [`port-guard-rollout/`](../../port-guard-rollout/README.md)（1 つの Go のモジュール） |
| C9 | チェックポイント 4（再起動）を行うか | 行う台、行う時期 |

## 未確認の点

| # | 点 |
|---|---|
| 1 | 対象のインスタンスで SSM Agent がどのくらい入っていて動いているか（「SSM の準備」の全台の確認で分かる）。今のインスタンスは SSH で直接入っていて、**SSM Agent は入っていない見込み**なので、多くが分類 B（入っていない）になると考えておく |
| 6 | 全台に SSH で入れるか、`sudo` をパスワードなしで使えるか（「SSM の準備」の全台の確認で分かる） |
