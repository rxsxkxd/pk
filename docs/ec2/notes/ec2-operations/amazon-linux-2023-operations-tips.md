# Amazon Linux 2023 の運用のチップス

> 位置付け: Amazon Linux 2023（以下 AL2023）を運用するときに、誤解しやすい点と知っておくと役に立つ点をまとめた備忘録。特にセキュリティ更新の扱いを中心にする。
>
> 関連: [土台の構成](../../initial-image-build/base-image-composition.md)（この構成での方針）、[更新のサイクル](../../initial-image-build/update-cycles.md)（いつ・何が・どの層を更新するかの図）、[配った AMI から起動したインスタンスの運用中のメンテナンス](../instance-provisioning/distributed-instance-maintenance.md)
>
> 調査日: 2026-10-27（AWS の文書の内容は変わることがあるため、使う前に出典で確認する。「未確認」と書いた点は、実機か AWS の文書で確かめてから使う）

## セキュリティ更新

### 1. 自動では何も更新されない（カーネルを含めて）

AL2023 は、OS の更新を自動では行わない。起動時にも、追加のセキュリティ更新は自動では入らない。

**カーネルを含めて、すべてのセキュリティ更新は、誰か（人、スクリプト、AWS のサービス）が実行しない限り入らない。** 「AL2023 は無停止で自動で OS が更新される」という話は正確ではない（無停止で当てられるのは、カーネルのライブパッチだけ。下の 3）。

### 2. リポジトリは版で固定され、セキュリティの修正は「新しい版」として出る

- インスタンスが使うパッケージのリポジトリは、起動した AMI の AL2023 のリリース（例: `2023.x.YYYYMMDD`）で固定されている
- セキュリティの修正は、**新しいリリース（版）**として出る。AWS はそのたびに新しい AMI も出す
- そのため、**ただ `dnf upgrade --security` を実行しても、固定された版の中の更新しか入らない**。その場で新しい修正を入れるには、上げる先の版を明示する

```bash
sudo dnf check-release-update                 # 新しい版があるかを確認する
sudo dnf upgrade --releasever=<上げる先の版>    # 版を上げて更新する（確認の後に実行される）
```

- 版を上げると、以降の `dnf` はその版を使う
- 版が固定されていることで、「同じ AMI から起動したインスタンスは、同じパッケージになる」（更新の結果が予測できる）という利点がある

### 3. カーネルのライブパッチは「無停止」だが「自動」ではない

Kernel Live Patching で、動いているカーネルに再起動なしでセキュリティの修正を当てられる。ただし、次の条件と制約がある。

| 項目 | 内容 |
|---|---|
| 既定 | **無効**。`kpatch-dnf` を入れて `dnf kernel-livepatch -y auto` で有効にし、`kpatch-runtime` と `kpatch` のサービスを入れて動かす |
| 適用 | **自動では当たらない**。`dnf upgrade --security`（または個別の `dnf install`）で当てる |
| 対象 | **カーネルだけ** |
| 範囲 | ベストエフォート。すべての CVE がライブパッチで出るわけではなく、通常のカーネルの更新と再起動でしか直せないものもある |
| 期間 | 1 つのカーネルの版に出るのは、リリースから 3 か月まで。その後もライブパッチを受けるには、新しいカーネルに上げて再起動する |
| 制約 | 適用中は、ハイバネーションや eBPF などの一部のデバッグツールが使えない |

ライブパッチは、再起動できるまでの**つなぎ**である。OS の更新の代わりにはならない。

### 4. 更新を実行する仕組みは、手書きのスクリプトでなくてよい

| 手段 | 内容 | 注意 |
|---|---|---|
| Systems Manager Patch Manager | パッチの基準（どの重要度の更新を当てるか）とメンテナンスウィンドウ（いつ当てるか）を決めて、複数のインスタンスに定期的に当てる。準拠状況の報告もできる | AL2023 の版の固定をどう扱うか（版を上げるのか、固定された版の中だけか）は**未確認**。使う前に確かめる |
| Systems Manager の定期実行（State Manager など） | `dnf` のコマンド（版を上げる手順を含む）を決まった時刻に実行する | 実行するコマンドは自分で決める |
| `dnf-automatic` | インスタンスの中で定期的に更新する仕組み | AL2023 で使えるか、版の固定とどう関わるかは**未確認** |
| 手書きのスクリプト | 上の手順をスクリプトにする | 実行の記録と失敗の検知を自分で作る必要がある |

### 5. 更新しても、再起動しないと効かないものがある

| 更新したもの | 効かせるには |
|---|---|
| カーネル（通常の更新） | OS の再起動 |
| OpenSSL、glibc などのライブラリ | そのライブラリを使っているサービスの再起動（多くの場合、OS の再起動が確実） |
| サービス自身のパッケージ（Web サーバーなど） | そのサービスの再起動 |

「その場で更新」でも、無停止になるとは限らない。どのサービスの再起動が必要かを調べる手段（`dnf needs-restarting` など）が AL2023 で使えるかは**未確認**。

### 6. OS の更新では、アプリのミドルウェアは更新されない

| もの | 更新のしかた |
|---|---|
| rbenv / ruby-build で入れた Ruby | Ruby のバージョンを上げて入れ直す（この構成では土台の作り直し） |
| gem（Rails を含む） | アプリの依存を上げてリリースする |
| Go の実行ファイル | ビルド環境の Go や依存を上げて、実行ファイルを作り直す。**Go は暗号処理を実行ファイルに取り込むため、OS の OpenSSL を更新しても効かない** |
| AL2023 のパッケージで入れたもの（`ruby3.4` など） | OS の更新で更新される |

### 7. 「その場で更新」と「入れ替え」は別の道筋

| 道筋 | 内容 | 向いている場面 |
|---|---|---|
| **入れ替え**（この構成の本来の道筋） | 新しい AL2023 の AMI を親に土台を作り直し、リリース用インスタンスを入れ替え、AMI を作り、配ったインスタンスを入れ替える。自動化するのは `dnf` ではなく、この入れ替えの流れ（土台の作り直しは EC2 Image Builder のスケジュール実行で定期化できる） | 通常の更新 |
| **その場で更新**（Patch Manager など） | 動いているインスタンスで版を上げて更新する | 緊急時、入れ替えが難しいインスタンス |

その場で更新すると、配った AMI とインスタンスの中身がずれる。その場で直したら、同じ内容が次の土台に入るようにしておく。

## そのほかのチップス

| チップス | 内容 |
|---|---|
| 最新の AMI の ID は SSM のパラメーターで取れる | AWS が公開している SSM のパラメーター（例: `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64`）で、最新の AL2023 の AMI の ID を取得できる。EC2 Image Builder の親イメージや、CloudFormation の指定に使える |
| SSM Agent と AWS CLI v2 は最初から入っている | Session Manager での接続や Run Command がすぐ使える。AWS CLI v2 は Python を同梱しているので、OS の Python に依存しない |
| 既定のユーザーは `ec2-user` | CentOS 系の `centos` ユーザーはない |
| cron は入っていない | `cronie` が既定で入っていない。AWS は systemd のタイマーへの移行を勧めている。cron を使うなら `cronie` を入れる |
| SELinux は有効で、モードは permissive | 拒否は記録されるが、止めはしない |
| EPEL は使えない | EPEL にしかないパッケージは、別の入れ方を探す（例: certbot は pip で入れる） |
| サポートの期間 | 標準サポートは 2027-06-30 まで（3 か月ごとのマイナーリリース）。その後のメンテナンスの期間（セキュリティと重大なバグの修正だけ）は 2029-06-30 まで。それまでに次の OS へ移行する |

## 補足: 無停止の更新は OS ではなく、台数と入れ替えで作る

### 方針

| # | 方針 |
|---|---|
| 1 | **どの OS でも、更新は停止（再起動・入れ替え）を前提に設計する**。AL2023 も例外ではない（ライブパッチで無停止にできるのはカーネルだけで、ベストエフォート・3 か月の期限付き。OpenSSL や glibc などはサービスや OS の再起動が要り、カーネルもいずれは再起動が要る） |
| 2 | **サービスとしての無停止は、台数とインスタンスの入れ替え（ローリング、ブルーグリーン）で実現する** |
| 3 | AL2023 のカーネルのライブパッチは、入れ替えまでの間にカーネルの緊急の脆弱性をしのぐ、**追加費用なしの保険**として扱う |

この方針なら、OS ごとのライブパッチの事情（有償かどうか、対応するカーネル）は設計に影響しない。

### ほかのディストリビューション（参考）

ほかのディストリビューションにもカーネルのライブパッチはあるが、多くは有償のサブスクリプションの機能である（例: Ubuntu は Ubuntu Pro の Canonical Livepatch、RHEL はサブスクリプションの kpatch。Debian などは配布元の無償の仕組みがなく、第三者の有償サービスになる）。どれも「カーネルだけ」「いずれは再起動が要る」点は AL2023 と同じで、方針 1〜3 はそのまま当てはまる。

### 無停止の入れ替えの手段は、配布先の構成で決まる

| 構成 | 無停止の更新の手段 | 必要になること |
|---|---|---|
| ロードバランサー＋複数台（Auto Scaling グループ） | ローリングアップデート（起動テンプレートの新しいバージョンへのインスタンスの更新） | ALB の導入。証明書は ACM になり、Let's Encrypt と 1 台ごとの Elastic IP は不要になる。アプリを複数台で動かせること（セッション、アップロードしたファイル、定期実行の重複など） |
| 単体のサーバー（今の運用） | ブルーグリーン（新しいインスタンスを並べて DNS を切り替える。[候補の文書](../../instance-provisioning/blue-green-switching-candidate.md)）、または短い停止を受け入れる | 切り替えの手順。Auto Scaling グループを 1 台で使っても、入れ替えの間は止まる |

どちらにするかは更新の方式というより、**配布先の構成（単体か複数台か）の選択**であり、[設計: フェーズ 2](../../instance-provisioning/design.md) の論点 P7 で扱う。起動テンプレートは、後から Auto Scaling グループで使える形にしてある（[メモ](../instance-provisioning/launch-template-auto-scaling-readiness-memo.md)）。

参考: [Ubuntu Pro on AWS](https://documentation.ubuntu.com/aws/aws-reference/pro/)、[Kernel Live Patching on AL2023](https://docs.aws.amazon.com/linux/al2023/ug/live-patching.html)

## まとめ

- カーネルを含めて、**セキュリティ更新は何らかの形で実行する仕組みが必要**（自動では入らない）
- AL2023 では修正が新しい版として出るので、その場で更新するなら**版を上げる**手順になる
- ライブパッチは**カーネルだけの、無停止のつなぎ**。自動ではなく、3 か月の期限がある
- この構成では、仕組み化するのは**土台の作り直しと入れ替えの流れ**。その場での更新（Patch Manager など）は、緊急時や入れ替えが難しいインスタンス向けの補助
- どの OS でも更新は停止前提で設計し、**サービスとしての無停止は台数と入れ替え（ローリング、ブルーグリーン）で作る**。ライブパッチは保険
