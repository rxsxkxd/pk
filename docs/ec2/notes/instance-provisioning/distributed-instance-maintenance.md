# 補足: 配った AMI から起動したインスタンスの運用中のメンテナンス

> 位置付け: 検討の整理。採用済みの設計ではない。配った AMI から起動したインスタンス（本番など）を運用し始めた後に、どのようなメンテナンスが必要になるかをまとめる。決まったことは [設計: フェーズ 2](../../instance-provisioning/design.md) や、土台の設計（[作業計画](../../initial-image-build/work-plan.md)の W1・W3）に反映する。
>
> 前提: OS は Amazon Linux 2023（[土台の構成](../../initial-image-build/base-image-composition.md)）。更新の流れは [更新のサイクル](../../initial-image-build/update-cycles.md)（C1〜C4）

## 結論

- 配った AMI から起動したインスタンスは、起動した時点から AMI と別々に古くなっていく。AL2023 は自動では更新されないため、**何もしなければ配った時点の OS のまま動き続ける**
- 必要なメンテナンスは、最初に「配ったインスタンスを**入れ替える**か、**その場で更新する**か」を決めると大きく変わる。今の設計は入れ替えを前提にしている
- 優先度が高いのは、**セキュリティの更新（入れ替えのサイクルを回し続ける）、証明書の更新と監視、ディスク（ログ）の監視**
- 多くは、**土台に最初から入れておけば、配ったインスタンスで個別に手当てしなくて済む**（CloudWatch エージェント、logrotate、ログの送信、Session Manager）

## まず決めること: 入れ替えるか、その場で更新するか

| 方針 | 内容 | 合う場合 | 弱点 |
|---|---|---|---|
| **入れ替え**（作り直し） | 更新は新しい AMI から起動し直して行う。インスタンスの中では何も更新しない | インスタンスに大事な状態（データ、手作業の設定）がない | サーバーごとのもの（Elastic IP、DNS、証明書、サーバーごとの値、WebUI への登録など）を、入れ替えのたびに引き継ぐ仕組みが要る |
| **その場で更新** | 動いているインスタンスで `dnf upgrade` やアプリの更新を行う | 台数が少なく、入れ替えが重い | 配った AMI とインスタンスの中身がずれていく（リリース用インスタンスで心配したドリフトが、全台で起きる） |

今の設計（リリースごとに AMI を作って配る。フェーズ 2 は置き換えが基本）は、**入れ替え**を前提にしている。ただし、[今の手作業の手順](../../instance-provisioning/manual-procedure-analysis.md)を見ると、1 台ごとにサブドメイン・Elastic IP・証明書・WebUI の登録を持つ、長く使い続けるサーバーに近い運用である。入れ替えを前提にするなら、それらを引き継ぐ仕組み（フェーズ 2 の設計の論点 P2・P3）が、メンテナンスの負担を左右する。

以下は、入れ替えを基本とした場合に必要なメンテナンスである。

## 1. セキュリティの更新（最重要）

| 対象 | 方法 | 頻度 |
|---|---|---|
| OS（パッケージ、カーネル） | 新しい土台の AMI に入れ替える（更新のサイクルの C3 → C4） | 土台の作り直しに合わせて。例: 月 1 回 |
| カーネルの緊急の脆弱性 | ライブパッチ（有効にしていれば）。入れ替えまでのつなぎ | 随時 |
| Ruby、アプリの依存（gem） | 新しいリリースの AMI に入れ替える | 脆弱性の公開に応じて |
| 状況の把握 | どのインスタンスがどの AMI（アプリの版と土台の版）で動いているかの一覧。Systems Manager の Inventory や Patch Manager の準拠状況の報告も使える | 常時 |

**アプリのリリースがない期間も、OS の更新のためだけの入れ替えが要る**（更新のサイクルの論点 U3）。

セキュリティ更新の実行のしかた（自動では入らないこと、版の固定、その場で更新するときの注意）は [Amazon Linux 2023 の運用のチップス](../ec2-operations/amazon-linux-2023-operations-tips.md)。

## 2. 証明書（Let's Encrypt）

| 項目 | 内容 |
|---|---|
| 自動更新が動いているか | 更新のタイマーの失敗に気付ける仕組み。Let's Encrypt の期限切れ通知メールは廃止されているので、残り日数を自分で監視する |
| 入れ替え時の引き継ぎ | 証明書を S3 などに保存しておき、新しいインスタンスで復元する。入れ替えのたびに新しく発行すると、レート制限に当たる |
| 有効期間の短縮 | 2027 年に 64 日、2028 年に 45 日になる予定。更新の失敗に気付くまでの猶予が短くなる |

詳細は [構築の流れの中で Let's Encrypt の証明書をいつ扱うか](./letsencrypt-certificate-timing.md) と [Let's Encrypt 証明書発行・初期設定の自動化](../ec2-operations/letsencrypt-automation.md)。

## 3. 監視

| 項目 | 内容 |
|---|---|
| インスタンスの状態 | ステータスチェック（失敗したら自動で復旧する設定もできる） |
| ディスク・メモリ | EC2 の標準のメトリクスには含まれない。CloudWatch エージェントを土台に入れて送る |
| アプリの応答 | 外からのヘルスチェック（Route 53 のヘルスチェックや外形監視） |
| ログ | インスタンスの中だけにあると、入れ替えで消える。CloudWatch Logs などに送る |
| AWS の予定のイベント | ハードウェアの都合での停止や再起動の予定（インスタンスのリタイアなど）。通知を受けて、入れ替えか停止・起動で対応する |

## 4. ディスクとデータ

| 項目 | 内容 |
|---|---|
| ログの肥大 | logrotate や journald の上限を土台で設定しておく。ディスクが一杯になるのは、長く動くサーバーでよくある障害 |
| インスタンスに残るデータ | アップロードされたファイルなどがインスタンスのディスクにあると、入れ替えで消える。S3 や EFS などの外に置くか、入れ替えのときに移す手順が要る |
| バックアップ | データがインスタンスにあるなら EBS のスナップショット（AWS Backup など）。データベースは RDS 側で |

## 5. アクセスと権限

| 項目 | 内容 |
|---|---|
| ログインの手段 | SSH の鍵を使うなら、鍵の管理と退職者などへの対応。Session Manager に寄せると鍵の管理が要らなくなり、操作の記録も残る（[SSM Session Manager による EC2 運用](../ec2-operations/ssm-session-manager-operations.md)） |
| SSM Agent | 自動では更新されない。土台の作り直しで新しくなるが、間が空くなら State Manager で更新する |
| シークレット | データベースのパスワードなどの定期的な変更。インスタンスに焼き込まず Parameter Store / Secrets Manager から読む形にしておくと、入れ替えなしで変えられる |

## 6. 手作業の変更を残さない

運用中にインスタンスで直接直したもの（設定ファイルの変更、パッケージの追加）は、次の入れ替えで消える。「直したら土台かアプリの定義に戻す」というルールと、直した内容の記録が要る。

## 7. 古いものの片付けと費用

| 項目 | 内容 |
|---|---|
| 古い AMI とスナップショット | リリースのたびに増える（AMI 公開パイプラインでは削除しない。[決定事項 D8](../../ami-publish-development-plan.md)）。ロールバックに使う分だけ残して整理する |
| 起動テンプレートの古いバージョン | 上限（1 つの起動テンプレートで 10,000 版）は遠いが、整理の方針は決めておく |
| 使っていない Elastic IP | 割り当てたまま関連付けていないと課金される。入れ替えや廃止のときの残りに注意 |

## 8. 長期の計画

| 項目 | 時期 |
|---|---|
| AL2023 の標準サポートの終了 | 2027-06-30（以降はセキュリティと重大なバグの修正だけ） |
| AL2023 のメンテナンスの終了 | 2029-06-30。それまでに次の OS へ移行する |
| Ruby・Rails のサポートの終了 | 各バージョンの終了に合わせて上げる |
| インスタンスタイプの世代 | 新しい世代への移行（費用と性能の見直し） |

## 運用する人が別の場合の責任の分け方

配った AMI を運用するのが別の人（顧客や別チーム）なら、責任の分け方を決めて渡す。

| 項目 | 例 |
|---|---|
| こちらが提供するもの | 新しい AMI（セキュリティの修正を含む）、何が直ったかの説明、入れ替えの手順 |
| 運用する側がすること | 入れ替えの実施、監視、バックアップ、証明書の確認 |
| その場での変更 | 許すか。許すなら、次の AMI への入れ替えで消えることの了解 |

## 優先度のまとめ

| 優先度 | メンテナンス |
|---|---|
| 高 | セキュリティの更新（入れ替えのサイクルを回し続ける）、証明書の更新と監視、ディスク（ログ）の監視 |
| 中 | ログとデータをインスタンスの外に出す、どのインスタンスが何の版かの一覧、アクセスの管理 |
| 低（計画的に） | 古い AMI などの片付け、OS とミドルウェアのサポート終了への対応 |

## 土台に入れておくと手当てが要らなくなるもの

| 土台に入れるもの | 減るメンテナンス |
|---|---|
| CloudWatch エージェント（ディスク・メモリ・ログの送信） | 監視とログの消失 |
| logrotate と journald の上限 | ディスクの肥大 |
| Session Manager で接続できる構成（SSH の鍵を配らない） | 鍵の管理 |
| 証明書の保存と復元、更新の失敗の通知 | 証明書の引き継ぎと期限切れ |
| シークレットを起動時に読む仕組み | シークレットの変更のための入れ替え |
