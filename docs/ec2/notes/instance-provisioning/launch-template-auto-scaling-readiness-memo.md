# メモ: 起動テンプレートを後から Auto Scaling グループで使うための余地

> 位置付け: 将来の選択肢を忘れないための備忘メモ。**現時点の運用では Auto Scaling グループを利用しておらず、本計画のスコープ外。** 関連する本体は [開発計画: AMI 作成以降](../../ami-publish-development-plan.md)（スコープは AMI の作成と起動テンプレートの用意まで）。

## 結論

**余地は残る。** 起動テンプレートの作成時点で Auto Scaling グループ（以下 ASG）の構成を含めなくても、後から ASG を作って複数台構成にできる。

- 参照の向きは「**ASG が起動テンプレートを参照する**」であり、起動テンプレートの中に ASG の設定を持つ必要はない
- 後から ASG を作るときに「この起動テンプレート（のこのバージョン）でインスタンスを N 台動かす」と指定するだけでよい
- 同じ起動テンプレートは、ASG のほか、単体でのインスタンス起動（`run-instances`）や EC2 Fleet でも使える

```
AMI                 … ディスクの中身（OS・アプリがインストール済みの状態）
  ↑ ImageId で指定
起動テンプレート      … インスタンスの起動設定（AMI、インスタンスタイプ、IAM、UserData など）  ← 本計画のスコープはここまで
  ↑ 起動テンプレート（のバージョン）を指定
Auto Scaling グループ … 「この起動テンプレートでインスタンスを常に N 台動かす」管理役          ← スコープ外（将来の選択肢）
  ↓ 起動
本番の EC2 インスタンス
```

## ASG で使える状態を保つための注意点

### 起動テンプレート側

| 注意点 | 内容 |
|---|---|
| サブネット・固定のプライベート IP を入れない | 起動するサブネットは ASG 側で指定する。起動テンプレートにサブネット、固定 IP、特定のネットワークインターフェイスを入れると、複数台で使えないか ASG の指定と衝突する。[AMI 公開パイプラインの起動テンプレート例](../../ami-build-pipeline.md#テンプレート例)はセキュリティグループのみの指定なので問題ない。一方、[nginx + Passenger + Rails のサンプル](../../samples/nginx-passenger-rails/template.yaml)の起動テンプレートはサブネットを指定しているため、流用する場合は外す |
| UserData を 1 台前提にしない | 固定のホスト名の設定など、1 台だけを想定した処理を書かない |
| AMI にインスタンス固有の状態を残さない | AMI 作成前の後片付け（ログ、鍵など）で対応済み |

### アプリ側（複数台にするときに必要になること）

| 注意点 | 内容 |
|---|---|
| DB | インスタンスの外（RDS など）に置く。SQLite のようにインスタンス内に置く構成は複数台では使えない |
| ファイル・セッション | アップロードファイルやセッションをローカルディスクに保存している場合は、S3 や共有ストアに移す |
| 定期実行ジョブ | cron など 1 台だけが実行すべき処理は、複数台で重複実行されるため仕組みを見直す |
| ヘルスチェック | ロードバランサーのヘルスチェックには既存の `/up` をそのまま使える |

## 移行するときの作業

起動テンプレートを上記の状態に保っておけば、複数台構成への移行は次の作業で済む。

1. アプリ側の対応（上記の DB・ファイル・セッション・定期実行ジョブ）
2. ロードバランサー（ALB）とターゲットグループの作成
3. 起動テンプレートを参照する ASG の作成（別スタックとし、AMI 公開パイプラインが更新する起動テンプレートのスタックには含めない）
4. 新しい AMI を本番に反映する方法（ASG のインスタンス更新など）の決定
