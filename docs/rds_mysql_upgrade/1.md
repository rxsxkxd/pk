## 手順概要

1. **実行SQL検証** — Green構築後・切替後に行う作業で、事前は重いクエリの棚卸しのみ。
2. **ライブラリ検証** — 接続経路とクライアントライブラリのバージョンを確認。mysql_native_passwordは8.4でON固定のためアプリ改修不要。
3. **パラメータ確認** — Blue/Green成立の実質的な事前準備（binlog_format=ROW、8.4用パラメータグループ、backup_retention_period≥1日、MyISAM→InnoDB変換、オプショングループ注意、事前スナップショット）。
4. **インスタンスタイプ検証** — 記事はコスト文脈のみだが、AWS公式ドキュメント上は実は前提条件。前世代インスタンスクラスではMySQL 8.4を作成できないため、対象が現行世代クラスか事前確認が必要。
5. **Green構築** — `create-blue-green-deployment`でGreenを8.4.9として作成、所要20〜40分。
5.5. **Green検証** — Green単体でVERSION・binlog_format・認証・InnoDB化・レプリ遅延・件数一致を確認する、記事最重要の安全弁。
6. **切替** — `switchover-blue-green-deployment`でエンドポイントをGreenへ付け替え、通常1分未満。
7. **切替後ヘルスチェック・後片付け** — バージョン/接続/ログを確認後、旧Blueとデプロイを削除して二重課金を防止。

---

## 記事の要旨

RDS for MySQL 8.0 は 2026年7月31日で標準サポートが終了し、8月1日から Extended Support の課金が自動的に始まります。東京リージョンでは vCPU 時間あたり $0.12（3年目からは $0.24）で、micro〜large はすべて 2 vCPU のため、db.t3.micro 1台でも月 +約¥28,000 ── 本体料金の約9.6倍が純増します。筆者は自社の本番RDS 3台（8.0.44）を Blue/Green Deployments で 8.4.9（LTS、コミュニティサポート2032年4月まで）へ移行し、実測ダウンタイムは13秒でした。

主眼は手順そのものより「延長サポート料金は割高で見落とされやすいので期限内に上げ切れ」というコスト論です。

## ご提示の順序に沿った整理

### 1. 実行SQLの検証
8.4 はオプティマイザの挙動が一部変わるため、重い一覧・検索・レポート系のクエリでプラン悪化が出ていないかをスロークエリログで確認する、という扱いです。ただし記事上、これは**事前**ではなく Green 構築後（代表クエリの疎通）と切替後（ログ確認）の作業です。事前にできるのは「重いクエリの棚卸し」までです。

### 2. ライブラリの検証
切替前に対象DBへ接続している経路を洗い出し、各アプリの MySQL クライアントライブラリのバージョンを確認することが推奨されています。加えてコネクションプールがリトライに対応していれば、クエリ実行中の切断も吸収できます。
認証面はRDS for MySQL 8.4 のパラメータグループでは mysql_native_password が ON 固定（変更不可）であり、native認証のユーザーはそのまま接続できたため、アプリ改修は不要だったとのことです。

### 3. パラメータの確認
Blue/Green の**有効化条件**そのもので、ここが実質的な事前準備の本体です。

- binlog_format = ROW が必須。RDSのデフォルトは MIXED なのでカスタムパラメータグループで明示設定する（動的パラメータのため再起動不要）
- 8.4 family のパラメータグループを新規作成し、こちらにも ROW を入れておく
- backup_retention_period が1日以上
- MyISAM が残っていると binlog レプリケーションの整合性が保証されず成立しないため、事前に ALTER TABLE ... ENGINE=InnoDB で変換
- カスタムオプショングループだとメジャーアップの Blue/Green が弾かれる（中身が空ならデフォルトOGに戻す）
- 切替前に手動スナップショットを取得

### 4. インスタンスタイプの検証
**元記事にはこの観点はありません。** 記事本文ではコスト文脈（micro〜largeは一律2vCPU）でしか触れられていませんが、AWS公式ドキュメントを確認すると実際には移行の前提条件の一つです。

AWS公式ドキュメント（[Major version upgrades for RDS for MySQL](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_UpgradeDBInstance.MySQL.Major.html)）には次の記載があります。

> You can only create MySQL version 5.7, 8.0, and 8.4 DB instances with latest-generation and current-generation DB instance classes.（MySQL 5.7・8.0・8.4のDBインスタンスは latest-generation / current-generation のインスタンスクラスでのみ作成できる）

前世代（previous-generation）クラスのままでは 8.0→8.4 のメジャーアップグレード自体が不可で、先にインスタンスクラスを現行世代へ変更してからでないとアップグレードできません。旧世代クラス（t2・m4・r4系など、多くはすでにRDSで新規作成自体が廃止済み）を使い続けている環境が対象に含まれていないか、念のため確認しておく必要があります。

Blue/Green では Green は基本的に Blue と同構成で作られるため、Blue側が前世代クラスのままだと `--target-engine-version 8.4.9` を指定したBlue/Green作成自体が失敗する可能性があります。サイズ変更を兼ねる場合は別途 `--target-db-instance-class` を検討する領域ですが、それ以前に「対象インスタンスが現行世代クラスかどうか」の確認は着手前に済ませておくべき項目です。

### 5. 移行先のインスタンス作成（Green構築）
`aws rds create-blue-green-deployment` に ソースARN / `--target-engine-version 8.4.9` / 8.4用パラメータグループを指定。まず同じ8.0でレプリカとして複製 → Green だけを 8.4.9 へアップグレード → 8.4化後も Blue(8.0) から追従し続ける、という流れで、全体で20〜40分程度と工程中で最も時間がかかります。

### 5.5. Green の検証 ← ここを独立させるべき
ご提示の順序では抜けていますが、記事では最も重要な安全弁です。Green のエンドポイントに直接つないで、VERSION() が 8.4.9・binlog_format が ROW・既存ユーザーがnative認証で接続可・全テーブルがInnoDB・Seconds_Behind_Source = 0 かつ IO/SQLスレッドがYes・主要テーブルの件数がBlueと一致、を確認します。本番は Blue で動いているので、問題が見つかっても引き返せます。

### 6. インスタンス切り替え
`aws rds switchover-blue-green-deployment --switchover-timeout 300`。AWS がレプリ遅延ゼロを確認 → 書き込みを一瞬止める → エンドポイントを Green に付け替える処理を行い、その瞬間に既存コネクションが切れて再接続が走ります（通常1分未満）。エンドポイント名は変わらないためアプリ側の接続先変更は不要。切替時間がALB/nginxのアイドルタイムアウト（既定60秒）より十分短ければ、エラーではなく「遅いけど成功」として吸収されます。

### 7. 切り替え後のヘルスチェック
VERSION() が 8.4.9でエンドポイント名が維持されていること、各アプリがログイン・主要画面・代表的な書き込みで応答すること、スロークエリログ・エラーログに新規異常がないこと。
後始末として、旧Blue は `<元の名前>-old1` として残るので当面は切り戻し用の保険になりますが、新Blue側の書き込みは反映されないため時間が経つほど非現実的になります。動作確認後は旧Blueと Blue/Green デプロイを削除して二重課金を止めます。削除保護がONだと `--no-deletion-protection` で解除が必要。

## 順序についての指摘

ご提示の7ステップはおおむね妥当ですが、2点ずれます。

1. **「実行SQLの検証」を最初に置くのは実務上むずかしい** — 8.4での挙動は Green ができるまで実測できません。事前は「対象クエリの棚卸し」、実検証は 5.5 と 7 に分割するのが実態に合います。
2. **「移行先のインスタンス作成」と「切り替え」の間に検証フェーズが必ず入る** — Blue/Green の価値の大半がここにあるので、独立した工程として立てておくべきです。

逆に、**ご提示の順序に足りていないのは工程0の「Blue/Green 成立条件のスクリーニング」**です。以下はいずれも満たしていないと作成リクエスト自体が弾かれる／メジャーアップグレードに進めない性質のもので、「パラメータの確認」に含まれるとも読めますが、実務上は最初にまとめてチェックする類のものです。

- MyISAM残存の有無
- カスタムオプショングループの中身
- backup_retention_period（1日以上）
- **インスタンスクラスが現行世代（latest/current-generation）かどうか** — 記事本文にはない観点ですが、AWS公式ドキュメント（上記4参照）により前世代クラスのままでは8.4作成自体が拒否されるため、他の3項目と同列の必須チェックです。
