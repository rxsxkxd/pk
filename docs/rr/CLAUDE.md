# インフラのコードの決まり（CLAUDE.md の雛形）

> 汎用の雛形（AWS と CloudFormation / SAM を想定）。新しいプロジェクトでは、このファイルの内容を `CLAUDE.md` に足し（設計・開発の決まりは DEVELOP_CLAUDE.md）、`<…>` の部分とプロジェクト固有の決まりを書き足す。

## 1. 進め方

- **AWS に変更を加える操作はしない**: スタックの作成・更新・削除、リソースの変更、デプロイは、頼まれたときだけ行う。ふだんは手順書とコマンドを渡す。読み取りの操作（`describe`・`get`・`list`）も、どのアカウントとリージョンかを確かめてから
- **大きな取得は先に確かめる**: コンテナイメージ・ツールチェーン・依存の取得は、量を伝えて可否を聞く
- **手元で確かめられることは確かめる**: テンプレートは cfn-lint、シェルは shellcheck、ワークフローは actionlint、SAM は `sam build`。AWS を呼ぶスクリプトは、`aws` を記録するだけの偽物に差し替えて流し、コマンドの順番と、設定が足りないときに止まることを見る
- **確かめていないことを残す**: AWS 上でしか確かめられないことは、未確認の一覧（例: `OPEN_ITEMS.md`）に書く

## 2. テンプレート（CloudFormation / SAM）

- **名前をベタ書きしない**: リソースの名前・関数名・ログのグループ名は、パラメータ（例: `NamePrefix`）か、スタック名（`AWS::StackName`）から作る
- **パラメータには説明を付ける**: 英語の `Description` と、その上の行に日本語のコメント（`# …`）
- **説明の文字列に記号を使わない**: SG の `GroupDescription` などは、使える文字が限られる（`'` などでエラーになる）。英数字と基本的な記号だけにする
- **秘密の値はテンプレートに入れない**: API キーや署名の鍵は、スタックの外で Parameter Store（SecureString）か Secrets Manager に作り、テンプレートには名前だけを渡す。ログや環境変数に平文で出さない。読めるのは、実行のロールだけにする
- **バケットの基本**: 公開のブロック、暗号化、TLS だけを許すポリシー、消えては困るものは `DeletionPolicy: Retain`、一時的なものは期限で消す
- **ログには保持期間を付ける**（パラメータで変えられるように）
- **版を固定する**: ランタイム・イメージ・ツールの版はテンプレートに明記し、保守の文書に、どこを上げるかを一覧にする

## 3. 構築と更新を分ける

- **構築（最初の環境づくり）**: スタックの作成と、秘密の値・接続などの準備は、手順書に沿って手で行う。手順書は `infra/` に置く
- **更新（CD）**: CD は、アプリのコード（Lambda の zip）と画面のファイルの差し替えだけにする。スタック・IAM・環境ごとの設定ファイルには触れない。そのぶん、CD のロールの権限は差し替えに要るものだけで済む
- **スタックと CD がずれないようにする**: スタックは固定の場所（例: `<prefix>/current/`）の成果物を指し、CD はそこに置いてから差し替える。あとでスタックを更新しても、動いているコードが変わらない
- **ロールバックできるように控えを残す**: 成果物はコミットごとの場所（例: `releases/<sha>/`）にも置き、戻すときはビルドし直さずに控えを使う

## 4. CI / CD

- **置き場所**: CI は `ci/`、CD は `cd/`（テンプレート・buildspec・スクリプト・文書）。`infra/` に置く CI / CD のものは、最初の構築の手順書だけ
- **CI はコミットごとの単体テストだけ**: GitHub Actions などで、pull request と push のたびに流す。AWS の権限を持たせない
- **CD はソースから**: CD は CI の結果を受け取らず、ソースから同じテストを流してからビルドする。ビルドは 1 回だけにし、その成果物を E2E とデプロイにそのまま渡す
- **長期の鍵を置かない**: 外部のサービスから AWS へは OIDC、AWS から外部のリポジトリへは CodeConnections などの一時的な認証を使う
- **権限を段ごとに分ける**: テストとビルドの段は AWS の資源に触れない。デプロイの段だけが、差し替えに要る権限を持つ
- **画面のファイルの上げ方**: 名前にハッシュの付いたファイル（`assets/*`）を先に上げ、`index.html` を最後に上げる。ハッシュ付きは長くキャッシュし、`index.html` はキャッシュさせない。環境ごとの設定（例: `config.json`）はビルドに含めず、CD でも上げない
- **イメージの取得元**: CI / CD でコンテナイメージを取るときは、Docker Hub の回数の上限に当たらないよう、ECR Public のミラー（`public.ecr.aws/docker/library/...`）などを使う
- **ビルド環境の版**: マネージドのビルド環境に要る版がないときは、言語のツールチェーンの自動取得（Go の `GOTOOLCHAIN=auto` など）で補い、イメージが追いついたら外す

## 5. 構成の注意

- **CPU の種類を選べる実行環境**: 動作に差がなければ、安いほう（AWS なら arm64）を基本にする。ビルドとテストも同じ種類でそろえる
- **ランタイムの更新の範囲を確かめる**: マネージドのランタイムでも、どこまで自動で更新されるか（言語の本体・OS・同梱の SDK）はサービスと種類で違う。自動で更新されない部分は、ビルドし直してデプロイする前提で手順を用意する
- **付けたい機能が直接付けられないサービス**: WAF・認証・独自ドメインなどが、そのサービスに直接付かないことがある。前段（CDN やロードバランサー）に付けられるかを先に確かめ、構成に含めておく
- **固定費のかかる部品**: 時間で課金される部品（NAT、常時起動のインスタンスなど）は、費用と、1 か所にしか置かないときの単一の障害点を書き出してから決める。冗長にするかはパラメータで選べるようにする
- **外への通信は絞る**: 送信先・ポートは必要な範囲だけに許可する。広く開けるときは理由を書く
- **タイムアウトは層ごとに書き出す**: 利用者に近い層から内側まで（CDN・ゲートウェイ・関数・外部への呼び出し）の上限を表にし、内側ほど短くする。各サービスの変えられない上限も一緒に書く
- **公開しないサイト**: 検索エンジンに載せたくないときは、レスポンスヘッダー（`X-Robots-Tag`）を配信の層でまとめて付け、HTML の `meta` も入れる。画面だけでなく API の応答にも付ける
