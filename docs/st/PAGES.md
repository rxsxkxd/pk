# 画面と HTML テンプレートの構成

チケット QR API について、利用者が見る画面がどこで作られているかをまとめる。対象は次の3つ。

- Web フロントエンド（SPA）の設計
- API の Go 版・Node 版が返す HTML
- ローカル開発用のフォーム

API の詳しい仕様は [DESIGN.md](DESIGN.md)、SPA の設計は [web/DESIGN.md](web/DESIGN.md)、Node 版の詳細は [NODE.md](NODE.md) にある。

## 1. 登場するエンドポイントと画面

このドキュメントでは、エンドポイントと画面を次の名前で呼ぶ。括弧内はコード上のルート名（ログに出る名前）。

### API のエンドポイント

| 名前 | メソッドとパス | 何をするか |
|---|---|---|
| **QR 同梱発行 API**（`issue-inline`） | `POST /v1/tickets/qr-inline` | 写真を受け取ってチケットを発行し、QR 画像（PNG を base64 にしたもの）を JSON に入れて返す。通信1回で QR まで手に入る |
| **チケット発行 API**（`issue`） | `POST /v1/tickets` | 写真を受け取ってチケットを発行する。普通のフォーム送信なら、チケット表示ページへ移動させる（`303`）。`Accept: application/json` を付けると、署名付きの QR 画像 URL を JSON で返す（`201`） |
| **チケット表示ページ**（`get-view`） | `GET /v1/tickets/{ticketCode}/view?sig=…` | API が HTML で返すチケットの画面。QR は `<img>` で QR 画像 API から読み込む |
| **QR 画像 API**（`get-qr`） | `GET /v1/tickets/{ticketCode}/qr?sig=…` | 署名（`sig`）を照合して、チケットコードの QR を PNG で返す。画像はその都度作る |

署名付きの URL は、チケット発行 API が作る。チケット表示ページと QR 画像 API は、署名が合わなければ 403 を返す。

### 画面

| 名前 | どこで作るか | 内容 |
|---|---|---|
| **SPA の発行画面**（`#/`） | Web フロントエンド | 写真を選んで発行する。メインは画面遷移方式で、ほかの方式はオプション（4章） |
| **SPA のチケット画面**（`#/tickets/{code}?sig=…`） | Web フロントエンド | URL の情報だけから QR とチケットコードを表示する |
| **チケット表示ページ** | API（Go / Node） | 上の表の `get-view`。フォーム送信で発行したときの移動先 |
| **エラーページ** | API（Go / Node） | チケット発行 API（フォーム送信のとき）とチケット表示ページで、エラーを HTML で見せる |
| **ローカル試験フォーム**（`http://localhost:8080/`） | ローカル開発用サーバー（Go / Node） | QR 同梱発行 API とチケット発行 API を手で試すためのフォーム。デプロイしない |

## 2. 全体像: API の使い方は3パターン

| パターン | 使う API と、その役割 | 使う画面 |
|---|---|---|
| **1. QR 同梱発行 API を使う** | ① QR 同梱発行 API: 発行して、QR 画像そのもの（JSON の中の base64）を受け取る | SPA の発行画面（その場表示方式。オプション）、ローカル試験フォーム |
| **2. チケット発行 API と QR 画像 API を使う** | ① チケット発行 API: 発行して、**JSON**（チケットコードと署名付きの QR 画像 URL）を受け取る<br>② QR 画像 API: SPA が描画した画面の `<img>` が QR を取る | SPA の発行画面（画面遷移方式。**SPA のメイン**）→ SPA のチケット画面 |
| **3. チケット表示ページと QR 画像 API を使う** | ① チケット発行 API: 発行して、チケット表示ページへの**リダイレクト**（303）を受け取る<br>② チケット表示ページ: API が HTML で画面を返す<br>③ QR 画像 API: その HTML の `<img>` が QR を取る | 普通のフォーム送信（SPA のフォーム送信方式（オプション）、ローカル試験フォーム、SPA を使わない利用）→ チケット表示ページ |

チケット発行 API は、パターン2と3の両方で使う。何を受け取るかは `Accept` ヘッダーで変わる。

| 呼び出し方 | 受け取るもの | パターン |
|---|---|---|
| `fetch` で `Accept: application/json` を付ける | `201` JSON `{ ticketCode, issuedAt, sig, qrUrl }` | 2 |
| 普通のフォーム送信（ブラウザの既定の `Accept`） | `303` チケット表示ページへのリダイレクト | 3 |

パターン2と3は、どちらも「発行」と「QR 画像の取得」を分けている。そのため、リロードや URL の共有をしても再発行されない。違いは、チケットの画面を SPA が描画するか（パターン2）、API が HTML で返すか（パターン3）だけ。

### パターン1: QR 同梱発行 API を使う

```
SPA の発行画面 / ローカル試験フォーム
  └─ fetch: POST /v1/tickets/qr-inline（写真）
       ◀─ 201 JSON { ticketCode, issuedAt, qr: { mimeType, data(base64) } }
  └─ <img src="data:image/png;base64,…"> でその場に表示
```

- 通信は1回で、QR まで手に入る
- 結果は URL に残らないので、リロードすると消える。もう一度見るには再発行になる
- エラーは JSON

### パターン2: チケット発行 API と QR 画像 API を使う

チケット発行 API は JSON を受け取るために使う。

```
SPA の発行画面（画面遷移方式。SPA のメイン）
  └─ fetch: POST /v1/tickets（写真、Accept: application/json）
       ◀─ 201 JSON { ticketCode, issuedAt, sig, qrUrl }
  └─ SPA のチケット画面 #/tickets/{code}?sig=… へ移動
SPA のチケット画面（URL の code と sig だけで描画する）
  └─ <img> が GET /v1/tickets/{code}/qr?sig=… ◀─ 200 PNG
```

- リロードや URL の共有をしても、SPA のチケット画面が QR 画像 API を呼び直すだけで、再発行されない
- エラーは JSON。署名が合わないと QR 画像 API が 403 を返し、SPA は `<img>` の読み込みエラーとして扱う
- チケット表示ページは使わない

### パターン3: チケット表示ページと QR 画像 API を使う

チケット発行 API は、チケット表示ページへのリダイレクトを受け取るために使う。

```
普通のフォーム送信（SPA のフォーム送信方式、ローカル試験フォーム、SPA を使わない利用）
  └─ form: POST /v1/tickets（写真）
       ◀─ 303 Location: {公開ベース URL}/v1/tickets/{code}/view?sig=…
チケット表示ページ
  └─ GET /v1/tickets/{code}/view?sig=…
       ◀─ 200 HTML（<img src="{公開ベース URL}/v1/tickets/{code}/qr?sig=…"> を含む）
  └─ <img> が GET /v1/tickets/{code}/qr?sig=… ◀─ 200 PNG
```

- 発行の直後に別の URL へ移動させる（PRG）ので、リロードしても再送信にならない。チケット表示ページの URL を開き直すだけで、再発行されない
- エラーは HTML のエラーページ（チケット発行 API・チケット表示ページとも）

### 画面を作る場所

| | Web フロントエンド（SPA） | API が返す HTML | ローカル試験フォーム |
|---|---|---|---|
| 置き場所 | `web/`（設計は `web/DESIGN.md`） | Go: `go/internal/view/`（テンプレートは `templates/`）<br>Node: `node/src/app.ts` の Views セクション | Go: `go/cmd/ticketqr/local.go`<br>Node: `node/src/local.ts` |
| 状態 | 実装済み（E2E は保留中） | 実装済み | 実装済み（開発専用） |
| 画面 | SPA の発行画面、SPA のチケット画面 | チケット表示ページ、エラーページ | ローカル試験フォーム |
| 関わるパターン | 2（メイン）、1・3（オプション） | 3 | 1、3 |

## 3. パターンごとの評価

### 3.1 比較

| 観点 | 1. QR 同梱発行 API | 2. チケット発行 API（JSON）＋ QR 画像 API | 3. チケット発行 API（リダイレクト）＋ チケット表示ページ ＋ QR 画像 API |
|---|---|---|---|
| 発行して QR が出るまでの通信 | **1回** | 2回 | 3回 |
| Lambda の起動回数（初回の表示） | 1（tickets） | 2（tickets、get-qr） | 3（tickets を2回、get-qr） |
| リロード | **消える**（もう一度見るには再発行） | 再表示できる（QR を取り直すだけ） | 再表示できる（PRG なので再送信もしない） |
| URL の保存・共有 | できない | できる | できる |
| JavaScript | 必要 | 必要 | **不要**（普通のフォームで動く） |
| CORS | 必要（別オリジンからの `fetch`） | 必要 | **不要**（画面の移動と `<img>` だけ） |
| 画面の作り手 | SPA | SPA | API（Go と Node の両方に HTML がある） |
| 署名付き URL の露出 | **なし**（URL を作らない） | SPA の URL（`#` 以降）に入る | ページの URL（クエリ）に入る |

### 3.2 パターン1: QR 同梱発行 API を使う

**良い点**
- 通信が1回で済み、表示までが一番速い。コールドスタートの影響も1回分だけ
- 署名付き URL を作らないので、URL が漏れて他人に見られる心配がない
- クライアントの処理が一番単純（受け取った base64 を `<img>` に入れるだけ）

**悪い点**
- 結果が残らない。リロードやタブを閉じると消え、もう一度見るには再発行が必要になる（画像解析の費用がかかり、同じ人に別のコードが発行される）
- URL で保存・共有できない
- JavaScript と CORS が必要
- 応答に PNG を base64（約1.33倍）で入れるので、応答が少し大きい（数KB なので実害はほぼない）

### 3.3 パターン2: チケット発行 API（JSON）と QR 画像 API を使う

**良い点**
- リロードや共有に強く、再発行されない
- 画面を SPA が自由に作れる（デザイン、発行日時の表示、エラーの見せ方を API に手を入れずに変えられる）
- 署名付き URL を `#` 以降に置くので、`<img>` が QR を取りに行くときの Referer やサーバーのログに `sig` が残らない
- 同じ JSON を、将来のアプリなどほかのクライアントでも使える

**悪い点**
- 通信が2回、Lambda の起動が2回。表示を開き直すたびに QR 画像 API が呼ばれる
- 署名付き URL を知っていれば誰でも開ける（有効期限がない。パターン3も同じ）
- QR の取得に失敗したとき、`<img>` の読み込みエラーからは原因（403 か通信エラーか）を区別できない
- SPA の配置（S3 / CloudFront）と CORS が必要

### 3.4 パターン3: チケット発行 API（リダイレクト）、チケット表示ページ、QR 画像 API を使う

**良い点**
- JavaScript なしで、普通の HTML フォームで動く。対応できる環境が一番広い
- PRG なので、リロードしても再送信・再発行されない。URL の共有もできる
- CORS も SPA の配置も不要で、API だけで完結する

**悪い点**
- 通信が3回、Lambda の起動が3回で、表示が一番遅い。コールドスタートが重なると体感にも影響する
- 画面の HTML が API 側にあり、Go と Node の2か所にある（SPA と合わせると、チケットの画面は3か所）
- 署名付き URL がページの URL（クエリ）に入るので、ブラウザの履歴やアクセスログに残る（Referer には `Referrer-Policy: no-referrer` で出さない）
- エラーの見せ方が、API の HTML のエラーページに限られる

### 3.5 共通の課題

- ほかのサイトから発行させない対策（Origin の照合）が、どのパターンでもまだない。フォーム送信も `fetch` も、ほかのサイトから送られれば処理されてしまう

### 3.6 決定: SPA はパターン2をメインにする

| | SPA での扱い | API 側 |
|---|---|---|
| パターン2 | **メイン**（画面遷移方式。既定で有効） | 対応したまま残す |
| パターン1 | オプション（その場表示方式。`config.json` の `modes` で有効にする） | 対応したまま残す |
| パターン3 | オプション（フォーム送信方式。`config.json` の `modes` で有効にする）。SPA を使わない利用（普通のフォーム送信）でも使う | 対応したまま残す |

API 側は、3パターンすべてに対応する前提で、今の実装（QR 同梱発行 API、チケット発行 API の JSON とリダイレクト、チケット表示ページ、QR 画像 API）を残す。

## 4. Web フロントエンド（SPA）

静的ファイルとしてビルドし、S3 または CloudFront から配信する SPA。サーバー側の処理は持たない。詳しくは `web/DESIGN.md`。

| 項目 | 内容 |
|---|---|
| 技術 | Vite 8、Vue 3.5、vue-router（hash モード）、Pinia、Tailwind CSS 4、zod |
| 利用者 | スマートフォン（iPhone / Android）のブラウザが主 |
| 写真 | 加工せず、そのまま `FormData` で送る。4MB を超えるときは送る前に知らせる |

### 3つの発行方式

| | 画面遷移方式（メイン） | その場表示方式（オプション） | フォーム送信方式（オプション） |
|---|---|---|---|
| 2章のパターン | パターン2 | パターン1 | パターン3 |
| `config.json` の `modes` | `page`（既定で有効） | `inline` | `form` |
| 流れ | チケット発行 API から JSON を受け取り、SPA のチケット画面に移る。QR は `<img>` で QR 画像 API から読み込む | QR 同梱発行 API の応答に入っている QR（base64）を、SPA の発行画面にそのまま表示する | 普通のフォームでチケット発行 API に送り、リダイレクトで API のチケット表示ページに移る（SPA には戻らない） |
| リロード | URL から同じ画面を出せる。再発行はされない | 結果は消える | URL から同じ画面を出せる |
| URL の共有 | できる | できない | できる |

### API 側に必要な変更

| 変更 | 状態 |
|---|---|
| チケット発行 API の `Accept: application/json` 対応 | 実装済み（Go・Node） |
| CORS（SPA の JS が応答を読めるようにする。フォーム送信方式は不要） | 未実装 |
| Origin の照合（ほかのサイトから発行させない） | 未実装 |

未確定の事項（その場表示方式の結果をリロード後も残すか、配置方式、CORS を先に実装するか、デザイン）は、`web/DESIGN.md` 11章にある。

## 5. API が返す HTML（Go 版・Node 版）

### 5.1 画面の中身

| 画面 | 表示する場面 | 中身 |
|---|---|---|
| チケット表示ページ | フォーム送信でチケット発行 API を呼んだときの移動先 | 見出し、`<img src=署名付きの QR 画像 API の URL>`、チケットコード。`<main data-ticket-code="…">` |
| エラーページ | チケット発行 API（JSON を求めていないとき）とチケット表示ページのエラー | 「チケットを表示できません」とメッセージ。`<main data-error-code="…">` |

`data-*` 属性は、E2E テストが画面を見分けるための目印。

### 5.2 Go と Node の作り方

Go と Node は、同じ内容の HTML をそれぞれ別の方法で作る。テンプレートファイルは共有しない。

| | Go | Node |
|---|---|---|
| テンプレート | `go/internal/view/templates/ticket.html`、`error.html`（`html/template` の構文） | `node/src/app.ts` の `ticketView` / `errorView`（`hono/html` の `html` タグ付きテンプレート） |
| 同梱の方法 | `go/internal/view/view.go` の `//go:embed templates/*.html` でバイナリに埋め込む | コードそのものなので esbuild がバンドルに含める |
| 描画 | `view.Renderer`（起動時に1回だけテンプレートを解析） | 関数を呼ぶだけ |
| スタイル | 各 HTML の `<style>` に直接書く | 文字列定数 `STYLE` を `raw()` で埋め込む（example 用のバンドルに残さないため） |
| エスケープ | `html/template` が文脈に応じて自動で行う | `hono/html` が自動で行う |

**そろえていること**
- 文言、`data-*` 属性、`<img>` の属性、スタイル
- セキュリティヘッダー。CSP は `default-src 'none'; img-src {公開オリジン}; style-src 'unsafe-inline'` で、Go は handler、Node は `commonHeaders` が付ける。ほかに `Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`

**そろえていないこと**
- 空白・インデント、`<meta ... />` の書き方、エスケープの表記（Go は `&#34;`、Node は `&quot;`）。表示と意味は同じ

文言やデザインを変えるときは、Go と Node の両方を直す。

### 5.3 共有をやめた経緯

以前は、テンプレートを Go と Node で共有する想定で `st/templates/` に置いていた。そのため、Go のモジュールルート（`go.mod`）も、`templates/` を埋め込めるように `st/` 直下に置いていた。

Node が `hono/html` で自前の HTML を作ると決めてからは、テンプレートを使うのは Go だけになった。そこで次のように整理した。

- テンプレートを `go/internal/view/templates/` に移し、`view` パッケージが直接埋め込む（`st/templates/embed.go` は削除）
- `go.mod` と `go.sum` を `go/` に移した。import パスは `ticketqr/go/internal/…` から `ticketqr/internal/…` に変わった。`make -C go test` / `build` / `run` は `go/` の中で完結する
- Go のテストが読む共通のテストデータ（`st/testdata/`）は、これまでどおり相対パスで読む

## 6. ローカル試験フォーム

`make -C go run`（Go）と `npm run dev`（Node）で起動するローカルサーバーの `http://localhost:8080/` に出るフォーム。

- QR 同梱発行 API を `fetch` で呼ぶフォームと、チケット発行 API に普通のフォーム送信をするフォームの2つがある
- 後者は、チケット表示ページまでの移動をブラウザで確かめるのに使う
- Go と Node でそれぞれ別に書いている。Lambda のデプロイパッケージには含まれない

## 7. 今後の注意点

- SPA を実装すると、チケットを見せる画面が「SPA のチケット画面」と「チケット表示ページ」の2か所になる。表示内容（QR・チケットコード）を変えるときは、SPA・Go・Node の3か所を確認する
- SPA のメインは画面遷移方式（パターン2）。チケット表示ページは、SPA のオプション（フォーム送信方式）と、SPA を使わない利用のために残す（3.6）
