# 発行 API の守り: Origin の照合、CloudFront を通らないアクセスの防止、WAF

> 2026-10-14 作成（検討。どちらも未実装）。前提: 経路は統合（すべて CloudFront で受ける。2026-10-14 に確定）、アクセス数の上限は API Gateway で実装済み、WAF は判断を後回し（[RATE_LIMITING.md](RATE_LIMITING.md)）。これまでの記述: [../E2E.md](../E2E.md) 4.2（Origin の照合）、[../web/DEPLOY.md](../web/DEPLOY.md) 11章（CloudFront を通らないアクセス）。

## 1. 結論

- **2つは関係が深い**。CloudFront に付ける守り（WAF、CloudFront での Origin の照合）は、API Gateway を直接呼ばれると効かない。迂回を防ぐ仕組み（秘密のヘッダー）を API（Go）に入れるなら、Origin の照合も同じ場所で行うとまとめて済む
- 今は、API Gateway の上限（迂回されても効く）があるので、**すぐに困ることは限られる**
- WAF（4章）は入れる予定で、判断は後回し。WAF は CloudFront に付けるので、3章の迂回の対策とあわせて考える
- 推奨: WAF を入れると決めたとき、または Origin の照合を入れると決めたときに、**Go に「秘密のヘッダーの確認」と「Origin の照合」を一緒に入れる**（5章）。それまでに Origin の照合だけを先に入れたいなら、CloudFront Functions が手軽（2.3 の B）

## 2. Origin の照合

### 2.1 目的と、効く範囲

発行の API（`POST /v1/tickets`・`POST /v1/tickets/qr-inline`）で、リクエストの `Origin`（どのサイトから送ったか）が、許可したサイト（CloudFront のドメイン、または独自ドメイン）かを確かめ、違えば断る（403）。

| | 内容 |
|---|---|
| 防げる | **ほかのサイトに置かれたページから、閲覧者のブラウザを使って発行させること**（CSRF）。ブラウザは `Origin` を自動で付け、ページの側で偽れない |
| 防げない | **ブラウザを使わない機械的な大量のアクセス**。`curl` などは `Origin` を自由に書ける。これはアクセス数の上限（API Gateway・WAF）の役割 |
| なぜ要るか | 統合の構成では CORS を設定しないので、ほかのサイトのページは発行の応答を読めない。ただし、送ること自体（フォームの送信など）はでき、発行は行われる（解析サーバーの呼び出しと、上限の回数を消費する）。照合はこれを止める |

### 2.2 決めておくこと（どこで行っても共通）

| 項目 | 案 |
|---|---|
| `Origin` がないリクエスト（ブラウザ以外） | **通す**（推奨）。断ると `curl` での確認やスモークテストに `Origin` を付ける必要があるが、機械的なアクセスはもともと `Origin` を付けられるので、守れる範囲はほとんど増えない |
| 許可するオリジン | CloudFront のドメイン（`web.yaml` の出力 `WebUrl`）と、独自ドメインを付けるならそのドメイン |
| 対象 | 発行の2つのルートの `POST` だけ（QR 画像・チケットの画面の `GET` は対象外） |

### 2.3 どこで行うか

| 場所 | やること | 長所 | 短所 |
|---|---|---|---|
| A. API（Go） | 発行の2つのルートで、`Origin` を `ALLOWED_ORIGINS`（環境変数）と照合し、違えば 403（最初の設計。E2E.md 4.2） | CloudFront を通らずに直接呼ばれても効く。単体テストで確かめやすい | Go の実装、テンプレートのパラメータ（`AllowedOrigins`）、設定が要る |
| B. CloudFront Functions | `/v1/*` の振る舞いに、受け取ったときに動く小さな関数を付け、発行の `POST` の `Origin` が許可したもの以外なら 403 を返す | API の実装を変えない。`web.yaml` だけで完結する。費用はほぼ 0（100 万件あたり 0.10 USD） | 直接呼ばれると効かない（3章） |
| C. WAF | `POST /v1/tickets*` で、`Origin` が許可したもの以外ならブロックするルール | WAF を入れるなら、ほかのルールと一緒に管理できる | WAF の判断は後回し。直接呼ばれると効かない |

## 3. CloudFront を通らないアクセスの防止

### 3.1 何が起きうるか

統合の構成でも、API Gateway（HTTP API）には既定の公開 URL（`https://{API の ID}.execute-api.ap-northeast-1.amazonaws.com`）が残る。この URL を知っていれば、だれでも CloudFront を通さずに API を直接呼べる。統合では SPA が相対パスで API を呼ぶので、画面からこの URL は見えないが、秘密の値ではない（ログや設定から漏れうる。知られていないことに頼る守りになる）。

### 3.2 迂回されると効かなくなるもの

| 守り | 直接呼ばれたとき |
|---|---|
| WAF（後回し） | **効かない**（CloudFront に付けるため） |
| CloudFront での Origin の照合（2.3 の B） | **効かない** |
| CloudFront のアクセスログ | 残らない（API Gateway のアクセスログには残る） |
| API Gateway の上限（1時間 1 万件・1日 10 万件、1 秒あたり） | **効く**（API Gateway 自体に付いているため） |
| Go での Origin の照合（2.3 の A） | 効く |

### 3.3 防ぎ方

| 方法 | やること | 防げるか | 手間 |
|---|---|---|---|
| **1. 秘密のヘッダー（推奨）** | CloudFront が API に送るリクエストに、秘密の値のヘッダー（例: `X-Origin-Verify`）を付け、API（Go）がその値を確かめる。なければ 403 | **防げる** | `web.yaml` の API のオリジンにヘッダー（`OriginCustomHeaders`）、Go に確かめる処理、秘密の値の置き場所（Parameter Store）と入れ替えの手順（入れ替えの間は新旧どちらも通す） |
| 2. 既定の URL を無効にする | API Gateway に独自ドメインを付け、既定の URL を使えなくする（`DisableExecuteApiEndpoint`）。CloudFront は独自ドメインに送る | 単独では防げない（独自ドメインも直接呼べる）。見つけにくくなるだけ | 独自ドメイン、証明書（ACM）、DNS、`api.yaml` の変更 |
| 3. Lambda の認可の関数 | API Gateway に、ヘッダーを確かめる小さな関数（Lambda オーソライザー）を付ける | 防げる（1 と同じ。Go の発行の処理は変えない） | 関数が1つ増える。呼び出しごとの費用と遅れ（結果の使い回しで軽くできる） |

秘密の値は、CloudFront の設定（テンプレート）と API の両方が知る必要がある。`web.yaml` のパラメータに直接書くとスタックの設定に平文で残るので、Parameter Store に置き、デプロイのときに読み出して渡すか、API と CloudFront の両方が同じパラメータを参照する形にする（詳細は実装のときに決める）。

## 4. WAF

### 4.1 位置づけと状態

| 項目 | 内容 |
|---|---|
| 状態 | **入れる予定、判断は後回し**（2026-10-14）。テンプレート（`web.yaml`）には、既存の Web ACL を CloudFront に付けるパラメータ `WebAclArn` だけがある。Web ACL 自体はテンプレートに含めていない |
| 付ける場所 | CloudFront（統合の構成なので、画面と API の両方を守れる）。API Gateway（HTTP API）には直接付けられない |
| 作る場所 | Web ACL はスコープ `CLOUDFRONT` で、**us-east-1** に作る（Web のスタックのリージョンとは関係ない） |
| 迂回 | execute-api を直接呼ばれると効かない（3章）。WAF を入れるなら、3.3 の 1（秘密のヘッダー）もあわせて入れる |

### 4.2 WAF でできること（この API に関係するもの）

| 用途 | 内容 | 関連 |
|---|---|---|
| 送信元（IP）ごとの回数の制限 | 例: 1 つの IP から、5 分に 100 回を超えた発行をブロック。API Gateway ではできない（全体の制限だけ） | RATE_LIMITING.md 3・5章 |
| 全体の回数の制限 | 集計を「すべて」にしたレート制限。ただし数え方が粗く（数十秒の遅れ）、時間の枠は最大 10 分。1時間・1日の上限は API Gateway 側（quota-guard）で実装済み | RATE_LIMITING.md 7章 |
| 既知の攻撃のブロック | AWS のマネージドルール（Core rule set、Known bad inputs、IP reputation） | web/DEPLOY.md 13.1 |
| Origin の照合 | 2.3 の C（`Origin` が許可したもの以外の発行をブロック） | 2章 |

### 4.3 入れるときの注意

- **画像のアップロードが止まらないようにする**: Core rule set の `SizeRestrictions_BODY` は 8KB を超えるボディをブロックするので、発行の2つのルートでは外す（Count にして、ほかのパスだけブロックする）。何もしないと、すべての発行が 403 になる
- ボディの検査は先頭 16KB（最大 64KB）だけ。画像の中身は守れないので広げない。画像のバイト列がボディを検査するルールに誤って当たらないか、実際の写真で確かめる
- 最初はブロックせずに数えるだけ（Count）で入れ、ログで誤検知がないことを確かめてから止める
- 携帯回線や会社のネットワークは、多くの利用者が同じ IP を使う。IP ごとの制限を小さくしすぎない
- 止めたときの応答は 403（CloudFront の HTML）。今の SPA は「発行できませんでした。もう一度お試しください」と出す
- 費用（目安）: Web ACL 月 5 USD、ルール 1 つ月 1 USD、リクエスト 100 万件あたり 0.60 USD

| 13.2 作る（AWS CLI） | ルールの JSON と `aws wafv2 create-web-acl` のコマンド（us-east-1、スコープ CLOUDFRONT、ボディの検査は 16KB） |
| 13.3 CloudFront に付ける・外す | `web.yaml` の `WebAclArn` を付けてデプロイする |
| 13.4 ログ | `aws-waf-logs-` で始まるロググループへの出力と、ブロックの見方 |

## 5. まとめて入れる場合（推奨の形）

Go の発行の API の入り口で、次の2つを順に確かめる。

| 順 | 確かめること | 違うとき |
|---|---|---|
| 1 | 秘密のヘッダー（`X-Origin-Verify`）が、Parameter Store の値（入れ替え中は新旧のどちらか）と一致するか | 403（CloudFront を通っていない） |
| 2 | `Origin` があれば、許可したオリジン（`ALLOWED_ORIGINS`）のどれかか | 403（ほかのサイトから送られた） |

作業:

- Go: 確かめる処理（発行の2つのルート。QR 画像・チケットの画面にも 1 を入れるかは決める）、設定の読み込み、テスト
- テンプレート: `api.yaml`・SAM に `AllowedOrigins` と、秘密の値のパラメータ名。`web.yaml` の API のオリジンに `OriginCustomHeaders`
- 手順書: 秘密の値の作り方と入れ替え、確かめ方（直接呼ぶと 403、CloudFront 経由なら通る、ほかの `Origin` なら 403）
- SPA は変えなくてよい（同じオリジンからの送信には、ブラウザが正しい `Origin` を付ける）

## 6. 決めること

1. Origin の照合を入れるか。入れるなら、どこで行うか（A: Go / B: CloudFront Functions / C: WAF）
2. CloudFront を通らないアクセスを防ぐか。防ぐなら、方法（1: 秘密のヘッダー / 3: Lambda の認可の関数）
3. 入れる時期（WAF の判断と合わせるか、先に入れるか）
4. `Origin` がないリクエストを通すか（推奨: 通す）
5. WAF を入れるか。入れるなら、ルール（web/DEPLOY.md 13.1 の案でよいか）、IP ごとのレート制限の値、テンプレートにするか（us-east-1 の別のテンプレート）か AWS CLI で作るか
