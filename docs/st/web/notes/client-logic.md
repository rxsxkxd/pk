# SPA の判定・確認のロジックと、発行方式の間での共通化

> 2026-10-10 調査（発行方式をビルド時に選ぶ形にした後の `web/src`）。決めること: 5章・6.3。

## 1. 結論

- 複雑なロジックはほとんどない。分岐の多い処理は2章の5つで、どれも数行〜十数行（`web/src` 全体で 約 850 行）
- 画面遷移方式（`page`）とその場表示方式（`inline`）の間では、5つとも共通化されている
- フォーム送信方式（`form`）は、対応する形式のリスト（`ACCEPT`）以外は使っていない。そのため、form では **Android でカメラを選べない**、**送る前に大きさと形式を確かめない**（4章）

## 2. 判定・確認のロジック

| 処理 | 場所 | 中身 | 規模 |
|---|---|---|---|
| ブラウザの判定とボタンの出し分け | `src/platform.ts`（`isAndroid`）、`src/components/CertificateImagePicker.vue` | 判定は Android かどうかだけ。User-Agent Client Hints の `platform` が `Android`、または User-Agent に `Android` を含めば Android とみなす。Android なら「画像を選ぶ」「カメラを起動」（`capture` 付き）の2つのボタン、それ以外は選択欄1つ | 判定 3 行、出し分けは `v-if` 1つ |
| 送る前の画像の確認 | `src/stores/ticket.ts`（`checkFile`） | 未選択 → 大きさ（`config.json` の `maxImageBytes` を超えるか）→ 形式（MIME タイプか拡張子のどちらかが対応する形式か）の順に見て、最初の問題の文言を返す | `if` 3つ |
| エラーの文言 | `src/stores/ticket.ts`（`messageFor`） | API のエラーコードを画面の文言に変える `switch`（6つのコードと「その他」） | 対応表のみ |
| 送信中の状態 | `src/stores/ticket.ts`（`canSend`・`send`） | 送れる条件（画像に問題がなく、送信中でない）と、送信中・成功・失敗の状態の切り替え。二重送信の防止もここ | 十数行 |
| 応答の解釈 | `src/api/client.ts`（`postImage`） | 通信の失敗は `NETWORK`、201 は方式ごとの形（zod）で確かめる、それ以外は API のエラーの JSON として読む、どちらにも合わなければ `UNEXPECTED` | 十数行 |

ほかには、正規表現による形の確認（チケットコード・署名・チケット画面の URL・`config.json`）と、日時の表示用の整形があるだけ。

入っていないもの:

- OS やブラウザのバージョンによる判定、機能の有無による切り替え、ポリフィル
- 画像の加工（縮小・圧縮・HEIC の変換・向きの補正）。画像はそのまま送る
- 画像の中身の確認。形式は拡張子と MIME タイプで目安として見るだけで、最終的な判定は API が行う

## 3. 発行方式の間での共通化

| 処理 | page | inline | form |
|---|---|---|---|
| Android の判定とボタンの出し分け（`CertificateImagePicker`） | 共通 | 共通 | **使わない**（ふつうの選択欄1つ） |
| 送る前の画像の確認（`checkFile`） | 共通 | 共通 | **使わない**（未選択だけ、ブラウザの `required` で止まる） |
| エラーの文言（`messageFor`） | 共通 | 共通 | 使わない（エラーは API の HTML のエラーページ） |
| 送信中の状態・二重送信の防止（ストアの `send`） | 共通 | 共通 | 使わない |
| 応答の解釈（`postImage`） | 共通 | 共通 | 使わない（`fetch` しない） |
| 対応する形式のリスト（`ACCEPT`） | 共通 | 共通 | 共通 |

- `page` と `inline` の発行画面（`src/modes/{page,inline}/GrantPage.vue`）で方式ごとに違うのは、送ったあとの処理だけ（`page` はチケット画面に移る、`inline` は結果をその画面に出す）
- form は `fetch` を使わず、ブラウザがフォームをそのまま API に送る。送信中の状態・応答の解釈・エラーの文言は、SPA の側には持てない（結果もエラーも API の画面に出る）

## 4. form の不足

送る前の SPA 側の処理なので、次の2つは form でも共通化できる。

| 不足 | 影響 |
|---|---|
| Android のカメラ | Android 14 以降は、`accept` が画像のふつうの選択欄だとフォトピッカーになり、カメラを選べない。form には「カメラを起動」のボタンがないので、Android ではその場で撮って送れない |
| 送る前の確認 | 大きさと形式を確かめずに送る。上限を超えた画像も送り、API の 413 のエラーページ、または API Gateway のエラー（JSON。web/DEPLOY.md 12章）がそのまま画面に出る |

今の form は、以前の設計（「送信前の確認はせず、API に任せる」）のまま。

form に共通部品を使う場合の作業:

- `CertificateImagePicker` の選択欄を、フォームの項目（`name="image"`）として使えるようにし、form の発行画面で使う
- Android では選択欄が2つ（「画像を選ぶ」「カメラを起動」）になるので、選ばれたほうだけがフォームで送られるようにする（例: 選ばれなかったほうの値を空にする、または `name` を選ばれたほうにだけ付ける）
- 送る前の確認（`checkFile`）に問題があれば、送信ボタンを押せないようにする（`page`・`inline` と同じ）
- テスト（`test/modes/form.test.ts`）に、Android の2つのボタンと、送る前の確認を足す

## 5. 決めること・気づいた点

| 項目 | 内容 |
|---|---|
| form に共通部品を使うか | form を本番で使う予定があれば、使うことを勧める（4章）。使わないなら、Android のカメラの制約を form の制限として手順書・設計書に書いておく |
| 大きさの表示の関数が2つある | `CertificateImagePicker.vue` の `formatSize`（選んだ画像の大きさの表示。MB は小数1桁に四捨五入、KB は切り上げ）と、`stores/ticket.ts` の `sizeLabel`（上限の表示「…（4MB まで）」。どちらも切り捨て）。丸め方が違うので、近い値で表示がずれることがある（例: 上限 2.05MB は「2MB まで」、2.04MB の画像は「2.0MB」と出て送れる）。1つにまとめるとよい |

## 6. さらに減らせるか（ライブラリへの置き換え・仕様の変更）

結論: npm のライブラリに置き換えても、コードはほとんど減らない（6.1）。複雑さを実際に減らせるのは、仕様を変えてロジックそのものをなくす方向で、候補は 6.2 の3つ。減らすなら A（端末の判定をなくす）がいちばん効果があり、form の不足（4章の Android のカメラ）の対策にもつながる。B と C は、使い勝手や API との分担が変わるので、仕様として決める（6.3）。

### 6.1 ライブラリへの置き換え（どれも勧めない）

| 処理 | 置き換えの候補 | 減る量 | 判断 |
|---|---|---|---|
| Android の判定（`platform.ts`、3 行） | `ua-parser-js`、`bowser` | 3 行 | 3 行が依存1つに変わるだけ。User-Agent の解析の全体を持ち込むので、容量が増える |
| 大きさの表示（`formatSize`・`sizeLabel`） | `pretty-bytes`、`filesize` | 数行 | 丸め方のずれ（5章）は直るが、自前の関数を1つにまとめれば済む。`pretty-bytes` は既定で 1000 単位（MB = 10^6）なので、API の上限（4 × 2^20）と表示を合わせるには設定が要る |
| 送信中の状態・二重送信の防止（ストアの `send`、十数行） | TanStack Query（`@tanstack/vue-query`）の `useMutation`、VueUse の `useAsyncState` | 十数行 | 状態（送信中・失敗）を持つ部分は減るが、ライブラリの考え方（キャッシュ、再試行の既定値など）を覚え、設定で打ち消す必要がある。この規模では割に合わない |
| 応答の解釈（`postImage`、十数行） | `ofetch`、`ky` | 数行 | タイムアウトと「2xx 以外は例外」は任せられる。API のエラーコード（`ApiError`）への変換と、zod での形の確認は残る |
| 形の確認（zod） | - | - | すでにライブラリ。201 の応答の確認をやめる（API を信じる）こともできるが、画面が想定外の値を扱わないための防御なので残す |

共通の注意: ライブラリを足すほど、iOS 13 への対応（../DESIGN.md 2.4）が難しくなる。依存先が iOS 13 にない組み込みの機能（`Array.prototype.at`、`Object.hasOwn`、`structuredClone` など）や新しい構文を使っていないかを、ライブラリごとに確かめる必要がある（構文はビルドで変換できるが、組み込みの機能は変換されない）。

### 6.2 仕様を変えて、ロジックをなくす

#### A. どの端末でも2つのボタン（「画像を選ぶ」「カメラを起動」）を出す

| 項目 | 内容 |
|---|---|
| なくなるもの | 端末の判定（`src/platform.ts`）、`CertificateImagePicker.vue` の出し分け（`v-if`）、`test/platform.test.ts` と出し分けのテスト |
| 端末ごとの動き | Android: 今の Android の画面と同じ。iOS: 「画像を選ぶ」でも、選択欄のメニューから写真・カメラ・ファイルを選べる。「カメラを起動」はカメラを直接開く（`capture` は iOS の Safari でも効く）。PC: `capture` が効かないので、「カメラを起動」もふつうのファイル選択になる |
| 引き換え | PC に「カメラを起動」が出る（押してもファイル選択になる）。iOS ではボタンが1つ余分になる（どちらからもカメラを使える） |
| ほかの効果 | 端末によって画面が変わらないので、説明や問い合わせの対応が簡単になる。form にも同じ部品を使いやすくなる（4章） |
| 作業 | `platform.ts` と `v-if` を消し、2つのボタンの形だけを残す。テストは「どの端末でも2つのボタン」に変える。../DESIGN.md 3章（証明書の画像の選択）を直す |

#### B. 送る前の形式の確認をやめる（大きさの確認は残す）

| 項目 | 内容 |
|---|---|
| なくなるもの | `checkFile` の形式の確認（拡張子のリスト `EXTENSIONS` と、MIME タイプとの照合）と、そのテスト |
| 代わりに防ぐもの | 選択欄の `accept`（`ACCEPT`）。多くの端末では、対応しない形式をはじめから選べない |
| 引き換え | `accept` を無視する端末や、「すべてのファイル」から選んだ場合は、送ってから API の 415（「この形式の画像には対応していません」）で分かる（送る時間がかかる） |
| 大きさの確認を残す理由 | 上限を大きく超えると、Lambda まで届かず API Gateway のエラーになり、SPA で文言を出し分けられない（web/DEPLOY.md 12章）。送る前に止めるほうが確実 |
| 作業 | `checkFile` から形式の確認を消す。テストと ../DESIGN.md 3章・4.4 を直す |

#### C. エラーの文言を API に持たせる

| 項目 | 内容 |
|---|---|
| 中身 | API のエラーの `message` を、利用者に見せる日本語の文言にする（今は英語の説明）。SPA はそれをそのまま出す |
| なくなるもの | `messageFor` の対応表のほとんど（API のエラーコードごとの文言） |
| SPA に残るもの | 通信エラー・タイムアウト・想定外の応答（`NETWORK`・`UNEXPECTED`）の文言、送る前の確認の文言（`checkFile`） |
| 引き換え | 文言を変えるたびに、API（Go・Node の両方）を変えてデプロイする必要がある。API の `message` は今はログや開発者向けの説明も兼ねているので、利用者向けの文言を別の項目（例: `userMessage`）にするかも決める。上限の文言（「…（4MB まで）」）は API の `MAX_IMAGE_BYTES` から作ることになる |
| ほかの効果 | form 方式で出る API のエラーページと、SPA の文言をそろえやすくなる |
| 作業 | API（Go・Node）のエラーの文言、共通のテストデータ、../../DESIGN.md のエラーコードの表、SPA の `messageFor` とテストを直す |

### 6.3 決めること

| 項目 | 選択肢 |
|---|---|
| A | どの端末でも2つのボタンにするか、今の出し分け（Android だけ2つ）を続けるか |
| B | 送る前の形式の確認をやめるか、続けるか |
| C | エラーの文言を API に持たせるか、SPA に持ち続けるか |
| 大きさの表示 | `formatSize` と `sizeLabel` を1つにまとめるか（5章。ライブラリは使わず、自前の関数で） |
