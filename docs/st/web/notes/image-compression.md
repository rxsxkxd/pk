# 【一時メモ】ブラウザ側での画像の圧縮: ライブラリの比較

> 一時的な検討メモ（2026-10-06。1.1・6.1・7章の方針は 2026-10-12 に追記）。**方針（案）は 7章の冒頭**。方針が決まったら [../DESIGN.md](../DESIGN.md) に反映し、このファイルは削除する。実装はしていない。数値は npm と GitHub の公開情報、ライブラリの README からの調査で、実機での計測はしていない。

## 1. 背景: 今の前提が変わる

今の設計は「写真は加工せず、そのまま送る」（パススルー）。進み具合（[upload-progress.md](upload-progress.md)）を検討していたのも、この前提で写真が大きいまま送られるため。ブラウザで圧縮すると、次のことが変わる。

| 項目 | パススルー（今） | ブラウザで圧縮 |
|---|---|---|
| 送るサイズ | 写真のまま。iOS が JPEG に変換した写真は 4MB の上限を超えることがある | 数百KB〜1MB 程度にできる（長辺と画質の設定しだい） |
| 送信の時間・進み具合 | 長くなりやすく、進み具合がほしい | 短くなり、進み具合の必要性は下がる |
| 画像解析サーバーに届くもの | 撮った写真そのもの（HEIC / AVIF / WebP なども） | ブラウザが作り直した JPEG（解像度と画質が落ちる） |
| EXIF（位置情報など） | そのまま届く | 既定では消える（プライバシーの面では利点） |
| ブラウザの負担 | なし | 写真をデコードして描き直す（古い端末では数百ミリ秒〜秒単位。未計測） |

- **最初に決めること**: 画像解析サーバーが、圧縮した画像で十分か（必要な解像度、形式、EXIF の要否）。DESIGN.md 7章の「画像の中身はパススルー」と、web/DESIGN.md の「画像の縮小・変換ライブラリは採用しない」を変えることになる
- 圧縮に失敗したとき（デコードできない、メモリ不足など）は、**元の写真をそのまま送る**ようにすれば、今の動きより悪くはならない

### 1.1 4MB の上限を超えやすい端末（2026-10-12 追記）

圧縮が要るかどうかは、実際の写真が上限（4MB。../../DESIGN.md 5章）をどれだけ超えるかで決まる。見込みとしては、**超えやすいのは高画素のカメラを持つ新しい端末**で、古い端末（8〜12MP）は収まりやすい。ただし、iPhone の写真が JPEG で渡される場合は、古い端末でも超えることがある。

下の値は一般的な目安（12MP 前後の写真1枚）。このプロジェクトで実機を測ったものではない。

| 端末 | 標準の写真 | 送られる形式 | 大きさの目安 | 4MB を超えるか |
|---|---|---|---|---|
| iPhone（iOS 11 以降、12MP。iPhone 7〜14 の多く） | HEIC | HEIC のまま | 1〜3MB | ほぼ超えない |
| 同上 | HEIC | JPEG に変換されて渡される場合 | 2〜5MB | **超えることがある** |
| iPhone（「互換性優先」の設定、または iOS 10 以前） | JPEG | JPEG | 2〜5MB | 超えることがある |
| iPhone 15 以降（標準 24MP） | HEIC | HEIC / JPEG | 3〜5MB / 6〜10MB | **超えやすい**（JPEG なら多くが超える） |
| Android の古い端末（Android 9 のころ、12〜16MP） | JPEG | JPEG | 2〜5MB | ときどき超える |
| Android の高画素の端末（48〜200MP。標準は画素をまとめて 12MP 前後で保存） | JPEG | JPEG | 3〜6MB | 超えることがある |
| 同上で、高画素モードで撮った写真 | JPEG | JPEG | 10〜30MB | **必ず超える** |

大きさを左右するもの:

- **画素数**: 古い端末は 8〜12MP が多く、1〜4MB に収まりやすい。24MP 以上で標準保存する新しい端末が超えやすい
- **形式**: 同じ写真でも、HEIC は JPEG の半分ほどの大きさ。SPA の選択欄は HEIC を受け付ける（`accept` に `image/heic`）ので、iOS は HEIC のまま渡すと見込んでいる。ただし、iOS が HEIC のまま渡すか JPEG に変換するかは条件によって違い、実機で確かめていない（4.1）。JPEG で渡されると、古い iPhone でも超えることがある
- **写っているもの**: 証明書は白地と文字が多く、風景などの写真より小さくなりやすい
- **その場で撮るか、選ぶか**: Android の「カメラを起動」で撮った写真は、カメラアプリの設定（解像度・画質）のまま保存される

確かめる方法（未実装）:

- 今の API の完了ログ（`"msg":"request completed"`）には、端末の情報（`client`。User-Agent など。../../DESIGN.md「ブラウザと OS の記録」）は残るが、**画像の大きさと形式は残していない**
- 完了ログに、受け取った画像の大きさ（バイト数）と、API が判定した形式を足せば、検証環境や本番で端末ごとの大きさの分布と、413 の出ている端末が分かる。足すのは Go・Node のログの項目2つで、画像の中身は出さない
- この分布で、圧縮が要るか（7章の 1）と、上限を超える割合を判断できる

| 観点 | Compressor.js | browser-image-compression | image-blob-reduce |
|---|---|---|---|
| 保守 | 2026年に2回リリース。課題が少ない | 2023-03 から更新なし。未解決の課題が多い | 2026年に更新（pica も） |
| サイズ | **最小（約4.7KB）** | 約20KB | 約24KB |
| 書き方 | コールバック（`new Compressor(file, { success, error })`。Promise にするには包む） | **Promise**（`await imageCompression(file, options)`） | Promise（`await reduce.toBlob(file, { max })`） |

| 写真の向き（EXIF） | `checkOrientation`（既定で有効） | `exifOrientation` | JPEG の向きを適用する |
| EXIF の扱い | 既定で消す（`retainExif` で残せる） | 既定で消す（`preserveExif` で残せる） | **既定で残す**（位置情報も残るので、消すには差し替えが要る） |

## 4. どのライブラリでも共通の課題

### 4.1 HEIC（iPhone の写真）

- ブラウザで圧縮するには、まずブラウザが写真をデコード（`<img>` や `createImageBitmap`）できる必要がある
- Safari が HEIC をデコードできるのは **iOS 17 から**。iOS 13〜16 と、Android の Chrome は HEIC をデコードできない
- 対策の候補:
  - **`<input>` の `accept` から `image/heic` を外す**: iOS は、写真を選んだときに JPEG に変換して渡すとされる（実機で要確認）。圧縮するなら、こちらの方が確実
  - デコードできない写真は、**圧縮せずにそのまま送る**（API は HEIC を受け付けるので、今と同じ動きになる）
  - heic2any で JPEG にする: 大きく（約2.7MB）、更新も止まっているので、使わない方向

### 4.2 iOS の canvas の上限

- Safari は、1つの canvas が 16,777,216 ピクセル（4096×4096）を超えると描けない。canvas の合計のメモリにも上限がある（iOS 15 で 384MB。古い iOS や端末ではもっと小さい）。超えると、真っ白な画像になったり、エラーになったりする
- 12MP（4032×3024）の写真はぎりぎり収まるが、48MP の写真は収まらない。**長辺を 4096 以下（実用的には 2048〜2560 程度）に縮める**設定にする

### 4.3 そのほか

- 写真の向き: 新しいブラウザは描くときに EXIF の向きを自動で適用する。ライブラリの向きの処理と二重にならないかを、実機で確かめる
- 処理時間: Android 9 の古い端末では、デコードと描き直しに時間がかかる可能性がある（未計測）。Web Worker を使えるライブラリなら、画面は止まらない
- 圧縮の結果が元より大きくなる場合（すでに小さい写真など）は、元の写真を送る

## 5. Vue 3.5 / 3.6 と TypeScript 7 との相性

### 5.1 Vue

- 3候補とも、Vue に依存しない（`File` を受け取って、縮めた `Blob` / `File` を返すだけ）。Vue の版に関係なく使え、Vue 3.5 から 3.6 に上げても影響しない
- Vue 3.6 は、2026-10-06 時点で RC（`3.6.0-rc.10`、2026-09-30）。正式版は 3.5.43。3.6 の大きな変更（Vapor モードなど）は描画の仕組みの話で、これらのライブラリの使い方には関係しない
- 組み込み方は、ストア（Pinia）の送信の前に、圧縮の関数を1つはさむだけ。Vue のコンポーネントのラッパーは要らない
- Web Worker を使う場合のファイルの置き方（Vite）: pica（image-blob-reduce）は分割ビルドの `pica_worker.js` を `new URL('pica/dist/pica_worker.js', import.meta.url)` で自分のサイトから読める。browser-image-compression は `libURL` に自分のサイトのファイルを指定する（既定は CDN）

### 5.2 TypeScript 7

各ライブラリの使い方の例（圧縮して `Blob` / `File` を受け取るコード）を、TypeScript 6.0.3（web が今使っている版）と 7.0.2 で型チェックした（`strict`、`verbatimModuleSyntax`、型定義のチェックも有効）。

| | `moduleResolution: bundler`（web の設定） | `moduleResolution: nodenext`（ESM） |
|---|---|---|
| Compressor.js | TS 6・7 とも問題なし | TS 6・7 とも問題なし |
| browser-image-compression | TS 6・7 とも問題なし | TS 6・7 とも型エラー（既定のエクスポートが呼び出せない型になる） |
| image-blob-reduce | TS 6・7 とも問題なし | TS 6・7 とも型エラー（pica の型が解決できない） |

- **TypeScript 6 と 7 で結果は同じ**だった。TypeScript 7 に上げても、これらのライブラリの型で新しく困ることはない
- `nodenext` の型エラーは、パッケージの型定義の作り方の問題（TypeScript の版とは関係ない）。web は Vite の `bundler` 設定なので、今は影響しない
- 型定義の作りが最も素直で、設定に左右されないのは Compressor.js
- web を TypeScript 7 に上げられない理由は、これらのライブラリではなく **vue-tsc**（Vue のテンプレートの型チェック）。vue-tsc 3.3.12 は TypeScript 7 では起動しない（web/DESIGN.md 2章で TS 6 に固定した理由）。vue-tsc が TypeScript 7 に対応すれば、どの候補を選んでも、そのまま上げられる

## 6. 評価（案）

| 重視すること | 向いている候補 |
|---|---|
| 小さく、保守が続いていて、単純。TypeScript 7 でも型が素直に使える | **Compressor.js** |
| ファイルサイズの上限を確実に守る（`maxSizeMB`）、`AbortSignal`、圧縮の進み具合 | browser-image-compression（ただし 2023 年から更新がない点と、CSP のための設定が要る点に注意） |
| 縮小の画質（画像解析の精度に効く可能性）、画面を止めない処理 | image-blob-reduce（ただし既定で EXIF を残すので、位置情報を消す処理を足す） |

- **第一候補は Compressor.js**: 4.7KB と最小で、2026 年にも更新されている。今回の用途（長辺を 2048 程度に縮めて JPEG にする）なら、必要な機能はそろっている。型定義の作りも素直で、TypeScript 6・7 のどちらでも、どの設定でも問題がない。メインスレッドで動くが、写真1枚なら許容できる見込み（実機で確かめる）
- 画像解析の精度のために縮小の画質を重視するなら、image-blob-reduce を比べる
- browser-image-compression は利用者が最も多く、機能も多いが、2023 年から更新が止まっていて未解決の課題も多いので、長く使う前提では選びにくい

### 6.1 Compressor.js の依存と、説明のしかた（2026-10-12 追記）

Compressor.js（1.4.0）を入れると、npm の依存が3つ増える（本体と、`is-blob`・`blueimp-canvas-to-blob`）。依存の説明を求められたときに、1つずつ調べ直さなくて済むように、ここにまとめる。

確かめたこと（compressorjs 1.4.0 の中身）:

- npm が読み込むのは `dist/` のファイル（`package.json` の `main` / `module` / `browser`）
- `dist/` のファイルには、2つの依存の中身がすでに組み込まれていて、`import` も `require` もない。**2つは `node_modules` に入るだけで、SPA のビルドには使われない**
- 2つとも、さらに依存を持たない小さなパッケージ（MIT ライセンス）
- `dist/` は古い書き方の JavaScript（アロー関数・`const` なし）。Web Worker、`eval`、`new Function` は使わない
- 大きさ: 本体と組み込み済みの依存を合わせて、約 4.8KB（minify + gzip）

| パッケージ | 中身 | 最終更新 | 実行時に使われるか | 今回の対象ブラウザで要るか |
|---|---|---|---|---|
| `compressorjs` | 写真の縮小・JPEG への変換・向きの補正・EXIF の除去 | 2026-10 | 使われる（`dist/` の1ファイル） | 要る |
| `is-blob` | 値が `Blob` かを確かめる関数（数行） | 2023-06 | 使われない（同じ処理が `dist/` に組み込み済み） | 要らない |
| `blueimp-canvas-to-blob` | `canvas.toBlob` がない古いブラウザ向けの代わり（143 行） | 2022-06 | 使われない（同じ処理が `dist/` に組み込み済み） | 要らない（`toBlob` は Safari 11・Chrome 50 から） |

依存の数を減らす案:

| 案 | npm の依存 | 説明すること | 引き換え |
|---|---|---|---|
| **A. そのまま入れる**（推奨） | 3つ | 下の説明の文だけ | 使われない2つが `package-lock.json` に載る。2つとも更新が止まっていて、さらに依存も持たないので、変わる心配は小さい |
| B. 本体の `dist/` の1ファイルを取り込む（例: `src/vendor/compressor.esm.js` と型定義。版とライセンスの表示を残す） | 0 | なぜ取り込んだか、どう更新するか | 版を上げるときは、ファイルを手で差し替える。脆弱性の通知（`npm audit` など）が届かなくなるので、自分で追う |
| C. 自前で書く（約 50 行） | 0 | 自前の処理の中身 | 写真の向きを自前で扱う。iOS 13.4 以降と Chrome 81 以降は描画のときに向きを自動で直すが、iOS 13.0〜13.3 は直さないので、そこで写真が横向きになる。Compressor.js はこの処理を引き受けている |

- 説明の手間が最も少ないのは A。B と C は依存は減るが、「なぜ取り込んだ（書いた）か」「どう保守するか」の説明が別に要る

使わない2つだけを npm の設定で外せるか（2026-10-12 に試した。npm 11.20.0）:

| 方法 | 結果 |
|---|---|
| npm の `overrides` で、2つを空のパッケージ（`file:./stub`）に差し替える | 入るのは空のパッケージになるが、`npm ls` が「invalid」のエラーを出す（CI で `npm ls` を使うと失敗する）。`package-lock.json` には名前が残る。差し替えの理由の説明も要るので、かえって説明が増える |
| npm の設定で、依存先の依存だけを外す | npm にはその機能がない（`--omit` で外せるのは dev・optional・peer の依存だけ） |
| （参考）pnpm の `overrides` で `"-"` を指定する | pnpm なら依存先の依存を外せる。この SPA は npm を使っているので、パッケージマネージャーを変えることになる |
| Compressor.js 側で直す（2つを `devDependencies` に移す） | 本来の直し方。`dist/` に組み込み済みなので、利用者の依存に入れる必要はない。作者は活動している（2026-10-01 にも変更を取り込んでいる）が、この件の課題や PR はまだない。提案するなら GitHub の課題で。取り込まれるかと時期は分からない |

- npm のまま、きれいに外す方法はない。依存を0にしたいなら B（1ファイルを取り込む）。Compressor.js に提案して、取り込まれたら A に戻す、という進め方もできる
- 依存の一覧を確かめるときは `npm ls --prefix web compressorjs`（本体の下に2つが並ぶ）

説明の文（そのまま使える）:

> 画像の圧縮に Compressor.js（compressorjs、MIT）を使っています。npm の依存は3つに見えますが、`is-blob` と `blueimp-canvas-to-blob` は Compressor.js の依存として入るだけで、実行時には使われません（Compressor.js の配布ファイル `dist/` に同じ処理が組み込み済みで、そこから読み込まれることはありません）。2つともさらに依存を持たない小さなパッケージ（MIT）です。Compressor.js 自体も、Web Worker や `eval` を使わず、ビルド後の大きさは約 4.8KB です。

## 7. 方針（案）と決めること

### 7.1 方針（案。2026-10-12）

**Compressor.js をそのまま入れ（6.1 の A）、上限を超えた写真だけを圧縮する。** 上限以下の写真は、今までどおり加工せずに送る。

この形にする理由:

- 上限を超えた写真は、今は送れない（送る前に止めるか、API の 413）。そのときだけ圧縮するので、**今送れている写真の扱いは何も変わらない**（パススルーのまま。画像解析の結果も変わらない）
- 圧縮に失敗しても、今と同じ「画像のサイズが大きすぎます」になるだけで、今より悪くならない
- 画像解析サーバーが「縮めた写真」で足りるかの確認（下の決めること 1）は、上限を超えた写真だけの話になる。確認の結果が出る前でも、「送れない」よりはよい

処理の流れ（画面遷移方式・その場表示方式。共通の部分に置く）:

| 場面 | 動き |
|---|---|
| 写真を選んだとき | 形式の確認（今と同じ）。大きさが `maxImageBytes` 以下なら、そのまま（今と同じ） |
| 上限を超えているとき | 選んだときに圧縮する（「画像を縮小しています…」と出し、その間は送れない）。縮んだら、縮んだ写真を送る対象にし、「縮小しました（5.2MB → 2.8MB）」のように出す |
| 圧縮しても上限を超えたとき・失敗したとき（デコードできない HEIC など） | 「画像のサイズが大きすぎます（4MB まで）」（今と同じ文言）。送れない |

圧縮の設定（案。上限に収まるまで順に試す）:

| 試す順 | 長辺の上限 | 画質 | 理由 |
|---|---|---|---|
| 1 | 4096 | 0.9 | 解像度をなるべく保つ（証明書の文字を読めるように）。4096 は iOS の canvas の上限（4.2）。12MP の写真（長辺 4032）は縮めずに画質だけ下げる |
| 2 | 4096 | 0.8 | |
| 3 | 3072 | 0.8 | |
| 4 | 2048 | 0.8 | ここでも超えれば諦める（「大きすぎます」） |

- 出力は JPEG。EXIF は消える（Compressor.js の既定）。上限以下でそのまま送る写真は、今までどおり EXIF が残る
- 写真の向きは、Compressor.js の `checkOrientation`（既定）に任せる。新しいブラウザの自動の補正と二重にならないかは、実機で確かめる（4.3）

使えない方式・注意:

- **フォーム送信方式（`form`）では使えない**。ブラウザがフォームをそのまま送るので、送る前に写真を差し替えられない（../notes/client-logic.md 4章）。form では、上限を超えた写真は今までどおり API のエラーになる
- **CSP**: Compressor.js は写真を読むときに `blob:` の URL を `<img>` に入れることがある。CloudFront の CSP の `img-src` に `blob:` を足す（`web.yaml`、web/DEPLOY.md 4章の `headers.json`、../DESIGN.md 9章）
- **HEIC**: デコードできない端末（iOS 16 以前、Android の Chrome）で上限を超えた HEIC は、圧縮できず「大きすぎます」になる（今と同じ）。ただし HEIC は小さいので、上限を超えることは少ない（1.1）
- **テスト**: Vitest（happy-dom）には canvas がないので、圧縮の部分は差し替えて、流れ（試す順・諦める条件・文言）を単体テストする。実際の圧縮は E2E（Playwright の Chromium）か実機で確かめる

作業（実装するとき）:

- `npm --prefix web install compressorjs@1.4.0`（版は固定）
- 共通の部分に圧縮の処理を足す（例: `src/image/shrink.ts`。上の試す順と、諦める条件）。ストアは、選んだ写真が上限を超えていれば圧縮し、縮んだ写真を送る対象にする。状態に「縮小中」を足す
- 画像の選択の部品（`CertificateImagePicker`）に、縮小中・縮小の結果の表示を足す
- CSP（`img-src` に `blob:`）、テスト、../DESIGN.md（2章の「採用しないもの」、3章、5章、9章）、../../DESIGN.md 7章（「画像の中身はパススルー」に、上限を超えた写真だけはブラウザで縮める、と足す）
- 説明を求められたときは 6.1 の説明の文を使う

### 7.2 決めること

0. 実際の写真の大きさを測るか（1.1 の「確かめる方法」。API の完了ログに画像の大きさと形式を足す）。1 の判断材料になる
1. ブラウザで圧縮するか（パススルーの方針を変えるか）。**→ 方針（案）: 上限を超えた写真だけ圧縮する（7.1）**。画像解析サーバーが、縮めた写真（JPEG、長辺 2048〜4096）で足りるかは確かめる
2. 圧縮の設定。**→ 案: 7.1 の試す順**（長辺 4096・画質 0.9 から、長辺 2048・画質 0.8 まで）。出力は JPEG
3. HEIC の扱い: `accept` から `image/heic` を外すか。デコードできない写真は、そのまま送るか
4. 失敗したとき・圧縮して大きくなったときは、元の写真を送るか。**→ 上限を超えた写真だけを圧縮するので、元の写真は送れない。「大きすぎます」を出す（今と同じ）**
5. EXIF（位置情報）を消すか。**→ 圧縮した写真は消える（Compressor.js の既定）。そのまま送る写真は今までどおり残る**。そのまま送る写真の EXIF も消すかは、別に決める（消すには、上限以下の写真も描き直すことになり、パススルーではなくなる）
6. ライブラリ。**→ Compressor.js を、そのまま npm で入れる（6.1 の A）。2026-10-12 に方向を決めた**
7. 圧縮するなら、アップロードの進み具合（upload-progress.md）はやめるか。上限以下の写真は今までどおり大きいまま送るので、進み具合の必要性はあまり変わらない
