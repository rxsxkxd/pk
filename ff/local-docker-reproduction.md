# 取得済みDocker資材によるローカル再現範囲

確認日：2026-11-13

対象：[システム構成と段階的なECS移行方針](./README.md)、[元の構成図](./a.svg)

> 本書は構築前の調査記録。後続の構築内容・起動手順は[Docker構成](./docker/README.md)、追加取得物と実測結果は[依存関係・検証報告](./docker/dependency-report.md)を参照。ローカル実装は2テナント分とし、Go Worker / BatchはGo Backgroundと呼ぶ。RailsはDBへ直接接続せず、PythonとGo BackgroundをInfrastructure層の実装として利用する。Go APIは直接DB参照とPython経由を使い分ける。Go BackgroundはRailsやPythonで重い処理を担い、Infrastructure層の役割も一部担う。

> 最新方針：DB 1 / DB 2は、各テナントの同一MySQLインスタンス内の別DB。Go API・Go Background・Pythonはいずれも両方にアクセスする。結合の主経路はPythonのSQLAlchemyによるORM JOINとし、性能重視の経路はGoのSQL直書きJOINを使う。以下の初回調査時点の別コンテナ案は、現行実装ではテナントごとにMySQL 1台へ統合している。

## 1. 判定

**取得済みイメージを使い、旧App・テナント別DB・共通サービスの接続と、旧環境の公開経路を閉じる動作をローカルで検証できる見込みがある。ただし、現在のコンテナを起動するだけでは構成図全体を再現できない。**

旧Appに近い実行環境と、Rails・Go・Python・MySQLのイメージは存在する。一方、アプリコード、DBのスキーマ・データ、テナント切替、サービス間連携、公開入口と内部ネットワークの構成は追加または復元が必要である。

本書は、Dockerの一覧・設定とローカルの定義ファイルを読み取り確認した結果を記録する。コンテナの起動、疎通、業務処理、負荷、分離動作は今回実行していない。「再現可能」は資材を利用した構築の見込みであり、動作確認済みを意味しない。

### 2.2 既存コンテナとコードの配置

- 確認した既存コンテナはすべて停止中だった。
- Rails系には終了コード1のコンテナがある。終了原因は今回調査していない。
- Go・Python・Railsの既存コンテナには、ホスト側のアプリコードを`/app`へバインドマウントする設定がある。
- 参照元の`/Users/ryo/Documents/workspace/sandbox/multiapp/`は確認時点で存在しなかった。
- したがって、イメージが存在していても、元のアプリをそのまま再起動できるとは判断できない。コードの復元または検証用コードへの差し替えが必要になる。
- 依存ライブラリ用のボリュームは設定上確認できたが、内容は未確認。起動時の`bundle install`や`pip install`が、追加ダウンロードなしで完了するかも未確認である。

### 2.3 既存ネットワーク

`al2-instance_default`、`gym_default`、`ec_default`、`ticketing_default`などのネットワークは存在するが、いずれも`Internal=false`だった。

Dockerの内部専用ネットワークによる隔離は設定されていない。他のファイアウォール等による通信制御は今回調査していないため、現在の通信可否や隔離状態までは断定しない。

## 3. 構成図との対応と再現範囲

| 構成図の要素 | 取得済み資材で再現できる範囲 | 追加・確認が必要なもの |
| --- | --- | --- |
| 左側の旧App | AL2・Apache・Passenger・Railsの組み合わせと、最小アプリの実行環境 | 本来の業務アプリ、DB接続、既存バッチとその依存先 |
| テナント別DB 1 / DB 2 | 取得済みMySQLを複数起動し、テナント別の接続先を用意する構成 | 本番DBのエンジン・バージョン、スキーマ、検証用データ、接続権限 |
| 共通ECS上のGo API | Goサービスをコンテナとして配置する構成 | APIコード、テナント判定、DB接続先切替、認証、内部連携 |
| 共通ECS上のRails Web App | Railsアプリをコンテナとして配置する構成 | 移行対象のコード、設定、旧Appとの機能分担 |
| Go Worker / Batch | Goコンテナを利用したワーカー・バッチ実行 | 処理コード、起動方式、重複実行防止、旧バッチとの分担 |

| 旧環境のインターネット分離 | 公開入口と内部経路を分け、旧Appの公開停止後も内部DB接続を維持する検証 | Compose等の定義、通信経路の設計、受信・送信それぞれの検証 |

既存の`gym`・`ec`・`ticketing`用イメージが、今回の移行先サービスそのものであることは確認していない。再利用できる実行環境の候補として扱う。

5テナントへの展開は構成を増やすことで検討できるが、同時稼働に必要なメモリ・CPU・ディスク容量は未評価である。

## 4. 旧App用イメージの再現度

旧Appに近いイメージには、次の[Dockerfile](../docs/ec2/port-guard-rollout/al2-instance/Dockerfile)と[説明資料](../docs/ec2/port-guard-rollout/al2-instance/README.md)がある。

| 要素 | 定義・資料上の構成 |
| --- | --- |
| OS | Amazon Linux 2 |
| Apache | 2.4.56 |
| Passenger | 6.0.18 |
| Ruby | 2.7.7 |
| Rails相当部分 | `railties` / `actionpack` 4.2.11.3による最小アプリ |
| その他 | SSH、cron、iptables。Composeでは`NET_ADMIN`を付与 |

この環境は、旧AppのWebサーバー構成やアクセス制御を試す土台として使える。ただし、以下の制約がある。

- 本来の業務アプリや既存バッチは含まれない。
- 最小アプリのGemfileにはActive RecordやMySQL接続用の定義がなく、業務アプリとしてのDB接続は追加が必要。
- systemdを動かさないため、systemdサービスの起動・起動時の復元は再現対象外。
- 資料上はarm64向けの環境であり、旧EC2のx86_64と同一条件ではない。
- SSH・HTTP・HTTPSは既存Composeでホストへ公開する定義になっている。分離を試す場合は公開方法を変更する必要がある。

上記のバージョンと制約はローカルの定義・資料から確認したもので、今回コンテナを起動して再検証した結果ではない。

## 5. ローカル検証とAWS上の検証の境界

ローカルでは、アプリ間の連携、テナント別DB接続、旧・新サービスの併存、公開経路の切替、旧Appの公開停止後の内部疎通を検証対象にできる。

一方、次の項目はDockerによる代替構成だけでは確認できず、AWS環境で別途検証する。

- ECSのタスク配置、サービス管理、デプロイ、スケーリング。
- IAMやタスクロールによるAWSリソースへのアクセス。
- CloudFront固有のキャッシュ、オリジン接続、公開設定。
- VPC、サブネット、ルート、セキュリティグループによる実際の通信制御。
- EC2の起動・復旧、SSM、実際の外部BI接続などの運用。

取得済みMySQLでの動作確認は、本番DBとの互換性確認を代替しない。また、Docker上で旧Appへのアクセスを遮断できても、AWS上の旧環境の分離が完了した証拠にはならない。

## 6. 最初に作る検証構成（案）

最初は、旧Appを1台で代表させ、テナント切替の違いを確認できる2テナントから始める。

| 要素 | 検証用の構成 |
| --- | --- |
| 公開入口 | 旧Appと共通APIへ振り分けるリバースプロキシ |
| 旧App | 取得済みAL2イメージを1台。検証用のDB接続処理を追加 |
| 共通API | Goコンテナを1台。テナント識別と接続先切替を実装 |
| テナントDB | 2テナントそれぞれのDB 1 / DB 2。接続先を分けて試す場合はMySQLを計4コンテナ |
| ネットワーク | 公開入口用と内部接続用の経路を分け、旧App・DBへの直接公開を避ける |

この段階では、5テナントすべての旧App、新Rails、Python、ワーカー、BI連携は再現範囲に含めず、中心となる切替と分離を先に検証する。

確認する動作は次のとおり。

1. テナントごとに異なる検証データを用意し、APIが正しいDBへ接続する。
2. 旧Appと共通APIが、意図したテナントのDBを利用できる。
3. プロキシから旧Appへの公開経路を閉じ、ホストから旧Appへ直接到達する経路も閉じる。
4. 公開停止後も、共通APIから各テナントDBへの接続と、旧Appに残す内部処理が動作する。
5. 外向き通信も遮断する方針の場合は、旧環境からの送信を制限し、必要な内部連携が継続する。

その後、5テナント化、新Rails・Python・ワーカーの追加、BI連携、残置する既存バッチとの整合性確認へ広げる。これは検証構成の提案であり、Compose定義の作成やコンテナの起動は未実施である。

## 7. 調査方法

今回実行した読み取り確認は以下のとおり。

- `docker context show`：利用するDockerコンテキストの確認（`desktop-linux`）。
- `docker ps -a`：既存コンテナ・イメージ名・終了状態の確認。
- `docker image ls`：取得済みイメージの確認。
- `docker inspect`：代表的なGo・Python・Rails・旧Appコンテナの起動コマンドとマウントの確認。
- `docker network ls`：既存ネットワークと`Internal`属性の確認。
- ホスト側のコード参照先と、旧App用Dockerfile・Compose・Gemfile・説明資料の確認。
