# 性能差について確かめていないこと

作成日: 2026-11-12

`runtimes.md`（9 章・10 章）と `swift-csharp.md`（2 章・3 章）の計測で見えた性能差のうち、**理由を確かめていないもの**をまとめる。各項目に「分かっていること」「仮説」「確かめ方」を書く。数字はすべて mandel（1200×900、最大反復 1000）の計算時間で、ネイティブ比は Go ネイティブ（約 386 ms）を 1.00 とした値。

---

## 用語

| 名前 | 指すもの |
|---|---|
| **計算時間** | プログラムの中で計った、計算だけにかかった時間（JSON の `elapsedMs`） |
| **全体の時間** | プロセス（コンテナの場合はコンテナ）の起動から終了までの時間 |
| **Liftoff / TurboFan** | V8（Node.js、Deno、Chrome）の Wasm のコンパイラ。Liftoff は手早く作る簡易なもの、TurboFan は時間をかけて最適化するもの |
| **Cranelift / winch** | Wasmtime のコンパイラ。Cranelift が既定の最適化するもの、winch は簡易なもの |
| **スピル** | レジスタに置ききれない変数を、メモリ（スタック）に退避して読み戻すこと |
| **機械語の確認** | Wasm から実行環境が作った CPU の命令を、逆アセンブルして読むこと（Wasmtime なら `wasmtime compile` と `objdump -d`） |

## Q1. 標準の Go の Wasm が、`//go:noinline` を付けても Wasmtime で速くならない理由

**分かっていること**

| | Wasmtime での計算時間 |
|---|---:|
| TinyGo（元） | 約 775 ms |
| TinyGo（`//go:noinline`） | 約 380 ms（ネイティブと同じ） |
| 標準の Go（元） | 約 820 ms |
| 標準の Go（`//go:noinline`） | 約 790 ms（ほぼ変わらない） |

TinyGo では、計算のループが大きな関数の中に置かれてスピルが起きることが原因だと、機械語で確かめた（`runtimes.md` 10-4）。標準の Go では、同じ対策が効かなかった。

**仮説**: 標準の Go の Wasm は、Go 独自のスタックをメモリ上に持ち、ローカル変数をそのスタック（Wasm のメモリ）に置く。そのため、関数の大きさに関係なく、ループの中でメモリの読み書きが多い。また、goroutine を切り替えられるように、関数を「途中から再開できる形」（関数全体を大きなループと分岐表で包む形）で出力するので、最適化が効きにくい。

**確かめ方**

1. 標準の Go の Wasm を `wasm-tools print` で WAT にし、`mandelbrot` のループで `i64.load` / `f64.store` などのメモリ操作が出ているかを見る
2. `wasmtime compile` と `objdump -d` で機械語を見て、ループの中のメモリ操作を数える（TinyGo と同じ方法）
3. 関数の入口に分岐表（`br_table`）があるかを見る

## Q2. Swift と C# の Wasm が、Wasmtime でネイティブと同じ速さになる理由

**分かっていること**: Wasmtime での計算時間は、Swift 382.7 ms、Embedded Swift 383.2 ms、C# 382 ms で、どれもネイティブと同じ。同じ Wasmtime で、Go・TinyGo は約 2 倍。

**仮説**: Swift（LLVM）も C#（NativeAOT-LLVM）も、計算の関数を小さな関数のまま出力していて、goroutine のための仕組みも入らない。そのため、Q1 のようなスピルが起きない。

**確かめ方**

1. 各 Wasm を `wasm-tools print` で WAT にし、計算のループがどの関数にあるか、その関数の大きさ（ローカル変数の数、命令の数）を見る
2. 機械語でループの中のメモリ操作を数える
3. 結果を Go・TinyGo・手書きの WAT と並べて表にする

---

## Q3. V8（最適化後）と wazero が、Go・TinyGo の Wasm で Wasmtime より速い理由

**分かっていること**

| 実行環境 | 標準の Go → Wasm | TinyGo → Wasm |
|---|---:|---:|
| V8（`--no-liftoff`） | 1.03 | 1.00 |
| wazero | 1.62 | 1.03 |
| Wasmtime | 1.96 | 2.04 |

**仮説**: V8 の TurboFan と wazero のコンパイラは、大きな関数でもループの変数をレジスタに置けている、またはメモリの読み書きをまとめて減らせている（レジスタの割り当て方や、ループの中の読み書きの最適化の違い）。

**確かめ方**

1. **V8**: Node.js の `--print-wasm-code`（または `--code-comments` などの設定）で機械語を出せるか調べる。出せなければ、リリース版の Node.js では難しいことを記録する
2. **wazero**: 機械語を取り出す方法を調べる（Go のライブラリとして使い、コンパイル結果を取り出せるか）
3. 取り出せたら、TinyGo のループの機械語を Wasmtime のものと比べる

## Q4. wazero で、標準の Go と TinyGo の差が大きい理由

**分かっていること**: wazero での計算時間は、標準の Go が 1.62 倍、TinyGo が 1.03 倍。V8 ではどちらもほぼ 1.0 倍。

**仮説**: Q1 と同じく、標準の Go の Wasm はメモリ上のスタックの読み書きが多く、wazero はそれを V8 ほど減らせていない。

**確かめ方**: Q1 の結果（標準の Go の Wasm の形）と、Q3 の wazero の機械語を合わせて見る。

---

## Q5. 言語によって、V8 の Liftoff での遅さが違う理由

**分かっていること**（Node.js の既定。1 回目の呼び出しが最後まで Liftoff のコードで動く）

| 言語 | ネイティブ比 |
|---|---:|
| 標準の Go | 3.49 |
| TinyGo | 2.41 |
| Swift | 2.39 |
| 手書きの WAT（1 回目） | 2.40（927 ms） |
| Embedded Swift | 1.68 |

**仮説**: Liftoff はほとんど最適化をしないので、出力された Wasm の命令の数や形がそのまま速さに出る。Embedded Swift は命令が素直で少なく、標準の Go はメモリ上のスタックの読み書きが多い。

**確かめ方**: 各 Wasm の計算のループの命令の数を数えて、Liftoff での時間と比べる。V8 の `--liftoff-only` などで、Liftoff だけの時間を安定して計る。

## Q6. Rust の mandel の速さ（未計測）

**分かっていること**: Rust は wcount しか作っていない。10-4 では「Rust は関数の分け方を自分で決めやすいので問題を避けやすい」と書いたが、確かめていない。

**確かめ方**: mandel を Rust で書き（Go 版と同じ計算と JSON）、`wasm32-wasip1` でビルドして、`bench/bench-cli.mjs` に行を足して計る。

## Q7. wazero の全体の時間が長い理由と、`-cachedir` で短くなるか

**分かっていること**: 標準の Go の mandel（4.5 MB）で、wazero の全体の時間は約 1,470 ms、計算時間は約 626 ms。差の約 850 ms のうち、コンテナの起動（約 0.57 秒）を除いても、約 0.3 秒が残る。

**仮説**: wazero は読み込むときに Wasm 全体を機械語にする（事前にまとめてコンパイルする方式）。Wasm が大きいほど時間がかかる。

**確かめ方**

1. `-cachedir` を指定して 2 回実行し、2 回目の全体の時間が短くなるかを見る（コンテナでは、キャッシュの置き場所をボリュームにする必要がある）
2. 大きさの違う Wasm（Go 4.5 MB、TinyGo 1.36 MB、Embedded Swift 67 KB）で、全体の時間と計算時間の差を比べる

## Q8. コンテナの起動にかかる時間の内訳

**分かっていること**: ホストの Wasmtime とコンテナの Wasmtime で、全体の時間の差は約 0.57 秒。

**仮説**: `docker compose run` が、コンテナの作成、ネットワークの準備、ボリュームのマウントを毎回行っているため。

**確かめ方**: `docker run --rm` を直接使う場合、`--network none` を付ける場合、空の Wasm（hello）を動かす場合の全体の時間を比べる。

---

## Q9. Wasmtime の計算時間のばらつき

**分かっていること**: 標準の Go の mandel で、Wasmtime の計算時間の中央値が 836 ms のとき、最小は 731.7 ms だった。ほかの実行環境ではばらつきが小さい。

**仮説**: スピルしたメモリの読み書きが、CPU のキャッシュやメモリの配置の影響を受けやすい。または、同じ時期に動いていたほかの処理の影響。

**確かめ方**: 回数を増やし（例: 20 回）、ばらつきを見る。`//go:noinline` 版（スピルが起きない）でもばらつくかを比べる。

---

## Q10. 計測の方法そのものの限界

**分かっていること**: どの計測も、1 台の Mac（Apple M5）で、各 5 回の中央値。ほかのアプリが動いている状態で計った。

**気を付けること**

- 5 回では、ばらつきの大きい項目（Q9）の判断には足りない
- CPU の温度や省電力の状態で結果が変わる可能性がある
- x86_64 の CPU では、結果の傾向が変わる可能性がある（特にレジスタの数が違うので、スピルの起き方が変わる）
- 計算時間は、各言語の時刻の取り方（Go の `time.Now`、Swift の `ContinuousClock`、C# の `Stopwatch` など）に依存する

**確かめ方**: 回数を増やす、何回か時間をおいて計る、可能なら x86_64 の環境でも計る。

## Q11. ブラウザの種類による違い

**分かっていること**: ブラウザでの計測は、ヘッドレスの Chrome 157 だけ。

**確かめ方**: Safari（JavaScriptCore。手元にある）で `web/index.html` を開いて計る。Safari は DevTools Protocol で自動化できないので、手で開いて結果を読む。Firefox（SpiderMonkey）は入っていない。

## 進め方の案

1. **Q1 と Q2 を先に確かめる**: 手元の道具だけで、10-4 と同じ方法（WAT と機械語の比較）で確かめられる。「言語ごとに Wasmtime で速さが違う理由」が 1 つの表にまとまる
2. **Q6（Rust の mandel）を足す**: 計測の表の空いているところを埋める
3. **Q7、Q8 は運用に関係する**: サーバーや CLI で使うときの起動の速さに効くので、必要になったら確かめる
4. **Q3〜Q5 は手間がかかる**: V8 と wazero の機械語の取り出し方の調査が要る
